Governance · Policy

Promotion policy

When does a way of putting components together stop being a pattern and become a component? This system had five composites and no written answer, which is how a specification came to cite a “rule of three” that did not exist. This page is the answer: the tier definitions, the evidence each promotion needs, what a closed specification without code does and does not oblige, and when a component may be frozen.

Why this exists

On 7 Sep 2026 the FileUpload specification justified shipping without an implementation “per the composite policy · the rule of three”, and asserted that two surfaces already assembled it by hand. Neither the policy nor the surfaces existed; both were plausible inferences stated as governance. The claims are retracted in that spec's §14 rather than deleted, and this card replaces them. A citation is only worth making if the thing cited can be read.

Promotion

The evidence each step requires
01

Pattern → Composite

Two tests, both required

An assembly earns a component when repeating it by hand is unsafe, not merely tedious.

  • The ownership test. Name a contract the assembly holds that no part can hold alone — an aggregate state, a relationship between two controls, a single identity over several inputs. If everything the assembly does belongs to one of its parts, it stays a pattern however often it recurs. FileUpload passes on “is this set finished?”; a Stack of buttons fails, which is why Toolbar's §01 argues the point rather than assuming it.
  • The consequence test. Say what goes wrong when the assembly is rebuilt slightly differently. If the answer is “it looks a bit off”, that is a pattern with a reference implementation. If it is “the ECR releases with the BOM at 64%”, it is a component. A promotion needs a failure worth preventing, stated in the product's own terms.

Recurrence is evidence, not a threshold. Two independent surfaces wanting the same assembly is a strong signal and worth citing — but there is no count that promotes anything on its own, and there is no queue. A single surface with a dangerous aggregate qualifies; five surfaces sharing a padding convention do not.

02

Composite → Core

Rare, and reversible only by deprecation

A composite becomes Core when it stops being decomposable: when its parts are no longer separately useful, or when its contract has grown to include states its parts cannot express.

  • The test: would anyone use the parts alone? FileDropzone and FileItem are separately useful (a read-only attachment list, a bare picker), so FileUpload stays composite. If a composite's parts only ever appear inside it, the assembly was really one control.
  • The cost: a full fourteen-section Core spec, and the parts become internal. Do not take this step to make an import shorter.
03

Anything → nothing

Demotion is a real move

A component whose contract turns out to belong to its consumers should be demoted to a pattern, not kept for politeness. State it in §14, keep the export for one minor version, and move the prose to specs/patterns. Nothing in this system is entitled to remain a component because it once was.

Specification without code

What a closed spec obliges, and what it does not
  • A spec may be closed before an implementation exists, and that is often the right order — the standard is what the implementation is written from, and FileUpload was built from its own closed spec without reopening it.
  • A closed spec binds anything that solves the same problem, component or not. Conformance is judged against the spec, so a hand-built attachment set that derives no aggregate status is wrong whether or not it imports the component.
  • A closed spec does not oblige anyone to build it, and it must not claim consumers it does not have. If the spec says two surfaces assemble this by hand, two surfaces must be nameable and readable.
  • Say which state it is in, in the masthead. specified, not built · built <version> · frozen <date>. A reader should never have to grep the components folder to find out whether a spec has code.

Freezing

What the word means here
  • Freeze after a consumer, not after a build. A shape has survived nothing until something outside the design system has used it. FileUpload was built at 1.30.0 and frozen at 1.30.1 — the two props in between (requiredMessage, showRequired) were found by building a real surface against it, and would have been frozen out had the freeze followed the build. Both are demonstrated in the evidence attachment reference implementation, which is the consumer that survives; the first one was deleted once that superseded it, and the citation was moved rather than left dangling.
  • Frozen means the API is closed, not that the component is finished. Additive exports and internal fixes continue: FileDropzone gained fileGlyph at 1.29.1 while frozen, because a new export changes nothing for existing callers.
  • Zero open items is a requirement of freezing, and “closed as decided” is how an item reaches zero. Every closure states the decision and its reason, so it cannot return as a fresh question — an item that merely disappears reads as an oversight.
  • Unfreezing is a breaking change with a version and a note. It is allowed. It is not quiet.
