Two system decisions

Both of these were logged three times, independently, by three different component specs. One sighting is a component gap; three is the system declining to decide something. Each is answered here once, and the component entries point at this page rather than repeating it.

Container queries

Adopted · 1.23.0

Logged by EmptyState §14, List §11 and DescriptionList §14 — each wanting to adapt to the width of the panel it sits in rather than the viewport, and each noting that no component in the system used a container query yet.

  • Support is not the obstacle it was when the first entry was written. Chrome and Edge 105+, Safari 16+, Firefox 110+ — all shipped by early 2023, all inside this system's stated floor.
  • No fallback is written, deliberately. In an unsupporting browser the @container block is skipped and the component keeps its authored layout — which is exactly what products get today. The failure mode of the new feature is the current behaviour.
  • Opt-in via responsive, never automatic. All three components are frozen. A default that changed underneath a shipped product is not a responsive improvement; it is a regression nobody asked for.

The real cost, stated plainly: this is the system's first component stylesheet. Every component here styles inline, on purpose, and @container has no inline equivalent — it is an at-rule or it is nothing. So tokens/container-queries.css exists, and its rules carry !important, because an inline style outranks a class selector and the component's own authored value is precisely what is being overridden.

That is a genuine erosion of a rule this system has kept everywhere else, which is why the file is kept to three components, a handful of properties, and only properties the specs already document as responsive. It restyles nothing generally. If it grows past that, the decision should be revisited rather than the file extended.

What each component does: DescriptionList collapses to stacked pairs below 360px — a 180px term column against a 120px value column is two truncated columns rather than an alignment. List tightens to the sm rhythm below 380px; its structure never changes, because §11 already fixes what shrinks and what does not. EmptyState drops the illustration below 380px, since the glyph is decoration and the title and action are the content.

Closes: EmptyState §14 · List §11 · DescriptionList §14

Virtualisation

Refused · not this system's job

Logged by Combobox, MultiCombobox and List: five thousand options or rows render five thousand nodes. The request each time is windowing — render the visible slice, and a spacer for the rest.

  • Windowing needs a fixed row height, and two of the three deliberately do not have one. List §05 states it outright: a list row is as tall as its content because nothing aligns across rows, and a min-height would put empty space under single-line rows in a run that also holds three-line ones. A windowing engine would either impose that height — undoing the reason the component exists — or measure every row, which is the work it was meant to avoid.
  • It moves a data problem into the view layer. Five thousand options in a Combobox is not a rendering problem; it is a filter that has not been applied. The honest fix is server-side paging or a capped result set, and it makes the interaction better rather than merely faster: nobody scrolls five thousand rows to find one.
  • Half a windowing implementation is worse than none. It breaks find-in-page, anchor links, screen-reader row counts (aria-setsize has to be maintained by hand), keyboard Home/End, and printing. Each is fixable; together they are a library, and a design system that ships one is maintaining a library it did not set out to write.

So the guidance is: cap or page on the server, and the components stay simple. A product that genuinely needs windowing should wrap the component with a windowing library of its choosing — the components take arrays and render what they are given, which is exactly what makes that possible. This is a refusal with a route, not a refusal with a shrug.

Answers: Combobox · MultiCombobox · List §14 — the entries stay open as known limits, not as work
