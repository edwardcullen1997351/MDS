Composite Component specification standard

A Composite Component is a standardized assembly of existing Core Components that carries meaning the parts do not carry alone. Its specification documents only what the composition adds. This page fixes the sections such a specification may contain, their order and numbering, and the test for including or omitting each one — so that any two composite specs in this system can be read the same way.

How to apply it

  • Two sections are unconditional; twelve are conditional. Purpose and Anatomy appear in every composite specification. The rest appear only when their include test is met.
  • Numbers are stable identifiers, not positions. A section keeps its number from this list whether or not the sections before it are present, so a cross-reference such as §07 Keyboard means the same thing in every spec. Sections appear in ascending numeric order and are never renumbered.
  • Omit rather than stub. An omitted section is absent — no heading, no "n/a", no restatement of a child component's contract. A section that only repeats what Chip or Select already documents is noise, and its presence implies the composite owns behaviour it does not own.
  • Every included section states a contract the composite owns. The recurring test behind all twelve conditionals is the same one: does the composition create this, or does it inherit it? If the answer is inherit, the section is omitted and the reader goes to the child spec.
  • Borderline calls are logged, not silently resolved. If it is genuinely unclear whether a behaviour is composite-owned, include the section and say so in it. A named open question is a decision the system can make later; an omission is invisible.

Required

Present in every composite specification
§01

Purpose

Always

Defines the semantic role of the Composite Component, the recurring UI problem it solves, and why that problem warrants a standardized component.

Include

Always. Every Composite Component requires an explicit reason for existing.

Omit

Never.

§02

Anatomy

Always

Defines the structural parts of the component, which parts are required or optional, and the relationships between them.

Include

Always. A Composite Component must have a defined composition.

Omit

Never.

Conditional

Included only when the composition creates the contract
§03

Properties

Conditional

Defines meaningful public configuration, content, behavioral, value, event, or integration inputs exposed by the composite.

Include

The composite requires a stable public API beyond the APIs of its constituent components.

Omit

Configuration can be expressed entirely through existing child-component APIs without additional composite-level meaning.

§04

Variants

Conditional

Defines a small set of semantically or behaviorally distinct standardized forms of the component.

Include

Multiple recurring forms have meaningfully different contracts that belong to the same abstraction.

Omit

Differences are cosmetic, arbitrary, content-driven, or adequately represented through existing child-component properties.

§05

Sizes

Conditional

Defines standardized component-level size options and the coordinated sizing rules they impose on constituent components.

Include

The entire composite requires coordinated size behavior.

Omit

Child-component sizing is sufficient, or independent sizing is appropriate.

Note, from practice. This is the section most often omitted by mistake. If a composite lays controls out in one row or one column, they share a height or width rhythm, and a single child left at its own default is visibly wrong — that is coordinated size behaviour, and only the composite can know all the pieces. Both composites built so far include §05 for exactly this reason. Omit it when the parts do not share an axis, or when their sizes are genuinely independent.

§06

States

Conditional

Defines states owned or coordinated by the composite rather than independently owned by its constituent components.

Include

The composite introduces meaningful states such as an aggregate value state, invalid relationship, expanded state, or coordinated disabled state.

Omit

All relevant states belong entirely to existing child components.

§07

Keyboard

Conditional

Defines keyboard interaction introduced by the composition, including focus movement, shortcut behavior, or coordinated keyboard operation.

Include

Combining components creates keyboard behavior not already defined by the constituent Core Components.

Omit

Existing child-component keyboard contracts completely determine behavior.

§08

Accessibility

Conditional

Defines semantic relationships, accessible naming, focus management, announcements, roles, reading order, and assistive-technology requirements created by the composition.

Include

The composite creates accessibility relationships or requirements beyond those of its individual children.

Omit

Composition introduces no additional accessibility contract.

§09

Motion

Conditional

Defines transitions or animation behavior owned by the composite.

Include

Motion communicates or supports a composite-owned state transition.

Omit

Motion belongs entirely to constituent components, or is merely decorative.

§10

Content rules

Conditional

Defines constraints governing content hierarchy, terminology, ordering, length, labels, truncation, or required supporting information.

Include

Consistent content structure is necessary for the component to preserve its semantic identity or usability.

Omit

The component accepts unconstrained content without compromising its contract.

§11

Responsive

Conditional

Defines standardized structural or behavioral changes triggered by available viewport or container space.

Include

The composite must change composition or interaction behavior at constrained sizes.

Omit

Ordinary layout primitives adequately handle adaptation without changing the component contract.

§12

Anti-patterns

Conditional

Defines recurring misuses that compromise semantics, usability, accessibility, or component boundaries.

Include

The abstraction has plausible and consequential misuse cases worth explicitly preventing.

Omit

Existing component documentation already makes misuse sufficiently clear.

§13

Implementation notes

Conditional

Defines internal structural, state-management, DOM, composition, or architectural requirements needed for consistent implementations.

Include

Correct implementation depends on constraints not apparent from the public API.

Omit

The implementation follows directly from the anatomy and existing child-component contracts.

§14

Developer notes

Conditional

Defines developer-specific integration guidance, event contracts, controlled/uncontrolled behavior, value representation, or other API considerations.

Include

Consumers require technical guidance beyond the component's general properties and implementation requirements.

Omit

Properties and implementation documentation adequately define the developer contract.
