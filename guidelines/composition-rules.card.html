Universal Composition Rules

A design system that ships 78 flawless components and 7 layout templates will still produce mediocre product screens if the rules of assembly are unwritten. This document is the master composition contract of the Meridian Design System: the explicit rules governing container nesting, data surface framing, feedback boundaries, and state choreography.

The Prime Directive of Composition

Never invent a container when the page, the frame, or the component already provides the boundary. In high-density industrial consoles, visual noise is cumulative: an unnecessary border, an extra wrapper div, or a misaligned card creates cognitive drag that degrades operator speed and situational awareness.

1. Container & Surface Nesting

Rules 01–03
§01

Card nesting law

Never nest a Card inside another Card. Two hairlines one inside the other say "this is grouped" twice and create visual vibration.

  • To group within a Card: Use an internal hairline divider (border-top: var(--border-hairline)), a section heading, or a sunken well (Surface tone="sunken").
  • To present a collection of items: Use List or Table inside a single enclosing Card, never a stack of mini-cards.

§02

Table & Card union

Tables live in Card padding="none" by canonical contract.

  • Header: Card title and subtitle name the dataset. Card actions hold collection-level buttons.
  • Body: The Table component is rendered with padding="none" so column rules meet the card hairline seamlessly.
  • Footer: Card footer houses Pagination, with footerAlign="end" or "between" (showing status readout on the left and pagination controls on the right).
  • Border collapsing: base.css automatically removes the bottom border on the last table row so it never doubles against the card footer.
§03

DescriptionList framing

A DescriptionList represents one record's fields. It is framed according to the host layout:

  • In Master-Detail / SplitView detail panes: Rendered directly inside the detail <section> with divided={true}, no surrounding Card needed.
  • In Dashboard modules: Hosted inside a Card padding="md" with layout="rows" or layout="columns".
  • In SingleColumn records: Placed in a Surface well to differentiate static record metadata from editable fields.

2. Feedback & Structural States

Rules 04–06
§04

Alert placement boundaries

Feedback LevelComponentPlacement & Rule
System / Service FailureAlert (live="on", tone="danger")Replaces the failing collection region (e.g. within a Card or Module). Never blank the entire screen if only one service failed.
Validation ErrorsField error messageRendered directly under the invalid control. A summary Alert is permitted only at the top of the form for >3 simultaneous errors.
Background OperationToast / ToasterFloating toast in bottom-right viewport. For non-blocking success announcements (e.g. "Calibration booked").
Destructive GateDialogModal dialog with explicit confirmation contract. Never used for passive notification.
§05

State choreography in Collections

Every collection surface (in CollectionWorkspace, Dashboard, MasterDetail) supports five discrete states that replace distinct regions:

  • 1. Loading State: Skeleton placeholder with lines matching the expected row count (8–10 lines). Skeletons replace the table body; controls and headers remain mounted.
  • 2. Collection-Level Failure: Alert with retry action replaces the collection surface; search and filter controls stay reachable so user input is not lost.
  • 3. Empty Register (First-run): EmptyState variant="first-run" replaces the empty table, offering primary action to create/import first record.
  • 4. No Matches (Refinement empty): EmptyState variant="no-results" with a secondary action to clear search/filters.
  • 5. Selection Active: Raises the bulk action region (Region 3) above the collection without displacing reading position.

3. Layout Framework Alignment

Rules 07–09
§06

Form sequence & width caps

Forms must follow SingleColumn measure caps to prevent ocular fatigue:

  • Form Container Width: size="sm" (640px) or size="md" (900px) maximum. Never use fluid full-width for forms.
  • Two-column pairs: Permitted only for naturally paired inputs (e.g. Start Date + End Date, First Name + Last Name, Quantity + Unit).
  • Action Region: Terminal (at sequence foot) by default; sticky anchored only for long workflows with >12 fields.
