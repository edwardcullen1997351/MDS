3-Tier Component Hierarchy

Meridian structures its UI inventory into three discrete classifications to resolve the tension between structural complexity (how an element is composed) and functional domain (what job an element performs). Every export in the library belongs unequivocally to one of these three tiers.

The Classification Law

Never mix structural tiers with functional concerns. Primitives (layout/foundations) and Composites (multi-part assemblies) represent structural tiers. The 5 functional domains (Core, Forms, Feedback, Navigation, Data) are sub-categories that sit strictly within Tier 2: Components.

Tier 1

Primitives

Token consumers & layout frame. Pure structural abstractions with no interactive states, no keyboard contracts, and no business logic.

Box Stack Grid Container Surface Text Heading Divider Spacer Image AspectRatio
Tier 2

Components

Single-purpose building blocks. Discrete UI controls with designed states, keyboard navigation, and full 14-section specifications across 5 functional domains.

Core Forms Feedback Navigation Data
Tier 3

Composites

Multi-part assemblies & workflows. Standardized compounds combining multiple Tier 2 components with synchronized state and cross-field logic.

DateRangePicker DateTimePicker FileUpload ScopePicker SearchField SortableCollection SplitButton Toolbar

Tier Comparison & Specification Requirements

Rules of Governance
Tier Primary Responsibility Specification Contract Interactive States & ARIA Consumer Rules
Tier 1: Primitives Geometry, layout rhythm, surface styling, typography scale mapping. .d.ts prop types, .prompt.md, token scale validations in scale.js. No 14-section spec (policy). None (except Surface interactive hover tint). No keyboard navigation, no ARIA roles. Reach for primitives before div. Pass token names, never raw px/hex values.
Tier 2: Components Single-purpose controls across Core, Forms, Feedback, Navigation, and Data. Full 14-section spec (.spec.html) required before freezing. API is closed. Four states always designed (rest, hover, press, focus). Full keyboard and ARIA compliance. Never fork or hand-roll custom styling. Use semantic tokens and props.
Tier 3: Composites Multi-component assemblies, multi-field synchronisation, compound workflows. 14-section conditional standard (composite standard) documenting only what composition adds. Coordinates state across constituent Tier 2 children; owns cross-control focus movement. Use when 2+ components recur together with coordinated sizing or shared state.

The Five Functional Sub-Domains of Tier 2

Components Tier Breakdown

1. Core & General

  • Role: Fundamental interactive units and markers.
  • Members: Button, IconButton, ButtonGroup, Avatar, AvatarGroup, Badge, Chip, Tag, Card, Link, SegmentedControl, Fieldset, Icon.

2. Forms

  • Role: Data capture, selection, range adjustment, and text entry.
  • Members: Input, Textarea, Select, Checkbox, CheckboxGroup, Radio, RadioGroup, Switch, Slider, RangeSlider, DatePicker, TimeField, Autocomplete, Combobox, MultiCombobox, FileDropzone, FileItem.

3. Feedback & Overlays

  • Role: Alerting, confirmation gates, transient notifications, contextual popovers.
  • Members: Alert, Dialog, Drawer, Popover, Tooltip, Toast, Snackbar, Progress.

4. Navigation

  • Role: Wayfinding, hierarchy switching, pagination, and multi-step progressions.
  • Members: Tabs, Breadcrumb, Menu, Pagination, StepNavigation, SequentialNavigation, GlobalNavigation, LocalNavigation, InPageNavigation, TreeNavigation, ScopeNavigation.

5. Data & Visualization

  • Role: Tabular listings, hierarchical trees, record summaries, and quantitative telemetry.
  • Members: Table, List, DescriptionList, Tree, EmptyState, Skeleton, BarChart, LineChart, AreaChart, PieChart, Heatmap, GeoMap, GanttChart, ScatterPlot, Treemap, NetworkDiagram, ParallelCoordinates, DistributionPlot, RangeChart, SankeyDiagram, TreeDiagram.
