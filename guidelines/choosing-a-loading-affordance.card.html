Choosing a loading affordance

There is no Loading component, and there should not be one. The system already has four, and each is a different answer to a different question. A fifth name over the top of them would be the List problem — one vague word standing for several unrelated things — except worse, because here nothing is actually missing. What was missing is this page: nothing told a consumer which of the four to reach for.

Pick by what you know

You know…UseBecause
The shape of what is coming, and it fills a regionSkeletonIt reserves the layout, so the page does not jump when content lands. The only affordance that prevents shift rather than covering it.
How much is done, as a percentageProgress value={n}A real measure. Never ease it toward 90 % while waiting — a bar that advances on a timer is a lie with a progress indicator's authority.
That work is happening, but not how long, and it owns the regionProgressIndeterminate bar. Says “working”, never “how long”.
That work is happening, in a small in-line spotProgress variant="spinner"A ring beside a control or in a cell. It reports nothing measurable — a ring that shows a percentage is a chart.
The user just pressed this buttonButton loadingThe feedback belongs on the thing they pressed, and it disables the button so the action cannot double-fire.
There is nothing, and there will be nothingEmptyStateNot loading at all. A spinner that never resolves is how an empty result is usually mis-shipped.

The delay that stops the flash

An indicator that appears for 120 ms and vanishes is worse than none: the flash reads as a glitch, and in a list that reloads per keystroke it strobes. Below roughly 300 ms a human reads the response as instant, so the honest indicator is nothing at all.

<Progress label="Searching" variant="spinner" delay={300} />
<Skeleton lines={4} delay={300} />

delay renders nothing until the threshold passes — not an empty reserved box, which would be the layout shift moved earlier. It defaults to 0 on both components because both are frozen, and a default that delayed a shipped product's spinner would be a behaviour change nobody asked for. Reach for it on anything that can return fast; leave it off for work you know is slow.

The rule that outranks all of the above

Under reduced motion, every loop in this system stops dead — tokens/motion.css collapses them. A spinner becomes a static ring; an indeterminate bar becomes a stationary stripe. So an animation may never be the only signal that work is happening. Whatever shows it must also say so in words: that is why Progress warns when it has no accessible name, and why Button's loading state keeps its label rather than swapping it for a lone glyph.

The sequence a region owes

Loading is one state of four, and the other three are already specified. A region that renders only the first two is the most common defect in this system's consumers.

if (loading)       return <Skeleton lines={4} delay={300} />;
if (error)         return <Alert tone="critical" …>;   // Alert §08
if (!rows.length)  return <EmptyState … />;            // EmptyState §01
return <Table rows={rows} … />;
  • Never swap a spinner for a skeleton mid-load. Two indicators for one wait reads as two waits.
  • Never nest them. A skeleton inside a card inside a page spinner tells the user three times and shifts the layout three times.
  • Do not put a spinner in a disabled button that is not loading. Disabled means unavailable; loading means working. They look alike and mean opposite things.
