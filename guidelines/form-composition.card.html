Guidelines · Composition

Form composition

Forms are the most-built screen in an ERP and the most often built badly, so it is tempting to standardize one as a Layout Template. That would be a mistake: every frame-level responsibility a form screen has is already owned — by single column, by Field and Fieldset, and by the submission patterns. What is genuinely unowned is not a frame but a set of composition decisions: what to ask, in what order, grouped how, at what width, and which pattern the commit belongs to. This card holds those, so that nobody has to invent a seventh layout to house them.

Why there is no Form layout template

Apply the layout template standard's single test — does the layout define this, or does its content? — and a form screen has nothing left to define.

ResponsibilityAlready owned by
One measured column, section rhythm, heading levels, an action region that reserves its heightSingle column — whose own reference implementation is a form: raising a maintenance work request on press line P-2

A "Form" layout spec would therefore restate single column in §02, list Field props in §03 and aggregate field states in §06 — the three things the standard explicitly forbids. The guidance below is what would have been smuggled in with it, and it belongs here because it is cross-cutting composition, not a frame.

Composition

Examples are the same plant throughout — Suryodaya Autocomp Ltd, Chakan plant (PL-04), Pune
01

Ask for less

Every field is a claim that the answer is both known and needed at this moment. A maintenance work request that asks the supervisor for a cost centre he has to phone accounts for is a form that will be filled in wrongly, consistently, for years.

  • Derive rather than ask. Plant, line, shift, requester, cost centre and current date are known from context or the item master. Show them as stated context, not as inputs.
  • Defer rather than ask. A field only the planner can answer belongs on the planner's screen, at their step — that is staged input across roles, not one long form.
  • Optional fields are a cost. If most people skip a field, it is either not needed or it is needed and badly explained. Both are fixed by removing it from the default path.
  • Mark the exceptions, not the rule. Where nearly everything is required, mark the optional ones; where nearly everything is optional, mark the required ones. Never mark both.
02

Order by the user's information, not by the data model

Field order should follow the order in which the person filling the form came to know things. A line supervisor standing at a stopped press knows, in this order: which machine, what happened, when it stopped, whether it is still running, how urgent it is. The table's column order knows nothing about that.

  • One decision per line in the primary flow. A row of three inputs is three decisions presented as one.
  • Identify first, describe second, qualify third. What this is about, then what is being said about it, then the codes and classifications the system needs.
  • Put the field that changes other fields before the fields it changes — a disposition that reveals a rework routing sits above it, never below (conditional input).
  • Never reorder fields between screens for the same object. A requisition that is entered in one order and approved in another makes the approver re-read it every time.
03

Group only where the legend earns its place

A Fieldset asserts that its members are one thing. Use it when the group has a name a person would actually say — "Downtime", "Delivery schedule", "Inspection result" — and when knowing that name changes how the fields are read.

Group

Three fields that answer one question together: stopped at, restarted at, still down. The legend "Downtime" is what the shift log calls it.

Don't group

Four unrelated fields under "Details", or a single field under a legend. A legend that adds no word the reader did not have is heading noise, and screen-reader users hear it on every field.

  • Two levels of grouping is the limit. Fieldsets inside fieldsets means the form is two forms.
  • Six or seven fields per group, at the most. Beyond that the legend stops being a claim about the fields and becomes a chapter title — which is a step (staged input), not a group.
  • Spacing is not grouping. A gap tells a sighted reader that something changed and tells nobody else anything; if the grouping matters, name it.
04

Width says what you expect

An input's width is a hint about the answer's length, and it is read as one. A four-character field for a work-centre code and a full-measure field for a fault description are both instructions.

  • Size the control to the content, not to the column. A quantity, a date, a shift or a part number in a full-width box says "write an essay here" and gets one.
  • Prose measure and input measure are different numbers. Explanatory text stays inside a readable measure; a long text input may be wider than the prose beside it, but never wider than the region.
  • Right-align numbers, and keep units out of the input. Units belong in the label or as a suffix on the field, so the value stays machine-comparable.
  • Never let a field's width vary between screens for the same value. Consistent width is how people learn the shape of an answer.

05

Two columns only for short paired values

Two fields on a line are legitimate when they are one thought — from and to, value and unit, date and shift, quantity and UOM — and both are short. Everything else is a single column, because two columns of inputs create two reading orders and a tab order that agrees with neither.

  • Never split a form into two independent columns of unrelated fields. The pair is the unit, not the column.
  • Pairs collapse to one column when space is short, in the same order they were authored (responsive).
  • A pair never straddles a group boundary. If the two fields belong to different fieldsets, they are not a pair.
  • Required fields do not hide in the right-hand half. Anything that can block submission belongs in the primary flow the eye follows.
06

The action region, and what belongs in it

Single column owns the region's placement and the fact that it reserves its height rather than covering the last field. What goes in it is a composition decision:

  • One primary action, named for what it does — "Raise the work request", not "Submit". The verb is the plant's, not the framework's.
  • At most one secondary and one cancelling action. A row of five buttons means the form has more than one purpose.
  • Destructive actions are not peers of the primary one and never sit adjacent to it.
  • Nothing in the action region validates. Whether the primary action is disabled, and when errors appear, is validated submission's contract; whether leaving with edits warns is explicit save's.
  • Say what will happen next where the answer is not obvious — who receives this, what number it gets, whether it can be edited afterwards. One line above the action, not a paragraph.
07

Staging a form: which frame, which pattern

A staged form is not a layout either. Staged input already owns the ordered stages, the single current stage, the gate on each forward move, the four separate movement controls, the progress rail's limits, focus placement on stage change, resumption and the preservation policy on cancel. The only decision left is where the rail sits — and that is a choice between two frames the system already has.

Rail above → single column

The rail reads as progress: how far through, how much left. Stage content keeps one measure and one action region. The default, and the right answer for a linear task of three to six stages — raising a purchase requisition, importing a supplier catalogue.

Rail beside → sidebar

The rail reads as navigation: a set of places, visible at once. Right when stages are revisited — a long approval dossier, a PPAP submission assembled over days — and it obliges backward movement to actually be permitted (staged input §04), with the rail's own track width, collapse and Drawer relocation coming from sidebar.

  • A lateral rail is a promise. Showing eight stages side by side while refusing to let the user reach stage six is a frame contradicting its pattern. If movement is strictly forward, put the rail above.
  • The rail is not the record of what is done. It reports position in the applicable stage set, never completion (staged input §14) — and stage applicability is recomputed from current values, so a rail that hard-codes a count will lie the first time a stage drops out.
  • Stage content still follows 01–06 above. Ask for less per stage, order by the user's information, one legend per stage, widths that fit the answers. A stage is not a licence to ask for thirty fields because there is a rail to prove progress.
  • The final action is never the forward button. Two controls, two labels, in the action region the frame owns — and "Raise the requisition" is not "Next".
  • If a stage would be a screen of its own for a different role, it probably is one: that is a handover between people, not a step in one form, and the queue each role works is master-detail or a collection workspace.
08

Which pattern the commit belongs to

Choose the pattern before building the form; it decides what the buttons mean.

If the form…Reach for
is entered once and submitted, with rules that must holdValidated submission
edits something that already exists, with a discardable draftExplicit save
runs across steps or roles, each with its own completionStaged input
reveals fields depending on an earlier answerConditional input
requires a document, photograph or certificateEvidence attachment
commits something irreversible or costlyConfirmed action
submits into a system that may not answerAsynchronous action · Recoverable failure

More than one applies on most real screens, and that is expected: a nonconformance disposition is conditional input inside validated submission with evidence attachment. What is not expected is a form built with none of them in mind, which is how a screen ends up with a disabled primary action nobody can explain.

09

Anti-patterns

  • A form in a dashboard grid or across the modules of one — the grid says order does not matter and a form says it does.
  • Asking for what the system knows. Every derived field re-asked is a defect waiting to be entered.
  • Placeholder text carrying the label. It disappears at the first keystroke and was never available to anyone using a screen reader on the field.
  • Help text explaining a badly named field. Rename the field.
  • A wall of fields with one legend, or every field in its own fieldset. Both mean the grouping decision was skipped.
  • Two columns of unrelated inputs, and required fields hidden in the second one.
  • A form that scrolls under its own action bar, so the last field can never be read while the primary action is visible.
  • Inventing a form frame. If a form screen seems to need a layout the system does not have, the thing it actually needs is usually a step boundary or one fewer field.
  • A lateral stage rail on a strictly forward flow, or a rail that reports completion rather than position (07).
