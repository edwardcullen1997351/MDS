Navigation System specification standard

A Navigation System is an architectural framework for wayfinding, orientation, hierarchical traversal, and destination routing across an application or multi-application suite. It owns the wayfinding model: how users locate where they are, discover where they can go, traverse levels (L1 global, L2 operational domain, L3 in-page workspace), resolve active routes, switch contexts, and recover origin trails. Its specification documents navigation-level responsibilities only — distinguishing wayfinding contracts from atomic components (which draw individual buttons or menus) and layout templates (which manage spatial grid regions). This page fixes the fourteen sections a Navigation System specification contains, their order and stable numbering, and what each section must answer.

How to apply it

  • All fourteen sections are defined; numbers are stable identifiers. Like the core standard and layout standard, sections §01 through §14 appear in exact ascending order. A cross-reference such as §07 Keyboard or §08 Accessibility retains the same meaning across all system specifications and is never renumbered.
  • Wayfinding architecture, not generic UI chrome. A navigation specification does not merely list links. It specifies information hierarchy (L1/L2/L3), active state determination, deep-link persistence, state synchronization with URL/history, badge count rollup, permission filtering, and landmark demarcation.
  • Navigation System vs Core Component vs Layout Template. A Core Component (e.g. Link, Menu, Tabs) defines an atomic interactive control. A Layout Template (e.g. Sidebar, MasterDetail) defines spatial containers and scroll boundaries. A Navigation System (e.g. AppShellNav, HierarchicalTreeNav, BreadcrumbTrail, CommandPalette, DrilldownNav) defines the end-to-end wayfinding model, destination hierarchy, routing integration, and user orientation across screens.
  • Unconditional clarity on routing and active identity. Every navigation spec must explicitly define how the active destination is computed (exact match vs prefix match vs ancestor match), how aria-current="page" is applied, and how URL changes synchronize with the navigation state.
  • Real manufacturing ERP context. Examples, labels, badges, and scenarios follow the fixed plant setting: Suryodaya Autocomp Ltd — Chakan plant (PL-04), Pune — real plant domains (Work Orders, Maintenance, Quality NCs, Stores, Shift Planning), rupees formatted en-IN, IST time, Indian supplier and employee personas.

What every navigation system specification ships

A Navigation System specification carries a status stamp in its masthead (status: frozen <date> · N open items) and is accompanied by a functional reference demonstration:

  • 1 · The specification. specs/navigation/<System>.spec.html — sections §01–§14 in order, documenting the complete wayfinding and routing contract, with status stamp, geometry tables, ARIA landmark mappings, and keyboard tables.
  • 2 · Live reference implementation. Interactive working demo built with real system components, wired to simulated routing and plant-real data at realistic depth and volume (e.g. 4+ modules, nested sub-items, badge counts, plant selector).
  • 3 · Do/Don't visual pairs. Placed directly inside the sections whose rules they demonstrate (e.g. §06 States, §08 Accessibility, §10 Content rules, §12 Anti-patterns) with concise rationale.

The fourteen

All present, in ascending order, in every Navigation System specification
§01

Purpose

Always

Defines the wayfinding role of the navigation system, the information architecture tier it addresses, the user orientation problem it solves, and the explicit boundary against adjacent navigation structures.

Must answer

Which IA level it serves (L1 Global Suite Shell, L2 Module/Domain Nav, L3 In-Page/Tab Nav, Contextual Jump/Switcher, or Ancestor Trail); when to choose this navigation system; when to use an alternative; and the routing relationship (URL-driven vs local view-state driven).

Shape

Prose, an IA Tier Classification badge, a routing model statement, and a comparison table: “You need to… / Use this system / Instead of… / Why”.

Do

"Use L1 App Shell Navigation for primary domain switching across plant modules (Planning, Quality, Maintenance, Stores)."

Don't

"Use L1 App Shell Navigation to switch between sub-tabs of a single inspection record." In-page workspace switching belongs to L3 In-Page Tabs.

§02

Anatomy

Always

Defines every structural zone, slot, item element, and boundary container that makes up the navigation system, including required and optional regions.

Must answer

All regions: Shell/Container, Brand/Product Header, Plant/Environment Switcher, Primary Destination List, Group Headers, Collapsible Tree Nodes, Item Anatomy (Icon, Label, Trailing Badge/Counter, Chevron Expander, Shortcut Pill), Utility Footer (User Profile, Quick Actions, Help/Docs, Collapse Toggle), and Off-Canvas/Overlay Scaffolding.

Shape

Diagram or numbered structural callouts over a live instance, followed by a Structural Slot table detailing slot name, role, mandatory/optional status, and token assignments.

§03

Properties

Always

Defines the public configuration API, data contracts, item schema, router integration points, and event handlers exposed by the navigation system.

Must answer

Navigation tree item schema (id, label, href, icon, badge, children, permissions), active destination key/path, collapsed/expanded controlled state, router adapter injection (LinkComponent, onNavigate), filter/search flags, and custom footer/header render slots. Explicitly documents refused properties (e.g. arbitrary raw HTML injections, deeply nested ad-hoc styling overrides).

Shape

TypeScript prop interface, item data schema table, and dedicated refusal notes explaining why omitted properties are intentionally excluded.

§04

Variants

Always

Defines the standardized structural and behavioral modes the navigation system supports, and the specific use cases for each.

Must answer

Allowed structural variants: Expanded Vertical Sidebar, Icon-Rail / Mini-Nav, Horizontal Topbar Navigation, Tree-Accordion Navigation, Drill-Down / Push Navigation, or Floating Command / Quick-Switcher. Clarifies what constitutes a legitimate variant vs an invalid cosmetic customization.

Shape

Variant comparison table detailing layout characteristics, cognitive load, recommended destination count range, and live preview rows for each mode.

§05

Sizes

Always

Defines width, height, density dimensions, touch targets, and rhythmic spacing across all viewports and density modes.

Must answer

Expanded width (e.g. 240px / 280px), collapsed rail width (e.g. 56px / 64px), topbar height, item row heights per density (compact: 32px, comfortable: 40px, expanded: 48px), icon bounding boxes, indent depth per nesting level (e.g. 16px per level), touch target minimums (44px/48px), and maximum label truncation thresholds.

Shape

Geometry dimension table using semantic tokens (--control-h-*, --space-*, --radius-*), density matrix, and nested indentation visual guide.

§06

States

Always

Defines all system-level and item-level interaction states, visual token assignments, active route resolution rules, and contrast measurements.

Must answer

Item states: rest, hover, active / current (the active page), ancestor-active (parent of active child), focus-visible, expanded / collapsed, disabled / restricted (with tooltip rationale for lack of plant permission), badge alert / unread, and skeleton / loading during route transitions. Contrast ratios for text, icons, and active indicators against navigation surfaces (minimum 4.5:1 text, 3:1 graphical indicators).

Shape

State transition matrix, active path resolution hierarchy rules, and live rendering for all item states with contrast verification.

Do

"Show ancestor items with subtle highlight and expanded tree branch when a deep child route (e.g. /quality/nc/NC-4081) is active."

Don't

"Mark both the parent category and child item with identical primary active pills." That confuses exact location with category membership.

§07

Keyboard

Always

Defines keyboard navigation patterns, landmark jumping, roving tabindex, shortcut keys, and tree traversal mechanics.

Must answer

Landmark cycling (F6 / Alt+F6 between navigation and main content), single Tab-stop entry with Arrow navigation (↑/↓ across items, →/← to expand/collapse tree nodes or move between horizontal tabs), Enter / Space activation, Home / End bounds jumping, Esc to close flyouts/drawers, and global switcher shortcuts (Ctrl+K / Cmd+K).

Shape

Key-to-action table, focus management flowchart on route change, and focus trap rules for modal mobile navigation drawers.

§08

Accessibility

Always

Defines the accessibility contract: ARIA landmark roles, accessible labeling, state attributes, skip affordances, screen reader announcements, and WCAG compliance.

Must answer

Landmark structure (<nav aria-label="Primary Navigation">), unique labels when multiple nav landmarks exist, aria-current="page" on current destination link, aria-expanded and aria-controls on collapsible parent nodes, role="tree" vs nested <ul> semantics, skip navigation link (<a href="#main-content" class="skip-link">), and live region announcements on page/view transition (WCAG 1.3.1, 2.4.1, 2.4.7, 4.1.2, 4.1.3).

Shape

WCAG compliance table with rule references, DOM semantic markup example, and screen reader output transcription.

Do

"Use aria-current='page' on the active navigation link and distinct aria-labels on primary, secondary, and breadcrumb <nav> landmarks."

Don't

"Use generic unlabeled <nav> elements or indicate active destination using CSS class styling alone without aria-current."

§09

Motion

Always

Defines transitions and micro-interactions for expanding, collapsing, drawer transitions, flyout submenus, and active pill indicators.

Must answer

Sidebar width expand/collapse transition (180ms cubic-bezier(0.2,0,0,1)), off-canvas drawer slide-in/out (200ms), submenu accordion height disclosure, active pill glide/fade, hover indicator smoothing, and prefers-reduced-motion overrides (instant swap with opacity-only crossfade).

Shape

Motion specification table listing Property, Duration Token, Timing Function, and Reduced Motion fallback.

§10

Content rules

Always

Defines copy standards, label length constraints, grammatical casing, destination naming conventions, badge numeral formatting, and plant taxonomy.

Must answer

Destination vs action naming (destinations are nouns/places like Work Orders, Shop Floor Maintenance; never imperative verbs like Create Order), maximum word count (1–3 words, max 24 characters before truncation), title capitalization, numeric badge format (exact up to 99, 99+ above), tooltip requirements on collapsed icon rails, and plant domain naming consistency.

Shape

Do/Don't terminology table with real shop-floor examples from Suryodaya Autocomp Ltd (Chakan plant), plus string length constraint table.

§11

Responsive

Always

Defines how the navigation system adapts across Desktop, Tablet, and Mobile breakpoints, including drawer transformations and bottom navigation patterns.

Must answer

Desktop (≥1024px: persistent expanded sidebar or topbar), Tablet (768px–1023px: icon rail or off-canvas drawer with overlay), Mobile (<768px: off-canvas drawer modal or bottom navigation bar with 3–5 primary tabs), touch target scaling (minimum 44×44px / 48×48px), safe area insets (env(safe-area-inset-bottom)), and gesture support (swipe-to-close drawer).

Shape

Breakpoint adaptation matrix with viewport thresholds, structural transformation rules, and narrow-screen layout previews.

§12

Anti-patterns

Always

Identifies recurring navigation architecture mistakes that break wayfinding, trap keyboard focus, obscure critical destinations, or cause cognitive overload.

Must answer

Explicit anti-patterns: placing destructive or transactional action buttons inside primary navigation lists; nesting navigation trees deeper than 3 levels without a drill-down pattern; using active state styling for temporary hover/selections; hiding primary workflow modules behind undiscoverable menus; mixing external web links and internal app routes without visual distinction; omitting skip links.

Shape

Do / Don't two-column guidance with realistic manufacturing plant consequence callout (e.g. operator unable to locate NC escalation route during Line 2 press stoppage).

Do

"Keep action buttons (like 'New Work Order' or 'Release Requisition') in the page header or toolbar, reserving navigation strictly for destinations."

Don't

"Embed primary form submit or record creation action buttons inside the primary navigation sidebar list."

§13

Implementation notes

Always

Defines internal architecture, DOM hierarchy, routing synchronization, scroll persistence, z-index layering, and design tokens consumed.

Must answer

DOM landmark structure, scroll preservation in navigation sidebar across page loads, lazy loading of deep sub-tree branches, z-index token hierarchy (--z-index-nav: 100, --z-index-drawer: 200, --z-index-overlay: 190), performance considerations for large navigation trees, and complete inventory of color, typography, elevation, and spacing tokens consumed.

Shape

DOM architecture diagram/code block, z-index coordination chart, and categorized token consumption list.

§14

Developer notes

Always

Defines framework integration patterns, client-side routing adapters (React Router, Next.js, TanStack Router), role-based permission filtering, testing assertions, and specification freeze status.

Must answer

Code examples showing router link delegation and programmatic navigation; route match strategy (strict vs prefix); role/permission-based dynamic item filtering; automated accessibility and keyboard test recipes (testing aria-current, focus rings, F6 jumps, skip link); and open/closed governance item log with freeze date.

Shape

TypeScript integration example, test assertion snippets, and status/open-item registry table.
