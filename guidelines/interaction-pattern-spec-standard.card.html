Interaction Pattern specification standard

An Interaction Pattern is a standardized way of solving a recurring interaction problem using existing components. It is not a component: it has no public API, no rendered anatomy of its own, and nothing to install. Its specification documents the interaction contract the composition creates — sequencing, coordination, commit and cancel semantics, recovery — and nothing that its constituent components already own. This page fixes the sections such a specification may contain, their order and numbering, and the test for including or omitting each one.

How to apply it

  • One section is unconditional; twenty are conditional. Purpose appears in every accepted pattern specification. The rest appear only when their include test is met. Most patterns land between six and eleven sections; a pattern needing all twenty-one is almost certainly two patterns.
  • Numbers are stable identifiers, not positions. A section keeps its number from this list whether or not the sections before it are present, so a cross-reference such as §10 Error handling means the same thing in every pattern spec. Sections appear in ascending numeric order and are never renumbered.
  • Omit rather than stub. An omitted section is absent — no heading, no "n/a", no restatement of a component contract. The recurring test behind all twenty conditionals is one question: does the composition create this, or does it inherit it? If it inherits, omit the section and let the reader go to the component spec.
  • Pattern, not composite. If the answer is a fixed assembly of parts with a public API that should ship as one unit, it is a Composite Component and follows §01–§14 of that standard instead. Patterns describe how independent components are used together over time; composites describe a thing.
  • Behavior over layout. A pattern spec that could be satisfied by a screenshot is under-specified. Describe what happens, in what order, under what conditions, and what is guaranteed to the user when something goes wrong.
  • Borderline calls are logged, not silently resolved. If it is genuinely unclear whether a behavior is pattern-owned, include the section and say so in it. A named open question is a decision the system can make later; an omission is invisible.

What every pattern ships

A pattern is not accepted on prose alone. Four artifacts, all four required:

  • 1 · The specification. specs/patterns/<Pattern>.spec.html — the sections below, in order, with the omissions and their reasons stated at the foot. Its masthead links artifacts 2 and 3.
  • 2 · A reference implementation. templates/<pattern-slug>/<Pattern>.dc.html, named Pattern · <Label> — one working, interactive example built from this system's real components, set in a manufacturing ERP scenario — a work order release, a nonconformance disposition, a purchase requisition, a routing change — because a pattern demonstrated on a generic sign-up form is read as a form, while the same contract shown against shop-floor consequences is read as a rule. The plant is fixed for every pattern: Suryodaya Autocomp Ltd, Chakan plant (PL-04), Pune — rupees formatted en-IN, IST, @suryodaya.co.in, Indian names in plant roles and Indian suppliers, so a reader moving between patterns recognises the same works. Use plant-real nouns, quantities, and failure modes; never lorem-grade filler. Prose cannot demonstrate focus landing on the first problem, a commit refusing a second activation, or values surviving a failure; readers who cannot see the contract behave will reinvent it. Every pattern-owned state must be reachable in it, with tweaks to force the ones a happy path never reaches — pending, failure, partial outcome, unknown outcome. Expose the pattern's live state so the contract is inspectable rather than inferred. Consuming projects copy it as a starting point, so the demo apparatus must be separable: mark every explanatory note, state inspector and simulated-operation harness data-harness="remove-on-copy", give them a dashed border so they read as scaffolding rather than design, group their tweaks under a section named as a harness, and comment the simulated request with what to replace it with. A reference implementation that cannot be stripped in one pass is a demo pretending to be a starting point, and teams will ship the scaffolding.
  • 3 · A reference card. specs/patterns/<slug>-reference.card.html, @dsCard group="Specs · Patterns" — frames the live implementation beside its spec in the Design System tab, with links to the spec and to the standalone file. This exists because artifact 2 alone is not discoverable: cards inside templates/ are not compiled, and the template picker is a flat list. The card is where anyone browsing the system actually meets the pattern.
  • 4 · Do/don't visual pairs in the spec itself, placed inside the section whose rule they demonstrate — never collected into a gallery at the end, where they lose the rule they belong to. One pair per call that is routinely got wrong, each with a one-line statement of why beneath it. Two to five pairs is the working range: a pair for every rule is a spec nobody reads.

Freezing a pattern. A pattern spec carries a status stamp in its masthead — status: frozen <date> · N open items — the same convention component specs use. It may only read 0 open items when all four artifacts exist, every §05 property it declares is reachable as a tweak in the reference implementation, and every pattern-owned state is reachable there. A declared policy with no way to see it behave is an open item, not a footnote.

A pattern with a specification and no reference implementation is a proposal, not a standard. Do not add it to the patterns index until all four exist.

How grouping is actually implemented. Template names land in one flat "Templates" group and @template has no group attribute, so the picker cannot separate pattern references from page templates. Grouping therefore happens in the card grid (artifact 3), where @dsCard groups are arbitrary. Two mechanisms, each doing what it can: the card groups the pattern properly under Specs · Patterns; the template name carries a Pattern · prefix so the flat picker still reads correctly. Without the prefix a team browsing templates cannot tell a page starting point from a contract demonstration, and will copy one expecting the other.

Required

Present in every accepted pattern specification
§01

Purpose

Always

Defines the recurring interaction problem, the user goal it serves, when the pattern is appropriate, and — where the boundary is easily crossed — when it should not be used.

Include

Always. Every accepted pattern requires an explicit reason for existing and an explicit scope.

Omit

Never.

Conditional

Included only when the composition creates the contract
§02

Anatomy

Conditional

Defines the components the pattern uses, which are required and which optional, the role each plays, and the relationships among them.

Include

The pattern depends on a specific set of components in specific roles, or a relationship between them that a reader could otherwise get wrong.

Omit

The pattern is component-agnostic, or its structure is fully implied by Flow. Never restate structural detail already documented by the components themselves.

§03

Flow

Conditional

Defines sequencing: entry points, the interaction sequence, branching paths and decision logic, progression, completion, cancellation, interruption, and exit points.

Include

The interaction has meaningful order — a user can be part-way through it, and where they can go next depends on where they are.

Omit

The interaction is a single indivisible act with no intermediate state.

Note, from practice. Branching is described inside Flow, as a decision tree where complexity warrants it. Do not create a separate Decision Tree section — a tree divorced from its entry and exit points reads as a diagram of nothing.

§04

Behavior

Conditional

Defines the behavioral contracts the composition owns: component coordination, trigger and response relationships, dependencies, selection-to-action relationships, disclosure, commit, cancel, dismissal, persistence, and synchronization.

Include

One component's state or event changes another's behavior, or the pattern must guarantee what "confirmed", "dismissed", or "still there when I come back" mean.

Omit

Every behavior in play is owned by an individual component and nothing coordinates them.

Note, from practice. This is the section most often omitted by mistake, and the one most often padded. Behavior earns its place when it describes what the composition owns; it becomes noise the moment it re-documents what Select or Dialog already guarantees.

§05

Properties

Conditional

Defines configurable behavior exposed at the pattern level — the choices an adopting team makes when applying the pattern, not props on a component.

Include

The pattern has legitimate configuration whose options change its behavioral contract.

Omit

Configuration lives entirely on the constituent components. Do not duplicate their properties here.

§06

Variants

Conditional

Defines genuinely different behavioral forms of the same pattern.

Include

Two or more recurring forms solve the same interaction problem with materially different contracts, and both belong to this pattern rather than to separate patterns.

Omit

The differences are cosmetic, product-specific implementations, minor configuration, or just different examples.

§07

Sizes

Conditional

Defines sizing rules that exist at the interaction-pattern level.

Include

The pattern imposes coordinated sizing across components that no single component can determine — rare.

Omit

Default. Component sizing specifications are sufficient; this section is expected to be unnecessary for most patterns.

§08

States

Conditional

Defines pattern-level states: coordinated, dependent, persistent, and transient states, and the transitions between them.

Include

The composition creates a state no component holds alone — a pending selection, a dirty draft, a partially satisfied precondition — or a transition with rules of its own.

Omit

The section would be an aggregation of component states. A list of children's states is not a pattern state model.

§09

Validation

Conditional

Defines validation conditions and timing, cross-component and dependent validation, submission constraints, validation messaging, and recovery. Validation concerns the correctness and acceptance of user input.

Include

The pattern decides when input is checked, or whether one field's validity depends on another's value.

Omit

Each input validates independently under its component's own rules.

§10

Error handling

Conditional

Defines failure conditions beyond input validation: operation and network failure, partial failure, retry, recovery, preservation of user input, restoration of state, failed asynchronous operations, and unavailable dependencies.

Include

The interaction can fail for reasons outside the user's control, and the pattern must guarantee what survives the failure.

Omit

The interaction is local and synchronous with no failure mode.

§09 Validation

Is this input acceptable? Owned by rules known before submission.

§10 Error handling

The input was fine and the operation failed anyway. Keep the two distinct; never merge them.

§11

Input & interaction modalities

Conditional

Defines requirements across keyboard, pointer, touch, stylus, and gesture input — including hover alternatives, modality-specific behavior, touch-target behavior, and haptics where applicable.

Include

The composition introduces modality behavior no component owns: a hover-revealed step needing a touch equivalent, a gesture spanning several components, cross-component focus movement.

Omit

Modality behavior is entirely owned by the individual components.

§12

Accessibility

Conditional

Defines semantic and accessible-naming relationships, focus management, focus order and restoration, announcements, status communication, and assistive-technology behavior created by the composition.

Include

The composition creates a relationship or a focus responsibility that spans components — which is true of nearly every pattern that opens, closes, or replaces content.

Omit

Composition adds no accessibility contract. Document pattern-level accessibility only; do not repeat component-level specifications.

§13

Motion

Conditional

Defines coordinated motion: transitions, choreography and sequence, easing, duration, enter and exit behavior, interruption, continuity, and reduced-motion behavior.

Include

Motion carries meaning across components — a sequence, a spatial relationship, a continuity the user relies on to follow the interaction.

Omit

Motion is component-owned or decorative. Specify exact timings and easing values only where they are genuinely normative.

§14

Content rules

Conditional

Defines constraints on labels, instructions, action language, status and validation and error messaging, content hierarchy, terminology, and content limits — where correct interaction depends on them.

Include

The user cannot make the right decision unless the words follow a rule: an action label that must name its consequence, a message that must say what to do next.

Omit

Content is unconstrained. This section is not for general editorial guidance unrelated to the interaction.

§15

Responsive

Conditional

Defines how interaction behavior changes with available space, viewport, device characteristics, presentation context, or input environment.

Include

The interaction itself changes — a step becomes a screen, an inline affordance becomes a sheet, a simultaneous choice becomes a sequential one.

Omit

Only layout reflows. Ordinary reflow is not a responsive interaction contract.

§16

Internationalization

Conditional

Defines behavior materially affected by RTL and bidirectional interfaces, direction-sensitive interaction, locale-sensitive input and formatting, text expansion, and date, time, and number conventions.

Include

Direction or locale changes what the interaction means or how it is operated — directional progression, locale-parsed input, ordering that follows reading direction.

Omit

Nothing in the interaction is direction- or locale-sensitive. Document only the concerns relevant to this pattern.

§17

Performance

Conditional

Defines behavior where timing and latency matter: time-to-feedback, debounce and throttle, loading thresholds, optimistic updates, blocking behavior, perceived latency, delayed operations, and behavior under slow responses.

Include

The interaction waits on something, and how it waits is part of its correctness.

Omit

The interaction is instantaneous. Do not prescribe arbitrary timing values without a behavioral reason.

§18

Edge cases

Conditional

Defines behavior at boundary conditions: extreme data volumes and input, overflow and truncation, rapid repeated input, duplicate and concurrent actions, race conditions, interrupted interactions, stale or conflicting state, and boundary limits.

Include

A boundary is reachable in real use and the correct behavior is not obvious — double submits, a back-navigation mid-flow, zero results, a value that changed underneath the user.

Omit

No boundary materially affects the pattern. Do not manufacture hypothetical cases to fill the section.

§19

Anti-patterns

Conditional

Defines incorrect applications, inappropriate combinations, misuse of the pattern, and situations where another interaction model should be preferred.

Include

The misuse is recurring and consequential, and naming it prevents it.

Omit

Misuse is already clear from Purpose. This section must not restate Purpose in the negative.

§20

Implementation notes

Conditional

Defines what preserving the interaction requires: state architecture, event sequencing, component orchestration, synchronization, asynchronous coordination, and implementation constraints.

Include

A plausible implementation reading only the sections above would break the contract — state held at the wrong level, events fired in the wrong order, a race left open.

Omit

Correct implementation follows directly from Flow, Behavior, and the component contracts.

§21

Developer notes

Conditional

Defines additional technical and integration contracts: APIs, data requirements, event hooks, integration contracts, analytics and telemetry hooks, and technical constraints not covered elsewhere.

Include

Adopting teams need a technical contract beyond the interaction contract.

Omit

Nothing technical remains unsaid. Analytics and telemetry requirements live here, unless this system later owns analytics as an independent cross-product specification.
