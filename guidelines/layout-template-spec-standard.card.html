Layout Template specification standard

A Layout Template is a standardized arrangement of regions for a whole screen or a major area of one — a list-detail work queue, a record page, a plant dashboard, a focused task screen. It owns the frame: which regions exist, what each is for, how space is divided between them, which region scrolls, and how the arrangement restructures as space changes. It owns nothing that sits inside a region. Its specification documents layout-level responsibilities only; every contract a placed component already carries is read in that component's spec. This page fixes the sections a Layout Template specification may contain, their order and stable numbering, and the test for admitting or omitting each one.

How to apply it

  • Six sections are unconditional; eight are conditional. Purpose, Anatomy, Accessibility, Responsive, Anti-patterns and Implementation notes appear in every accepted Layout Template specification — a layout that cannot say what its regions are, how they behave in less space, what reading and focus order it creates, how it is got wrong, or what an implementation must preserve is not specified. The other eight appear only when the layout itself defines them.
  • Numbers are stable identifiers, not positions. A section keeps its number whether or not the sections before it are present, so §11 Responsive means the same thing in every layout spec. Sections appear in ascending numeric order and are never renumbered.
  • Omit rather than stub. An omitted section is absent — no heading, no "n/a", no restatement of a child contract. State the omissions and their reasons in one line at the foot of the spec, so a reader can tell a considered omission from an oversight.
  • The single test for every conditional: does the layout define this, or does its content? A layout is keyboard-accessible because a Table and a Button inside it are; that earns no Keyboard section. A layout that moves focus into the detail region when a row is selected defines keyboard behavior, and earns one.
  • Never repeat a specification a child owns entirely. No child states aggregated into a States section, no child props listed as Properties, no child size scale reprinted as Sizes, no child motion re-timed as Motion. If deleting the sentence loses nothing a reader could not get from the component spec, delete the sentence.
  • Frame, not content. A layout spec describes regions, space, order, scroll and restructuring. It does not describe what belongs in a region beyond that region's purpose, and it never prescribes a specific component where any component of the right role would do.
  • Layout, not pattern, not composite. If the answer is a contract about sequencing, commit, or recovery over time, it is an Interaction Pattern. If it is a fixed assembly with a public API that should ship as one installable unit, it is a Composite Component. Layouts are arrangements of regions that products fill.
  • Borderline calls are logged, not silently resolved. Where it is genuinely unclear whether a responsibility is layout-owned, include the section and say so in it. A named open question is a decision the system can take later; an omission is invisible.

What every layout template ships

A layout is not accepted on prose alone. Three artifacts, all three required:

  • 1 · The specification. specs/layouts/<Layout>.spec.html — the sections below, in ascending order, with omissions and their reasons stated at the foot, and a status stamp in the masthead (status: frozen <date> · N open items). It may only read 0 open items when all three artifacts exist and every §03 property and §04 variant it declares is reachable in the reference implementation.
  • 2 · A reference implementation. templates/<layout-slug>/<Layout>.dc.html, named Layout · <Label> — one working screen built from this system's real components, set in a manufacturing ERP scenario at the fixed plant: Suryodaya Autocomp Ltd, Chakan plant (PL-04), Pune — rupees formatted en-IN, IST, @suryodaya.co.in, Indian names in plant roles, Indian suppliers. Regions must be filled with plant-real content at realistic volume, never lorem-grade filler: a layout demonstrated with three short rows hides every overflow and truncation decision it is supposed to standardize. Every declared region configuration and responsive form must be reachable — expose the breakpoint form and any optional region as tweaks rather than asking the reader to resize a window and guess. Consuming projects copy it as a starting point, so the demo apparatus must be separable: mark explanatory notes and region outlines data-harness="remove-on-copy", give them a dashed border so they read as scaffolding, and group their tweaks under a section named as a harness.
  • 3 · A reference card. specs/layouts/<slug>-reference.card.html, @dsCard group="Specs · Layouts" — frames the live implementation beside its spec in the Design System tab, with links to the spec and to the standalone file. Cards inside templates/ are not compiled and the template picker is a flat list, so this card is where anyone browsing the system meets the layout. The Layout · name prefix does the same work inside that flat picker: without it, a team cannot tell a frame from a pattern demonstration and will copy one expecting the other.

Freezing a layout. frozen and 0 open items are two separate facts, and a dependency's open items are not the layout's. A layout may not read 0 open items while a component or pattern it names carries an open item that bears on the frame's own contract — a measure the frame promises but a child cannot hold, an overflow the frame delegates and the child leaves undecided. Open items that do not touch the frame stay where they are: they are named limits inside their own frozen spec, and a layout adopting that component neither inherits them nor closes them. Using something in a layout never freezes it, and never resolves its open items by decree.

Do/don't pairs live inside the section whose rule they demonstrate — never collected into a gallery at the end, where they lose the rule they belong to. Two to five per spec, each with a one-line statement of why beneath it. A pair for every rule is a spec nobody reads.

A layout with a specification and no reference implementation is a proposal, not a standard. Do not add it to the layouts index until all three exist.

Unconditional

Present in every accepted Layout Template specification
§01

Purpose

Always

Defines the kind of screen the layout serves, the work it supports, the information hierarchy it asserts, when it is the right frame, and — where the boundary is easily crossed — when a different layout should be chosen instead.

Include

Always. Every accepted layout requires an explicit reason to exist and an explicit scope, including a named neighbour it is confused with.

One fixed element. §01 closes with an applicable interaction patterns statement — Primary: the pattern the frame exists to host, or none, and Supported: the patterns it is known to carry, each linked. It belongs here because it is scope, not anatomy: it tells a reader whether their problem is the one this frame answers. A frame with no primary pattern says so explicitly rather than omitting the line.

Omit

Never.

§02

Anatomy

Always

Defines the regions the layout is made of: each region's name and purpose, whether it is required or optional, its ordering and nesting, the space and alignment rules between regions, which region owns scroll and which is fixed, and what may and may not be placed in each.

Include

Always. The region set is the layout; a layout without a documented anatomy cannot be adopted consistently.

Omit

Never.

Note, from practice. Name regions by role, not by position or by the component expected in them — record header, not top bar; primary work region, not the Table. Positional names go stale the moment §11 restructures the frame, and component names quietly promote one implementation into the standard.

Do

"The detail region owns its own scroll; the list region scrolls independently and its header stays pinned."

Don't

"The detail region contains a Table with sortable columns." Scroll ownership is layout-owned and nothing else can decide it; the Table's sorting is already specified in Table.

§08

Accessibility

Always

Defines the accessibility contract the frame creates: landmark roles and their region mapping, accessible names for repeated or ambiguous regions, document heading order across regions, DOM reading order against visual order, skip and bypass affordances, and where focus goes when a region is replaced, revealed or collapsed.

Include

Always. Landmarks, reading order and heading hierarchy are layout-owned by definition — no component inside a region can see the others to decide them.

Omit

Never.

Note, from practice. Do not restate what placed components guarantee. State the ordering, naming and focus-transfer rules that only the frame can guarantee, and state them for every responsive form in §11 — a reading order that is correct at desk width and wrong on a tablet is an unmet contract, not a detail.

§11

Responsive

Always

Defines behavior as available space changes: the breakpoints or container thresholds that matter, what each region does at each — reflow, collapse, stack, become an overlay, disappear — the priority order in which regions yield space, the reading order that results, and which behavior is normative versus permitted.

Include

Always. A layout is a claim about space; unspecified behavior in less space is the most common source of divergence between products adopting the same frame.

Omit

Never.

§05 Sizes

Standardized size classes the layout offers by choice — a comfortable and a compact frame the adopting team picks between.

§11 Responsive

What the frame does when space forces it. Never merge the two: one is a decision, the other a consequence.

§12

Anti-patterns

Always

Defines recurring misuses of the frame: regions repurposed for content they were not meant to hold, layouts nested inside themselves, competing scroll containers, primary actions stranded outside the region that owns them, a different layout being the correct answer.

Include

Always. Layouts are copied far more often than they are read, so every accepted layout names the misuses its own shape invites.

Omit

Never — but do not restate §01 in the negative. Each entry must name a misuse a reader could plausibly commit after reading §01 correctly.

§13

Implementation notes

Always

Defines what preserving the frame requires: the structural technique the contract depends on (grid or flow, named areas, container queries), minimum and maximum measures, overflow and min-size behavior, scroll containment and sticky ownership, stacking and overlay context, where the layout's own state lives, and the constraints a region imposes on whatever is placed in it.

Include

Always. Layout contracts are broken by implementation choices more than by misreading — a region that cannot shrink below its content, a nested scroll container, an overlay trapped in the wrong stacking context.

Omit

Never.

Conditional

Admitted only when the layout itself defines them — not its contents
§03

Properties

Conditional

Defines configuration exposed at the layout level — the choices an adopting team makes when applying the frame: which optional regions are present, split ratio and resizability, region pinning, density inheritance, scroll ownership where it is genuinely selectable.

Include

The layout has configuration whose options change the frame's own contract, and each option has a stated default and effect.

Omit

Configuration lives entirely on the components placed in regions. Never list child props here, and never invent knobs to populate the section.

§04

Variants

Conditional

Defines genuinely different structural forms of the same layout — a list-detail frame with the detail beside the list versus stacked beneath it as a standing choice, not as a breakpoint consequence.

Include

Two or more recurring forms serve the same purpose with materially different region structure, and both belong to this layout rather than to separate layouts.

Omit

The differences are the responsive forms of §11, cosmetic, or product-specific. If a form has a different purpose and a different anatomy, it is a different layout — split it.

§05

Sizes

Conditional

Defines standardized size or density classes at the frame level and the coordinated measures they imply — region widths, gutters, content measure, the padding scale regions inherit.

Include

The layout offers named size classes that a team selects between and that no single component could determine.

Omit

Default. Space comes from the spacing and density tokens and from §11; component size scales are already specified. Do not reprint a child size ladder, and do not describe responsive consequences here.

§06

States

Conditional

Defines states the frame itself holds: a region collapsed or expanded, a detail region empty because nothing is selected, a whole-frame loading or unavailable condition, a persisted split position.

Include

The frame holds a state no component inside it holds, and that state changes which regions exist or how space is divided.

Omit

The section would aggregate the states of placed components. A list of children's states is not a layout state model — and a region simply containing a component in its own empty or loading state is that component's business.

§07

Keyboard

Conditional

Defines keyboard behavior the frame introduces: tab order across regions where it must differ from DOM order, region-level bypass or jump affordances, shortcuts that move focus between regions, focus transfer when a region collapses or is replaced.

Include

The layout creates a keyboard relationship between regions, or takes responsibility for focus at a region boundary.

Omit

Default, and the most frequently mis-added section. That every component inside the frame is keyboard-operable is not a layout contract; do not add this section to say so.

Include

"Activating a row moves focus to the detail region's heading; collapsing the filter region returns focus to its toggle."

Omit

"Users can Tab through the filters and arrow through the table rows." Both are owned by Field and Table; repeating them creates a second source of truth that will drift.

§09

Motion

Conditional

Defines motion for structural change: a region collapsing or expanding, a panel entering as an overlay, a split resizing, continuity across a responsive restructure, and reduced-motion behavior for each.

Include

The frame's structure changes and the change needs to be legible — motion tells the user where a region went or where it came from.

Omit

Motion inside the frame is component-owned or decorative. Never re-time a child's transitions here; specify exact durations and easing only where the value is genuinely normative, otherwise name the motion token.

§10

Content rules

Conditional

Defines constraints the frame places on content across regions: what a region's title must identify, terminology shared between regions, ordering and grouping of content within a region, content measure and length limits, truncation and overflow policy where the frame decides it.

Include

The frame only reads correctly if content follows a rule — a detail region whose heading must name the selected record, a region title that must not repeat the page title.

Omit

Content is unconstrained by the frame. This section is not general editorial guidance, and not a place to specify the copy inside components.

§14

Developer notes

Conditional

Defines technical and integration contracts beyond the structural ones: region slot or composition API, routing and URL responsibilities where the frame owns them, persistence of layout state, data-loading boundaries per region, analytics and telemetry hooks.

Include

Adopting teams need a technical contract the sections above do not give them.

Omit

Nothing technical remains unsaid once §13 is written. Do not split §13 across both sections: structure and its preservation belong to §13, integration surfaces to §14.
