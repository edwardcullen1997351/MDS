Core Component specification standard

A Core Component is a single control with its own contract — Button, Input, Switch, Table, FileDropzone. Its specification is the whole contract, which is why it has no include tests: all fourteen sections appear in every one, in order, and a section with nothing to say is the strongest signal in this system that the component is not finished being thought about. This page fixes what each section must answer, so that any two core specs here can be read the same way — and so the next one is not written from whichever spec happened to be open.

How to apply it

  • All fourteen, always. Unlike the composite standard, there is no include/omit test: a Core Component owns its sizes, its states, its keyboard, its motion and its content rules by definition, because there is no child component to inherit them from. If a section feels empty, the answer is a decision — “two sizes, and no lg, because …” — not an omission.
  • Numbers are identifiers, not positions. §08 is Accessibility in every spec in this system, core or composite, and cross-references rely on it. Never renumber.
  • Say what the component refuses, and why. Every mature spec here spends real space on the props that do not exist: no loading on Switch, no url on FileItem, no lg, no tone. A refusal with a reason is the most durable thing a specification contains — it survives the next person who wants the prop.
  • Write the failure the component invites. §12 closes with the one misuse that actually happens and what it costs, in plant terms. Not a list of style slips: the mistake a competent person makes.
  • Record defects and their fix, with the version. §13 is where the system's history lives — what shipped wrong, what it measured, what it is now. Deleting that history is how a defect gets reintroduced two years later by someone who thought the old value looked cleaner.
  • Every number is real. Contrast ratios, pixel geometry, durations and token names are checked against the implementation, not estimated. A spec that disagrees with its component is worse than no spec.
  • Primitives are exempt. Box, Stack, Text and the rest are documented by their .d.ts and .prompt.md — see the primitives policy, which sets out what these fourteen sections would have said and why writing them would be theatre.

The masthead every core spec carries

Above §01: an eyebrow (Forms · Component specification), the component name as h1, a lede that states the component's single defining idea in prose — not a feature list — and a mono meta line with the source path, the window export path, the status (open, or frozen <date> plus the open-item count) and the version it appeared in.

status: frozen 4 Sep 2026 · 1 open items  ·  since: 1.0.0 · revised 1.2.0

The lede is load-bearing. “A setting that takes effect the moment it is flipped” decides most of Switch's fourteen sections on its own, and a spec whose lede is a summary of its own table of contents usually has no such sentence yet.

The fourteen

All present, in ascending order, in every Core Component specification
§01

Purpose

Always

What the component is for, in one idea, and the boundary against every neighbour that could be confused with it.

Must answer

Where it is used; what it must never be used for; and — as a table — “you want to… / use this / why”, one row per adjacent component. The Switch/Checkbox pair is the model: the routing table is what stops the wrong control being chosen.

Shape

Prose, a routing table, a short use / do-not-use list, and a live demo of the correct case beside the tempting wrong one.

§02

Anatomy

Always

Every region of the rendered control, named, with the reason it exists and the token that draws it.

Must answer

Numbered callouts over a live instance — one per region, each saying what it does and why it is drawn that way (“the off track is 1.60:1, so the border is what identifies the control”). Then a geometry table: region, value at md, token.

Shape

Demo, numbered callout list, geometry table. Hidden parts are anatomy too — the hidden input, the live region, the described-by node.

§03

Properties

Always

The full public prop surface, and the props that deliberately do not exist.

Must answer

Prop, type, default, and a note that carries the rule rather than the type again. Then, in prose, each significant refusal with its reason — this is the half of §03 that ages best.

Shape

Table including style and …rest; one paragraph per refused prop. Types must match the .d.ts exactly.

§04

Variants

Always

The distinct forms the component takes, or the explicit statement that it has none.

Must answer

If there is a variant prop: what each one means semantically, not how it looks. If there is not: say so, name the placements or shapes that get mistaken for variants, and say why they are not (a form without handlers is not a variant of a form with them).

Shape

Table plus a demo row per form. “No variant prop” is a complete and common answer.

§05

Sizes

Always

The size steps, what each is for, and how the component behaves under the three densities.

Must answer

Every step with its real geometry; which steps deliberately do not exist and why; and a density table — what compact, comfortable and expanded change, and what they pointedly do not. Sizes come from --control-h-*, never from literal pixels.

Shape

Size table, demo row per step, density table. A component with one size still answers this — “no size prop; the row is sized by density”.

§06

States

Always

Every visual state, with the tokens that paint it and the contrast it measures.

Must answer

Rest, hover, active, focus-visible, selected, disabled, invalid, read-only, loading — whichever exist — each with its measured ratio where legibility is in question. Two cues for any state that matters, and a greyscale check where colour alone could be doing the work.

Shape

State table, demo per state, and a warning callout for the state most often misused (a disabled control as a status light is the recurring one).

§07

Keyboard

Always

Every key the component responds to — and the keys it deliberately ignores.

Must answer

Key, behaviour, and the reason where it is not obvious. Tab order and whether the component is one stop or several; roving tabindex or not, with the reason; what Escape, Enter, Space and the arrows do or do not do. “Arrow keys: nothing” is an answer, and it needs its sentence.

Shape

Table, then a short list of the keyboard rules a consumer could break (intercepting Space, removing a focus ring).

§08

Accessibility

Always

The requirement, and how this component meets it — with the WCAG reference where one applies.

Must answer

Role and accessible name; the label/description split; boundary and state contrast (1.4.11); focus (2.4.7); target size (2.5.8); announcements (4.1.3); change of context (3.2.2) where the control can cause one. Any past failure is stated with the ratio it measured and the ratio it measures now.

Shape

Two-column table — requirement, how it is met — plus a right/wrong demo pair where the failure is visual.

§09

Motion

Always

What animates, for how long, on which property — and what must never animate.

Must answer

Change, duration token, easing, property. Only opacity, transform, colour and shadow are animated in this system; any exception (a determinate progress fill) is named as an exception and justified. Reduced-motion behaviour, and why no bespoke rule is needed if there is none.

Shape

Table with a “never” row, plus the reasoning for the one thing that does move.

§10

Content rules

Always

The words that go in each slot, in this product's voice.

Must answer

Slot, its job, what to write, what not to write — with real strings from the plant, not lorem. Length limits, tense, capitalisation, and the phrasings that are always wrong (“Enable …” on a switch label, “Error” as an error).

Shape

Write/Not table plus a rules list. Every example obeys the voice card and the plant setting in CLAUDE.md.

§11

Responsive

Always

What changes at each breakpoint, and what must not change.

Must answer

mobile / tablet / desktop / ultrawide, each with a behaviour — including the ultrawide answer, which is nearly always a measure cap rather than more width. Where reflow could reorder meaning, state that it may not.

Shape

Breakpoint table plus a narrow demo. “As authored” is a legitimate row; a missing row is not.

§12

Anti-patterns

Always

The do/don't pair, and the one failure this component invites.

Must answer

Two panes of short imperatives, then a closing warning: the single most consequential misuse, what it looks like on screen, and what it costs the operator. Written as a scenario, in the plant, not as a rule.

Shape

Do / Don't panes plus one warning paragraph. Six to eight items a side; a twenty-item list is a spec with no priorities.

§13

Implementation notes

Always

What actually ships, why it is built that way, and every defect closed so far.

Must answer

The DOM shape and the reason for it; the decisions invisible from the API (why the description sits outside the label, why transform not left); which core components it composes rather than hand-rolls; every console warning it emits; and each past defect with its version, its measurement and its fix. Closes with the full tokens consumed list.

Shape

List, then a mono token grid. New or retargeted tokens are called out with the version that changed them.

§14

Developer notes

Always

The integration contract, the tests, the lint rules, and the state of every open question.

Must answer

A real code sample showing the intended pattern (not a prop dump); the integration rule the sample exists to teach; Testing — the queries and assertions that hold the contract; Lint — what static analysis should flag; and then every open item, each marked Open or Closed as decided with the reason. Ends with the freeze line: the date and the closed API surface, or an explicit “not frozen”.

Shape

pre sample plus a list. A closed item states the decision and why, so it cannot be reopened as a fresh question; an item that merely disappears reads as an oversight.

Applies to: Core Component specifications (specs/core, forms, feedback, data, navigation) · Composite Components keep their own section set · Navigation Systems keep theirs · Interaction Patterns keep theirs · Primitives are exempt, per the primitives policy · Sections are numbered §01–§14 and never renumbered · Layout Templates keep theirs
