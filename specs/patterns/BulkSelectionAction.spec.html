Interaction pattern

Bulk selection and action

Selecting several items from a collection and running one operation over them — with selection held as identities, an aggregate whose scope is declared rather than assumed, a target snapshot taken when the operation begins, and an outcome that says exactly which items are done and which are not.

Written against: Interaction pattern spec standard §01–§21Required: Table or List, Checkbox, ButtonReference implementation: card · standaloneReference domain: manufacturing ERP — posting gate-inward goods receiptsSections included: 13 of 21status: frozen 7 Sep 2026 · 0 open items
§01

Purpose

Required

A stores clerk has eighteen counted goods receipts waiting and wants to post the fourteen that are clean. The items are chosen explicitly, the operation runs once over the chosen set, and each item can succeed or fail on its own. The pattern owns what sits between the ticks and the outcome: what selection is when the collection changes underneath it, what an aggregate checkbox covers, what the operation targets once it has begun, and what the user is left holding when half of it worked.

Use it when one operation should apply to several explicitly chosen items of a collection.

Appropriate

  • A work queue or register where items are dispatched in batches.
  • An operation whose per-item result can differ — posting, releasing, approving, exporting.
  • A set the user assembles across pages or refinements before acting.

Not this pattern

  • Rows arriving in a file. Import rows have no identity until they are created, were never chosen, and are addressed by line number — which this pattern rightly forbids. That is bulk data import, where partial acceptance is the expected answer rather than a broken promise.
  • Moving one item to a new position, or into another collection. That is direct manipulation of order: one identity, an origin index, and a rollback — not a snapshot of many with per-item outcomes.
  • An operation over everything. "Post all pending receipts" needs no selection; a checkbox column that is always fully ticked is scaffolding for a decision nobody makes.
  • One item at a time. A per-row action is a row action. Selection exists to make one operation cover many; a bulk bar over a single selection is a slower row action.
  • Narrowing what is shown. Ticking to filter is collection refinement — refinement changes membership, selection changes targets.
  • The confirmation itself. The dialog's own contract — what it says, how it is dismissed, what it guarantees — belongs to confirmed action; this pattern owns only whether one is required and what set it names.
§02

Anatomy

RoleComponentRequirement
CollectionTable or ListRequired. Provides the items and their stable identities. Its pagination and refinement define the scopes the aggregate may cover (§05).
Item selectionCheckbox, per itemRequired. Named after the record, not "select row" — the name is what a screen reader reads when the user arrives on it.
Aggregate selectionCheckbox in the header, tri-stateRequired wherever more than a page of items exists. Covers exactly the declared scope, reports the mixed state, and never claims more than it selected.
Scope extensionButtonRequired when the aggregate covers less than the whole set — the explicit second step that reaches the rest, stated in items ("Select all 18 pending lines").
ActionsButton, grouped in a Toolbar or ButtonGroup; Menu for the long tailRequired, at least one. Each names its scope and its count (§14). A Toolbar gives the set one accessible name and one tab stop, which is what keeps a growing action row usable.
ConfirmationDialogRequired per the declared confirmation policy (§05). It names the set, not just the action.
OutcomeAlert · Toast or Snackbar for a wholly successful, low-consequence resultRequired. A partial outcome must persist until the user resolves it, which rules out a timed notification for anything with unresolved items.
ProgressProgressRequired while the operation runs, with the count in the label. The collection is not replaced by a spinner.
§03

Flow

  1. Selection. The user ticks items, or the aggregate for its declared scope, or extends that scope explicitly. Each change updates the count and the availability of every action.
  2. Initiation. The user activates an action. The targets are snapshotted here (§04) and the action becomes single-shot until it resolves.
  3. Confirmation. Where required, a dialog names the operation and the snapshotted set. Cancelling changes nothing — not the selection, not the collection.
  4. Execution. The operation runs over the snapshot. Selection may not be edited into the running operation; the collection remains readable.
  5. Resolution. The result is per item: done, or unresolved with a reason. Membership is updated for the items that completed.
  6. Disposition. Selection is reconciled under the declared postActionSelection policy — unresolved items retained so retry has a target, or cleared — and the outcome is announced.
  7. Retry. Retry runs on the unresolved items only, as a new operation with its own snapshot.

Order matters in two places: the snapshot precedes the confirmation, so what the dialog names is what will run; and membership is updated before the outcome is announced, so the counts the user reads match the register in front of them.

§04

Behavior

  • Selection is a set of stable identities. Receipt numbers, not row indices — a sort, a page turn or a refinement re-assigns every position, and an index-based selection then points at whatever moved into that slot.
  • Selection outlives the page. Identities selected on one page stay selected when the user navigates; the count is of items, never of visible rows, and is stated against the collection total.
  • The aggregate covers a declared scope and says which. Visible page, current result set, or whole collection (§05). Anything beyond that scope is reached by an explicit second action, never by an aggregate that quietly means more than it shows.
  • The aggregate reports mixed state honestly. Some-but-not-all in scope is indeterminate; it is not unchecked, and it is not checked.
  • Membership changes reconcile the selection. An item that leaves the collection leaves the selection, and the removal is stated with the new count. A selection holding identities that no longer exist is the mechanism by which a bulk action acts on the wrong thing.
  • Action availability follows the current selection. With nothing selected, actions are unavailable under the declared policy and say why. Availability is derived from the selection, never a flag toggled by the selection handler.
  • The operation resolves against the snapshot taken at initiation. Selection edited after the button is pressed does not join the running operation, and items removed from the selection mid-flight are not spared from it.
  • An action is single-shot until it resolves. A second activation of the same action does nothing — not a second operation, not a queued one.
Do
MRR-2026-1841BRK-4820-B
MRR-2026-1842BRG-1120
selection = ["MRR-2026-1842","MRR-2026-1846"]2 of 18 lines selected — across 3 pages.

Identities, so sorting by gate time or paging to the next six changes nothing about what will be posted.

Don't
MRR-2026-1841BRK-4820-B
MRR-2026-1842BRG-1120
selection = [1, 5]2 rows selected on this page.

Row 1 after a re-sort is a different receipt. The clerk posts a ₹1,68,000 casting line they never ticked, and the count silently resets on every page turn.

§05

Properties

Four choices belong to the application of the pattern. The first is the one users get wrong most often when it is left implicit, because both plausible answers are defensible.

PropertyOptionsWhat it decides
aggregateScopepage · result-set · collectionWhat the header checkbox selects. page is the safe default and pairs with an explicit extension to the wider set; result-set suits a refined view the user has deliberately narrowed; collection is legitimate only where the whole collection is small and fully known — and where no refinement is in play, result-set and collection coincide, which is why the reference implementation offers the two distinguishable scopes. Whatever is chosen, the scope is named in words beside the count.
actionAvailabilitydisabled-with-reason · hiddenHow actions present with nothing selected. disabled-with-reason teaches the interaction — the user sees what selecting is for; hidden keeps a dense screen quiet but hides the affordance from a first-time user. Never a live action that fails on an empty set.
confirmationdestructive-only · always · thresholdWhen a confirmation step is required. threshold names a count above which any action confirms, for operations that are safe in tens and alarming in hundreds — the count itself is declared with it. The dialog's own contract is confirmed action's; what this property decides is whether it appears.
postActionSelectionkeep-unresolved · clear-allWhat the selection becomes after an operation resolves. keep-unresolved leaves retry a target and is right wherever partial failure is possible; clear-all suits an operation that cannot partially fail, where a surviving selection invites a second, pointless run.
§08

States

StateWhat is trueWhat is displayed
none selectedThe selection is empty. The baseline.The collection, the pending total, actions unavailable under the declared policy with the reason.
partially selectedSome items in the aggregate's scope are selected.Count of items against the collection total, aggregate indeterminate, actions available and counted.
all in scope selectedEvery selectable item in the declared scope is selected.The scope named in words, and — where the scope is narrower than the collection — the explicit extension to the rest.
action pendingAn operation is running over a frozen snapshot.Progress with the operation and the count; the collection still readable; the action single-shot.
partially failedResolved with some items done and some unresolved, each with a reason.A persistent outcome listing both sets, unresolved items still selected, retry scoped to them.
wholly failedResolved with nothing done.The failure and its cause, the selection intact, retry over the same set.
completedEvery snapshotted item resolved successfully.The outcome with the count, membership updated, selection disposed of under the declared policy.

Partially failed is a first-class state, not an error message. An operation over many items has a distribution of outcomes, not a boolean. Modelling the result as success-or-failure forces the two lies this pattern exists to prevent: reporting a partial run as a success, and offering a retry that repeats the work that already succeeded.

§10

Error handling

  • Partial failure names the unresolved items, individually, with a reason each, whenever the response distinguishes them. "Some items could not be posted" leaves the user to diff eighteen rows against their memory.
  • Completed work is stated too. The user needs to know what no longer needs doing as much as what does — and that is what makes the retry scope legible.
  • Retry targets the unresolved set only. Successful items have left the operation's world: they are out of the snapshot, out of the collection where the action removes them, and cannot be repeated by pressing retry.
  • Where per-item outcomes are unavailable, the whole operation reports as unresolved and says the outcome is unknown — never as success, and never as a specific count the response did not support.
  • The selection after a failure supports recovery. Under keep-unresolved the failed identities remain selected and the actions stay available on them; the user never has to re-tick their way back.
  • An outcome with unresolved items persists until acted on. A toast that expires takes the only record of what failed with it.
  • An item that vanished mid-operation is unresolved with that reason, not silently dropped from the count. "Posted by stores while this ran" is a different fact from "posted by you".
Do
4 of 6 lines posted · 2 unresolved
Posted: MRR-2026-1842, 1843, 1844, 1845. Still pending: MRR-2026-1841 — received 240 against a PO balance of 200. MRR-2026-1846 — PO-88209 under amendment, revision 3 pending approval.
Retry 2 unresolved

Both sets named, each failure attributed to a cause the clerk can act on, and a retry that cannot double-post the four that worked.

Don't
Some receipts could not be posted.
Retry all 6

No identities, no reasons, and a retry over the original six — which reposts four lines into inventory and puts the stock count out by 24,800 pieces.

§12

Accessibility

  • Every item checkbox is named after its record. "Receipt MRR-2026-1841", not "Select" — a column of eighteen identical names is unusable, and the row's other cells are not read on arrival at the control.
  • The aggregate control names its scope and reports mixed state through the platform. "Select all 6 lines on this page", with the indeterminate state on the control itself rather than a dash drawn on top of it.
  • The selection count is announced politely as it changes, once per change, including the scope in words. A count rendered only as a heading is invisible to anyone not looking at it.
  • Changes in available actions are perceivable without seeing them. Actions live in a named group, and their labels carry the count, so an action that becomes available is discoverable by reading rather than by noticing a colour change.
  • Focus is not moved by selection. Ticking an item leaves focus on that item's control so a keyboard user can tick the next; the outcome announcement does not steal it either.
  • Outcomes are announced by their severity. Completion politely; partial or whole failure as an alert, because the user's model of what has been done is now wrong.
  • Focus after a resolved operation lands somewhere accountable — the outcome message when there is unresolved work to read, otherwise the action that ran. Never the document, and never a row that has left the collection.
§14

Content rules

  • Action labels state their scope and count. "Post 6 lines", not "Post" — the label is the last thing the user reads before an irreversible operation over a set they assembled minutes ago.
  • The scope of an aggregate is written in words, not implied by where the checkbox sits: "all 6 on this page", "every line in the register".
  • The extension to a wider scope states the wider count. "Select all 18 pending lines" — a user who cannot see the total cannot judge what they are about to take on.
  • Confirmation names the consequence for the set, in the set's own units and value: how many, what happens to them, what cannot be undone. "Are you sure?" adds a click and no information.
  • Partial-failure wording separates completed from unresolved and never merges them into a single count. Both halves get their identities.
  • Counts are stated against the collection total, "6 of 18 lines selected", so a selection assembled across pages is never mistaken for the whole register.
Do
6 of 18 lines selected · all six on this page
Post 6 lines
Reject 6 lines
Select all 18 pending lines

Scope, count and consequence are all readable before the press, and the wider scope is an offer with its own number.

Don't
All selected
Post
Reject

"All" of what — the page, the register, or the filtered view? The clerk presses Post believing six, and eighteen lines and ₹10,15,000 of stock go to inventory.

§17

Performance

  • The single-shot guard is applied at the state transition, not by disabling the button — a disabled attribute arrives a frame late and a double press is faster than a frame.
  • An operation over a large set reports progress in items, not as an unmeasurable spinner: "posting 140 of 400 lines" is the only signal that tells the user whether to wait.
  • The rest of the page stays usable while the operation runs. The collection is readable and the user can page through it; only the actions and the selection are frozen, because both are inputs to the running operation.
  • Per-item results are applied as they arrive where the response streams them, so a long operation shows real progress; the outcome is still announced once, when the operation resolves.
  • An operation that outlives the view is not lost. Either it is bounded and the view waits for it, or it is a job with its own progress and its own record — a bulk action that silently continues after the user navigates away has no outcome contract at all.
§18

Edge cases

ConditionRequired behavior
Selected item disappearsRemoved from the selection, and the removal stated with the new count. Never left in the set to be sent as a target that no longer exists.
Collection changes after selectionSelection reconciles against membership on every read. Items that remain stay selected; the aggregate recomputes against the new scope, which may make a full selection partial.
Item disappears while the operation runsResolved as unresolved with that reason (§10). The snapshot is not edited mid-flight.
Aggregate scope narrower than the collectionThe count and the scope are stated together, and the wider set is offered explicitly with its own total. An aggregate never silently means more than it selected.
Repeated activationThe second activation is refused while the first is pending. No queue, no second operation, no double post.
Selection edited after initiationIgnored by the running operation. Newly selected items are not swept in, and de-selected items are not spared.
Confirmation cancelledNothing changes: not the selection, not the collection, not the availability of the action. The snapshot is discarded.
Every item in the collection acted onThe collection becomes genuinely empty and says so — "everything has been posted", not "no results". The selection is empty and the actions unavailable.
Selection spans a refinement changeIdentities outside the refined view remain selected, and the count says how many are not visible. Refinement changes what is shown, never what is selected.
Ineligible item selectedSelectable, and either refused by availability with the reason before the run, or resolved as unresolved with the reason after it. Never silently skipped inside a successful count.
§20

Implementation notes

  • Store selection as a set of identities above the collection component, so paging, sorting and refinement cannot touch it. The table renders the intersection of the selection with what it is showing; it does not own the selection.
  • Reconcile on read, not on event. Deriving the live selection as identities-still-in-membership means no event handler has to remember to prune it, and no path can leave a ghost identity behind.
  • Declare the aggregate scope as data, and compute both the aggregate's own state and the extension offer from it. A select-all implemented as "tick every visible checkbox" cannot express the wider scope at all.
  • Snapshot the targets into the operation object at initiation and let nothing else read the live selection afterwards. This is what makes confirmation, execution and outcome all describe the same set.
  • Guard the operation with the state transition itself — a pending operation object refuses a second start — rather than with the button's disabled state.
  • Require per-item results from the operation. The response says which identities succeeded; the outcome, the membership update and the retry scope are all derived from that one list. A boolean response makes §10 unimplementable.
  • Derive the retry set from the outcome, intersected with current membership, so retry after a further change still targets only what genuinely remains.
  • Update membership before announcing, so the announced counts and the collection agree at the moment the user reads them.
