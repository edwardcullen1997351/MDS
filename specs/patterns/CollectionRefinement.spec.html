Interaction pattern

Collection refinement

Narrowing a collection through several independently adjustable criteria, with one canonical refinement state behind the controls, the active-criteria display and the collection — so that what is selected, what is listed as applied, and what is on screen can never describe three different refinements.

§01

Purpose

Required

A maintenance head arrives at a backlog of 24 open work requests and needs the six that shift A can actually take on: two areas, breakdowns only, nothing waiting on a part. Each criterion is a separate control, the criteria compose, and the same refinement is represented in three places at once — in the controls, in whatever lists what is currently applied, and in the collection itself. The pattern owns that agreement: one state model, explicit composition rules, a defined unrefined state to clear back to, and reconciliation of anything the collection carried that a new refinement invalidates.

Use it when a user narrows a collection they already have, through reusable criteria they will adjust repeatedly.

Appropriate

  • A work queue, backlog or register triaged by several dimensions.
  • Criteria that persist across a session and are adjusted one at a time.
  • Refinement whose active criteria must be visible, and removable, away from the controls.

Not this pattern

  • Query and retrieval. A query the user composes as text, whose lifecycle — loading, none, failed, stale — is the contract, is search results. That pattern owns retrieval; this one owns coordinated criteria. A free-text criterion inside a refinement set is still this pattern.
  • Choosing values in a form. Controls whose values are submitted rather than reflected in a collection are validated submission: there is nothing to keep synchronized while the user works.
  • One control switching between prepared views. A saved-view selector replaces the collection wholesale; nothing composes.
  • Sorting. Ordering changes no membership and produces no empty result. It rides along, and is not a criterion.

What the pattern owns is the model beneath this list: one refinement object, read by the controls, by the active-criteria display, by the counts, and by whatever retrieves the collection.

§03

Flow

  1. Entry. The collection opens in the declared unrefined state, or under criteria restored from a session, a URL or a saved view — which are evaluated on arrival exactly as user-set criteria are.
  2. Change. The user adjusts one criterion. Under immediate refinement this settles and updates the collection; under explicit application it changes the pending refinement only, and the collection continues to describe what is applied.
  3. Application. Immediate: on the settled value. Explicit: on the apply action, for every pending change at once — never a partial application of some dimensions.
  4. Update. The collection is refined by the full criteria set under the composition rules of §04. Collection-dependent state is reconciled in the same pass.
  5. Statement. The settled result is announced politely, once, with the count and anything reconciled. Focus stays where the user put it.
  6. Removal. A criterion is removed from its own control or from its active-criteria entry; either writes the same model, and the other reflects it immediately.
  7. Clearing. Clearing returns controls, active criteria and collection to the same unrefined state defined in step 1 — not to the state the user arrived in, if that was refined, unless that is what the label says.

Order matters in one place: reconcile collection-dependent state before announcing. An announcement of the count that precedes the pagination reset states a range the user is not looking at.

§04

Behavior

  • Controls, active criteria and collection represent one refinement state. Each is a view of the same model. Three renderings of one object cannot disagree; three copies always eventually do.
  • Removing an active criterion updates its originating control. Removal is not a second mechanism that hides rows — it writes the model, and the chip, token or range the criterion came from returns to its unset value.
  • Removing an active criterion is an explicit act. Under explicit application it applies at once rather than becoming a pending change: the user acted on something labelled as applied, and expects the collection, not a queue.
  • Composition is stated as a rule, not implied by layout. Different dimensions must all hold; several values within one dimension mean any of them; ranges are inclusive. The rule is written where the criteria are, because the same controls could plausibly mean either.
  • Clearing returns to a defined unrefined state, identical for controls and collection, whatever route was taken to get there.
  • Refinement that invalidates collection-dependent state resets or reconciles it, and says so. A pagination position past the new end, a selection of rows that are no longer members, an expanded row that fell out: each is reconciled in the same pass and reported with the count.
  • Counts offered against options state what choosing them would leave — computed against the other dimensions, not against the whole collection and not against the refinement including that dimension itself. A count that ignores the current refinement is a promise the next click breaks.
  • Only the current refinement may write collection state. A slow update for criteria the user has already moved past is discarded (§17).

§05

Properties

Four choices belong to the application of the pattern. The first is the one that changes the state model, so it is declared once for a refinement set and never mixed within one.

PropertyOptionsWhat it decides
modeimmediate · explicitWhether a criterion change refines at once or waits for an apply action. immediate where the collection is cheap and the user refines by feel; explicit where an update is expensive, or where several criteria are normally set together and intermediate results are noise. One mode per refinement interaction: a set where some controls apply immediately and others wait has no legible state.
debounceA stated interval, in ms — immediate onlyHow long a continuous control must settle before the collection updates. Named, not emergent: a range slider or a text criterion otherwise issues an update per pixel or per keystroke (§17).
unavailableOptionsdisabled-with-count · hiddenHow a value that would leave nothing presents. disabled-with-count keeps the dimension's shape stable and shows the zero, which is itself information; hidden keeps the panel short where the option set is long and volatile. Never silently reordering, and never removing a value that is currently selected.
zeroResultRecoveryremove-last · clear-allThe way back offered when a valid combination matches nothing. remove-last names the narrowest criterion and undoes just that; clear-all is right where criteria are few and starting again is cheaper than reasoning about which one to drop.

Whether a dimension is single-value or multiple-value is not a property of the pattern: it is declared by the control supplied for that dimension, and the composition rule (§04) covers both.

§08

States

StateWhat is trueWhat is displayed

Unrefined and no-matches are opposite ends, not neighbours. Both show no criteria-specific content, and implementations routinely collapse them into "nothing to show" — which tells a user who has narrowed four times that the backlog is empty. Keep the criteria count in the state: zero active criteria and zero matches are different sentences.

§12

Accessibility

  • Each control declares what it constrains and what it affects. The dimension is the control's accessible name, and the controls sit in a region named for the collection they refine — a chip group called "Area" beside a table of work requests, not a bare row of place names.
  • Active criteria are not conveyed by styling alone. A selected chip reports its selected state through the platform; an active-criteria token carries its dimension and value in text and a real remove control, keyboard-reachable, named "Remove criterion Area: Press shop".
  • The collection announces politely and does not take focus. Focus stays on the control the user just operated, so refining several dimensions in sequence remains possible from the keyboard.
  • One statement per settled refinement, naming the count, the range shown and anything reconciled. Not one per keystroke of a range slider, and not one per dimension when several are applied together.
  • The collection region carries aria-busy while updating, and its skeletons stay aria-hidden.
  • An unavailable option explains itself outside the control. A disabled chip may never be read; its count and the reason belong in the group's description.
  • Removing the criterion a user is focused on moves focus predictably — to the next active-criteria entry, or to the clear action, never to the document.
§14

Content rules

  • A criterion label names the dimension being constrained, not the act of filtering: "Area", "Priority", "Estimated downtime" — never "Filter", "Options", or a bare list of values whose dimension the user has to infer.
  • An active criterion keeps enough context to be read alone. "Area: Press shop", not "Press shop"; "Downtime: 10–16 h", not "10–16". A token that has left its control must still say what it constrains, and must not be truncated past the point where it does.
  • Clearing states its scope. "Clear all 4 criteria" — a bare "Clear" beside a panel of controls could mean this dimension, this panel, or everything, and the cost of guessing wrong is the whole refinement.
  • The composition rule is written where the criteria are, in words: different criteria must all hold, several values within one count as any of them.
  • Counts state what they count. "3 of 24 requests" rather than "3 results", so the refined count is always read against the unrefined total.
  • No-matches copy says the combination is valid and the collection is not empty, names how many criteria are active, and offers the declared way back. It never invites creation as if nothing existed.

§17

Performance

  • Immediate refinement controls its own update frequency. Continuous criteria — a range slider dragged, a text criterion typed — settle on a stated interval (§05) rather than issuing an update per event.
  • Stale updates never override newer criterion state. Each update carries the refinement that requested it, and only the current one may write the collection. Debouncing reduces the overlap; the identity guard is what makes it correct.
  • Discrete criteria apply without delay. Debounce is for continuous input; delaying a chip toggle makes the control feel broken.
  • Update indication is delayed past the flicker threshold — roughly 300 ms — so a fast refinement does not strobe.
  • Controls stay live while the collection updates. Disabling the panel during an update turns every slow response into a lost adjustment, and blocks the user from correcting the criterion that caused it.
  • Option counts are computed with the collection, not per control. One pass over the current refinement yields every dimension's counts; a request per dimension multiplies the cost of every change.
§18

Edge cases

ConditionRequired behavior
Zero active criteriaThe unrefined state — stated as such, with no clear action and no active-criteria row. Not an empty result, and not a prompt.
Mutually restrictive criteriaThe refinement is applied and reports no matches, with the criteria count and the declared way back. Combinations are never silently prevented, and one criterion never quietly drops another.
Option becomes unavailablePresented under the declared unavailableOptions policy. A value that is currently selected is never hidden or disabled — the user must always be able to undo their own criterion.
Option disappears from the source dataA selected value that no longer exists stays visible as an active criterion, marked as no longer offered, so it can be removed. Dropping it silently changes the result set without the user acting.
Criterion removed while an update is pendingThe pending update ceases to be current at that moment. Its response is discarded, and the removal produces the next update.
Collection shrinks below the pagination positionReconciled to the last existing page — page 1 for a criteria change, the new last page for a re-fetch of the same criteria — and the reconciliation is announced with the count.
Selection outside the new collectionRows that are no longer members leave the selection, and the drop is stated with the count. A selection that survives invisibly is acted on by the next bulk action.
Rapid successive changesThe settled criteria decide. Intermediate refinements produce no announcement and no rendered collection.
Restored criteria that match nothingEvaluated on arrival, and presented as refined-with-no-matches — never as an empty collection. The recovery action is present before the user has touched anything.
Explicit mode, criteria changed then navigated awayPending changes are either applied or discarded explicitly; they are never carried invisibly into a later view where the controls and the collection would disagree on arrival.
§20

Implementation notes

  • One canonical refinement object. Controls, active-criteria display, option counts and collection retrieval all read it, and every change writes it. This single rule is most of the pattern.
  • No second copy of a criterion. No control-local state mirroring the model, no separate list of tokens built at add-time, no derived "filter string" that is edited independently. Every copy is a divergence waiting for the first unusual path.
  • Under explicit application, hold exactly two versions of the one model — pending and applied — and derive the pending count by comparing them. A per-dimension dirty flag drifts from the values it claims to describe.
  • Represent the unrefined state as a value, not as absence. Clearing assigns that value; comparison against it is what tells you a criterion is active, and what makes "clear all" and "arrive fresh" identical by construction.
  • Composition is one pure function of the model over the collection, evaluated in a defined order over dimensions. Rules scattered across the controls cannot be read as a whole or tested as a whole.
  • Option counts come from the model minus that dimension, which is why the count function takes the dimension to exclude. Excluding nothing produces counts that contradict the panel; excluding everything produces counts that ignore the refinement.
  • Every update carries the refinement identity and only the current one may write. Cancelling the request is an optimisation; the guard on write is the correctness measure.
  • Reconcile collection-dependent state in the same pass that applies the refinement, and derive the announcement from the reconciled result — so the statement matches what is on screen.
  • Serialise the model, not the controls, when refinement goes into a URL or a saved view. A restored refinement is then evaluated by the same function as a user-set one.
