Interaction pattern

Direct manipulation of order

Changing the sequence of a collection, or an item's membership of one, by moving the item itself — with the order held as committed state that only a successful commit may write, a refused move that returns the item to the index it came from, a keyboard route that is the same operation rather than a substitute for it, and a resulting position stated in the collection's own terms.

§01

Purpose

Required

The routing for BRK-4820-A runs blank, pierce, deburr, wash, bore, harden, inspect, pack. Sandeep Kulkarni wants deburr done before pierce, because the pierce tool is picking up burr from the blank and the bench is idle at 06:00 (IST). He is not editing a field: the thing he wants to change is which operation comes after which, and the fastest honest way to say that is to take op 30 and put it above op 20. The pattern owns everything between picking the operation up and the routing actually changing: what the collection shows while an item is in hand, which positions will accept it, where the item goes when MES refuses the sequence, and what a user who cannot use a pointer does instead.

Use it when the order of a collection, or an item's membership of one of two collections, is itself the data — and the user's mental model of the change is "this goes there".

Appropriate

  • Sequence that has meaning downstream — routing operations, inspection steps, a picking sequence, priority in a dispatch queue.
  • Membership between two named collections where the move is the decision: in-house against subcontract, this line against that line.
  • Small, surveyable collections where the user can see both the item and its destination at once.

Not this pattern

  • Changing values on the items. Adjusting an operation's cycle time in place is collection editing. Order is not a field, and a draft of a field is not a proposed position.
  • Sorting. A user re-sorting by work centre is asking for a different view of the same data; nothing is committed and nothing is theirs to keep. Sorting is owned by Table, and a collection that can be sorted and reordered must say which one it is currently showing (§18).
  • One operation applied to many chosen items. Subcontracting six operations at once from a selection is bulk selection and action — one snapshot, one operation, per-item outcomes.
  • Ranking by typed number. Where the collection is long, or the destination is off screen, a sequence field edited in place is kinder than a drag across a scrolling container, and it is collection editing.
  • Moving a file, a card between board columns, or a node in a tree, where the containers are the product's primary navigation. The move contract below still applies; the surrounding structure is not this system's to specify.

§03

Flow

  1. Read. The collection renders the committed order. Nothing is in hand, and each movable row carries a handle with an accessible name that includes the item.
  2. Grab. The user takes an item — pointer press on the handle, or Space/Enter on it. The pattern records the item's identity and its origin index, and enters grabbed state. The committed order has not changed.
  3. Propose. The user moves the item. A proposed index exists at all times while grabbed, is shown where it would land, and is checked against the declared legality rules — an illegal position is refused under dropLegality and the reason is available in text.
  4. Release or abandon. Release on a legal position requests the move. Escape, or a release outside the collection, abandons: the item returns to its origin index and nothing is requested.
  5. Move. Under commitTiming: optimistic the collection shows the new order at once, marked as not yet confirmed; under pending the item stays where it was and the proposed order is shown alongside. Either way the canonical order is untouched until the response.
  6. Resolution. On success the canonical order is replaced and the resulting position is announced. On failure the order returns under rollbackTarget, the failure is stated persistently, and the routing's actual sequence is named.

Steps 2 and 4 are a pair, and the origin index recorded in step 2 is what makes step 4 and the rollback in step 6 possible. A pattern that records only "an item is being dragged" can abandon a move but cannot put the item back where it was, which is why so many implementations drop a refused item at the end of the list.

§04

Behavior

  • Order and membership are committed state, not a rendering accident. The collection holds a sequence of identities. A move is a transformation of that sequence, requested once and applied once — not a mutation of a DOM node's position that state is later reconciled to.
  • A grab records identity and origin index. Both. Identity survives a refresh that reorders other items; the origin index is the only thing that can honestly answer "put it back".
  • A proposed index always exists while grabbed, and it is never the same thing as the committed index. Nothing downstream — a cost roll-up, a printed routing sheet, a capacity calculation — reads the proposed order.
  • Legality is declared, not discovered on release. Which positions accept the item is a rule over the item and the collection, evaluated for every candidate position while the item is in hand. A rule that can only be evaluated by the service is not legality; it is failure (§10).
  • An abandoned move has no side effects. Escape, a release outside the collection, a release on the origin index, and a release on a refused position all resolve to the same thing: the committed order, unrequested and unannounced as a change.
  • The commit is the only writer of order. Canonical order changes on a successful commit and at no other moment. An optimistic view is a claim about the future, labelled as such.
  • A move is single-shot until it resolves, guarded at the state transition. A second move of the same item while the first is in flight is refused, not queued: two sequence writes racing on one routing is how an operation ends up twice in the list.
  • A refused move returns the item to its origin index under rollbackTarget, and never to the end of the collection. "Back where it was" is the user's expectation and the only rollback that does not silently reorder something else.
  • A superseded response writes nothing. A response that arrives after a newer move of the same item, after a revert, or after the item left the collection is discarded with a recorded reason.
  • A transfer is one commit over two collections. Removal from the source and insertion into the destination succeed together or neither is applied (§06).

Properties

§06

Variants

Two forms, one contract for the grab, the legality check and the rollback — and a materially different commit.

VariantWhat changesWhat it must additionally guarantee
Reorder within one collectionThe sequence of identities changes; membership does not. One collection, one write.Every other item's position is a consequence of the move, and the announcement says so where it matters — moving op 30 up moves op 20 down, and a user who was told only about op 30 has half the change.
Transfer between two collectionsMembership changes, and both collections' contents change in one action. Order within the destination may also be part of the move.One commit for both sides under transferAtomicity: all-or-nothing; both counts restated after it; a rollback that restores both collections, including the item's index in the source. An item may never be rendered in both collections, and never in neither.

They are one pattern because the failure that makes both of them dangerous is the same failure — a move applied to the view and not to state, with no record of where the item came from. Where a product's transfer is between more than two collections, the contract is unchanged and the announcement must name the source and destination, since "moved" no longer identifies either.

§08

States

StateWhat is trueWhat is displayed

"Moving" and "moved" are not the same claim, and an optimistic collection must never make the second while doing the first. A routing that drops the unconfirmed marking the instant the row lands has told the line supervisor that deburr now precedes pierce; if MES then refuses the sequence, the correction arrives against a list that has already been read, and possibly already printed.

§10

Error handling

  • A failed move restores the order the user last saw committed, under rollbackTarget. The item goes back to its origin index — not to the end, not to the position the service happened to return, unless service-order was declared and the second change is stated.
  • The rollback is perceivable, not silent. A refused move that quietly snaps back looks like a gesture that failed to register, and the user repeats it. The failure is stated persistently, in an Alert that names the item and the sequence the collection now holds: "The routing still runs op 20 Pierce before op 30 Deburr."
  • Failure is not illegality. A position refused by a declared rule (§04) is a legality refusal, resolved without any request; a position the service rejects is a failure. The two never share a message, because only one of them is worth retrying.
  • Retry re-requests the move the user currently intends, which is the move as it stands at the moment of retry. Where the collection has changed underneath in the meantime, the retry is re-evaluated for legality first.
  • A transfer fails as one thing. Under all-or-nothing, either side failing rolls both back, and the message states both collections' contents. A message that reports the destination alone leaves the user unsure whether the operation is still costed in-house.
  • An unknown outcome claims neither. Where the request times out, the pattern says the sequence may or may not have been accepted, shows the last known committed order, and offers a re-read of the canonical order — never a blind retry, which on a sequence write can apply the same move twice.
  • An item withdrawn mid-move ends the move and keeps the explanation. The pattern says which item left, why, and what the attempted position was.
  • The collection never fails with the move. One refused move leaves the rest of the collection readable and movable.

§11

Input & interaction modalities

This is the section the pattern exists for. A drag is a compound gesture spanning several components, and no component in this system owns it — so the pattern must state what the gesture is, and what the same operation is for everyone who is not making it.

  • The keyboard route is the same operation, not an alternative feature. Grab on the handle (Space or Enter), move the proposed index (↑/↓, or ←/→ in a horizontal collection), drop (Space or Enter), abandon (Escape). It runs the same legality checks, produces the same commit, and returns to the same origin index. If the keyboard path is implemented as a separate "move up" that skips the legality check, the two paths will disagree, and the one nobody tested is the accessible one.
  • Grab mode is modal, and says so. While an item is grabbed by keyboard, the arrow keys move the item and not the focus, and the row states that it is in hand and how to get out. Silently swallowing arrow keys is how a user loses the list.
  • Every move is reachable without a drag, always. Explicit "move up" / "move down" / "move to position" controls stand beside the handle. They are not a degraded mode: a supervisor on a tablet with gloves on will use them by preference, and a destination twenty rows away is faster typed than dragged.
  • Touch: the grab is deliberate and the target is big. The handle is a full touch target at the system's minimum, and a drag starts from the handle rather than from the row, so a scroll gesture on the list is never mistaken for a move. Where a long press initiates a drag on the row, it has a stated duration and is accompanied by a state change the user can see before they move.
  • Hover is never load-bearing. Any affordance revealed on hover — the handle, the move controls — is also present on focus and permanently present on touch. A handle that appears on hover does not exist on a shop-floor tablet.
  • Auto-scroll during a pointer drag is bounded and interruptible, and the pattern requires an alternative to it: a destination the user must scroll to while holding an item is the case the explicit move controls exist for.
  • Pointer cancellation is honoured. A lost pointer capture, a released button outside the window, or a system interruption abandons the move — it does not commit whatever index was last proposed.

§12

Accessibility

  • The handle is a control with a name that includes the item. "Move op 30 Deburr" — not "Drag", and not an unlabelled glyph. A column of eight handles all called "Reorder" is unusable.
  • Grabbed state is announced, and so is the way out. On grab: "Op 30 Deburr grabbed, position 3 of 8. Use up and down arrows to move, Space to drop, Escape to cancel." The instruction is part of the announcement because the modal keys are not discoverable.
  • Each proposed position is announced as the user passes it, politely, naming the position and its neighbours under announcementScope, and naming a refusal with its reason where the position is illegal. A move made blind is a move made by guess.
  • The result is announced in the collection's own terms, once: position, total, and — under position-and-neighbours — what it now follows and precedes. "Moved" is not a result.
  • Focus stays with the item through the move and after it. The handle of the moved row keeps focus at its new position, so a user making several moves is not returned to the top of the list between them. On abandon, focus stays on the handle at the origin index.
  • A refusal or a failure is announced where the user is, and a failure is an alert, because the user's belief about the sequence is now wrong.
  • Position is stated in text, not carried by order alone. Each row states its sequence number, so a change of order is perceivable to a user reading one row at a time.
  • Reduced motion does not remove the information. Where a move animates, the announcement carries the whole result independently; where motion is reduced, the result is still stated in full.
§14

Content rules

  • Items are named by what they are, not by their index. "Op 30 Deburr · DB-01", never "row 3" — an index is the thing being changed and cannot also be the name.
  • A result states position out of total, and what it changed. "Op 30 Deburr is now 2 of 8 — after op 10 Blank, before op 20 Pierce." A bare "Order updated" tells a planner nothing they can check against the routing sheet.
  • A refusal names the rule and the blocking item. "Op 50 Bore is pinned to fixture FX-2210 and must follow op 20 Pierce" — not "Invalid position", which names neither the rule nor anything the user can move instead.
  • Failure copy states that the order did not change, in the collection's own sequence, before it explains the cause. "Not moved" first, mechanism second.
  • Undo is named as the reverse move, not as "Undo": "Put op 30 Deburr back to position 3". The user has made several moves and needs to know which one is coming back.
  • Transfer copy names both sides and both counts. "Op 60 Harden moved to Subcontract · Nashik Forge & Machine Works — 2 subcontracted, 6 in-house."
  • Instructions for the modal keys are stated where the mode begins, not in a help panel, and not only in a tooltip on a handle nobody has hovered.

§16

Internationalization

  • Direction is part of the operation in a horizontal collection. Under RTL, ← moves the item later in the sequence and → moves it earlier: the arrow keys follow the reading direction, because the user is moving the item through the list as they read it, not through screen space.
  • Sequence words and direction words are not interchangeable. The rule is stated in sequence terms — earlier, later, before op 20 — and where a control must be spatial, "move up" belongs to a vertical collection only. A horizontal collection whose control says "move left" is wrong in half the world's locales and ambiguous in the rest.
  • Insertion indicators mirror; the sequence does not. Position 1 is first in the reading order, which under RTL is the rightmost. The number stated in text is the source of truth for anyone the mirroring confuses.
  • Announcements state numbers, not directions, wherever both would do. "Now 2 of 8" is direction-free and survives translation; "moved up one" does not survive being read in a mirrored list.
  • Position numerals follow the locale, and the collection's own numbering — a routing's op numbers are identifiers, not positions, and are never localised or renumbered by a move (§18).
§17

Performance

  • The proposed index is local and immediate. Nothing about following the user's pointer or arrow key may wait on the network; legality is evaluated locally from declared rules (§04), which is why legality is declared.
  • The move is guarded at the state transition, not by disabling the handle: a second grab can be initiated before the disabled attribute lands, and two sequence writes on one routing can produce a duplicated operation.
  • Each move carries a request identity, and only the current one for that collection may write canonical order — a response arriving after a newer move, a revert, or a withdrawal writes nothing.
  • Optimism is a declared policy with an obligation attached. Under optimistic the unconfirmed marking is not optional and the rollback is not optional; without both, optimism is a lie told quickly.
  • A slow move is reported against the item, with progress naming it. A page-level spinner over a per-item move hides which operation is waiting, and blocks the collection the user was reading.
  • Several moves in succession are ordinary use. Where the service accepts one sequence write at a time, the pattern says so — the second grab is refused with the first named — rather than allowing an interleaving it cannot reconcile.
§18

Edge cases

ConditionRequired behavior
Dropped on its own origin indexNo move, no request, no announcement of a change. It is an abandon, not a zero-length move.

Another user reorders the collection underneathThe grab holds its identity, the origin index is re-derived from the new committed order, and the change is announced. Where the item's own position moved, the move is re-evaluated for legality before it commits.

§20

Implementation notes

  • Hold order as an array of identities, separate from the items. order: ['OP10','OP20',…] plus a map of items by id. A move is a pure transformation of that array; nothing reads a DOM index to find out what the sequence is.
  • Hold the grab as its own object: { id, originIndex, proposedIndex }. All three, from the moment of grab. An implementation that stores only draggingId cannot implement Escape, cannot implement rollback, and will reach for "move to end".
  • Never write the canonical order before the commit succeeds. Under optimistic, render from a derived sequence — committed order plus the in-flight move — rather than by mutating the committed one. Rollback is then discarding the in-flight move, not computing an inverse.
  • Write legality as one function over (item, candidate index, collection) and call it from the pointer path, the keyboard path and the pre-commit check. One function is what makes the three paths agree; three implementations is what makes the keyboard one wrong.
  • Derive the state, do not store it. At rest, grabbed, proposing, refused, moving, failed and moved are all computable from the grab object, the legality result and the in-flight request. A stored isDragging flag is what leaves a list grabbed after its item disappears.
  • Tag each move with a monotonic request number and check it — plus current membership — before writing anything.
  • Send the move, not the array. { id, fromIndex, toIndex, baseRevision } lets the service detect that the sequence moved underneath the user; posting the whole reordered array is a silent last-write-wins over anyone else's change. The service must therefore expose a sequence revision, and the response must be attributable to the request that asked for it.
  • Keep focus management with the transitions, not in the rows: grab focuses nothing new, a completed move keeps focus on the moved item's handle at its new index, an abandon keeps it at the origin. Rows that claim focus on mount fight the pattern and lose the user's place.
  • Implement the keyboard path first — or better, do not implement it: SortableCollection is this state machine, and its one canDrop is what keeps the two input paths in agreement. Where you must hand-build it, the keyboard path is the whole state machine with none of the pointer noise; built second, it becomes a bolted-on approximation of the pointer path.
  • For a transfer, hold both orders and commit once. The grab records the source collection as well as the origin index, and the rollback restores both arrays.

Closed as decided, 7 Sep 2026 — promoted. The pointer and keyboard mechanics this pattern leans on — the grab handle, the insertion indicator, the modal keyboard grab with its live position readout, bounded auto-scroll and the per-position legality check — are now SortableCollection. Both promotion tests were met: the grab is aggregate state no row can hold alone, and a hand-rebuilt one loses the keyboard route, which is a consequence rather than a cosmetic difference. The split is exactly the one this spec was written around — the composite owns the mechanics and no commit at all, so everything in §04, §05, §08, §10, §16, §17 and §20 about order as committed state, optimism, rollback and atomicity stays here, with the consumer. Transfer (§06) stays a pattern for the same reason: its commit spans two collections. The composite ships unfrozen — its API closes once a consumer outside this design system has used it, per the promotion policy.

Omitted sections and why. §07 Sizes — no coordinated sizing exists at the pattern level; the handle's touch-target minimum is a system-wide rule (§11) and the control sizes are the components' own. §09 Validation — a position is not judged for correctness. A rule known before the drop is drop legality, which is availability of a destination (§04, §05); a rule only the service knows is failure (§10). Merging them would offer a retry for a position that can never be legal. §13 Motion — an item may animate into its new position and a rollback may animate back, but no motion carries information the announcement does not, and none may delay it; the requirement that a rollback be perceivable rather than instant is stated as a failure rule in §10 and as an announcement rule in §12, where it can be met without motion at all. §15 Responsive — narrow viewports change which input is practical, not what the interaction is; that belongs to §11, which requires the explicit move controls unconditionally rather than as a small-screen fallback. §19 Anti-patterns — the refusals in §01, the separation rules in §04, the modality requirements in §11 and the failure rules in §10 cover the recurring misuses; a section restating them adds nothing. §21 Developer notes — the contract in §04, §05, §08, §10 and §20 is the whole contract; its two requirements of an API — a sequence revision, and a response attributable to the move that asked for it — are stated in §20.
