Interaction pattern

Bulk data import

A file that is not evidence for a record but the transaction itself. The columns must be mapped to fields before anything can be judged, the judgement must happen before anything is written, and the usual outcome is neither success nor failure but partial acceptance — some rows in, some handed back for correction.

§01

Purpose

Required

Deccan Machine Supply sends a catalogue extract: 500 rows of parts Suryodaya has agreed to buy, to be created in the PL-04 item master. Nobody typed them and nobody chose them — they arrived. Before a single row can be created, three things must be settled that no file can settle for itself: which of the supplier's columns is the part number and which is the unit of measure, whether a row naming a part that already exists is an update or a refusal, and what happens to the rows that break a rule. The answer that survives contact with a plant is: map the columns, judge every row without writing anything, show the verdict, and let the planner commit it knowing 412 will be created and 88 handed back.

Use it when a file is the transaction — its rows become records — and the correspondence between the file and the system has to be established and verified before anything is written.

Appropriate

  • An item-master, BOM, routing or supplier-price load from a file whose shape the system does not control.
  • Any import where rows can be individually rejected and the remainder is still worth committing.
  • A load where a row may collide with an existing record, and insert-versus-update is a real decision.
  • A recurring feed a planner runs monthly, where last month's mapping should not have to be rediscovered.

Not this pattern

  • Files that substantiate a record. A calibration certificate, an inspection photograph — the record is typed and the file proves it. That is evidence attachment, and its gate is the set's status, not a row verdict.
  • Selection, upload, progress and retry of the file. Owned entirely by FileUpload and FileItem. This pattern begins when the bytes have arrived and says nothing about how they got there.
  • One operation over records the user picked. That is bulk selection and action: its targets are stable identities already in a collection, chosen deliberately. Import rows have no identity until they are created, were never chosen, and are addressed by line number — which that pattern rightly forbids.
  • An import that failed because the service was down. The outage, the retry and what survives it are recoverable failure. Rows refused by rule are this pattern's normal output, not a failure at all.
  • A few records typed in a grid. If the user is entering the data, it is validated submission over a collection of fields.
§02

Anatomy

RoleComponentRequirement
The fileFileUploadRequired, exactly one, and the only thing this specification says about it: it owns selection, refusal, per-file progress, cancel and retry. This pattern begins at the point its entry reports complete. A set of several files is several imports.
The mappingSelect per target field, in a Table or a DescriptionListRequired whenever the file's column names are not guaranteed. One row per target field, never per source column: the fields are what the system needs, and a field with nothing mapped to it is the thing the user must see. An unmapped source column is stated, not hidden.
The verdictTableRequired. Rows with their line numbers, their disposition (create · update · reject) and, for a reject, the rule that refused it. This is what the commit acts on.
The countsText, beside the commitRequired. "412 to create · 0 to update · 88 rejected, of 500 rows" — stated before the commit, in the file's own units, so the commit's consequence is legible without reading the table.
The commitButtonRequired. Its label carries the number it will write — "Create 412 parts" — never "Import" or "Confirm". Single-shot; a second activation is refused by the state transition, not by the disabled attribute alone.
Progress of the writeProgressRequired where the write is long enough to notice, in rows: "creating 180 of 412". Never an unmeasured spinner over a 500-row load.
The outcomeAlertRequired, persistent. Names what was created, what was not, and where the rejects are. A toast is refused here: it takes the only record of 88 rejected rows with it when it expires.
The rejectsButton that downloads, or a TableRequired per rejectDelivery (§05). A reject list the user cannot take away is a list they must retype from the screen.

The mapping table is keyed by target field, not by source column. Listing the supplier's columns and asking "what is this?" reads naturally and fails the moment a required field has no column at all — the row that should exist is simply absent, and nothing tells the user. Keyed by field, an unmapped required field is a visible empty row that blocks the dry run.

§03

Flow

  1. Arrive. The file is selected or dropped and uploads. Nothing about the import exists yet; the mapping and the verdict are both absent, not empty.
  2. Read the shape. The header row and a sample are parsed. The file's columns become known, and under mappingSource: inferred-confirmable a proposed mapping is offered — proposed, and marked as such.
  3. Map. Every required target field is bound to a column, by the user or by confirming the proposal. Unmapped required fields are named; unmapped source columns are stated as ignored, so nothing is silently dropped.
  4. Dry run. Every row is judged against the mapping and the system's rules. Nothing is written. Each row resolves to create, update or reject-with-a-reason, and the counts follow from that.
  5. Read the verdict. The planner sees the counts, can read the rejected rows and their reasons, and decides. This is the pattern's centre: the decision is taken on a judgement of the whole file, not on a hope.
  6. Commit. The dry run's verdict is what commits — the same rows, the same dispositions. Under commitScope: accept-valid-rows the rejects are left behind; under all-or-nothing a single reject means the commit is not offered at all.
  7. Resolve. Created, partially created, failed, or unknown (§10). The rejects are delivered per rejectDelivery.
  8. Correct and re-import. The user fixes the reject file and starts again at step 1. The corrected file is a new import, not a resumption of this one — and under insert-only the rows already created must not be created twice.

The branch that matters is between steps 4 and 6: the mapping changing, or the underlying data changing, after a dry run. A verdict computed against a different mapping than the one now on screen is arithmetic about a file that no longer exists — resolved by previewStaleness (§05), and never by committing anyway.

§04

Behavior

ContractRule
Nothing is written before the commitThe dry run is a pure judgement: no records created, no sequences consumed, no partial state left if the user walks away. This is the pattern's central guarantee, and the reason a planner will run it on a file they do not trust.
The verdict is the transactionThe commit sends the dispositions the dry run produced, not a re-judgement at write time. What the counts promised is what is attempted. Where the service must re-validate, a row it now refuses is reported as a commit-time reject (§10) and never silently dropped from the total.
The mapping gates the dry runThe dry run is unavailable until every required field is bound, with the missing fields named beside the control. A judgement over an incomplete mapping would reject every row for the wrong reason.
The dry run gates the commitNo verdict, no commit — and a verdict that no longer matches the mapping is no verdict (previewStaleness).
Rejection is not failureA rejected row is a judgement about data. It uses validation's vocabulary, not failure's: it is reported per row with the rule that refused it, and it never colours the whole import as an error.
One import at a timeThe commit is guarded by the state transition itself. Two commits of one file create 824 parts, and the second one's duplicates are indistinguishable from the first one's successes.
The rejects survive the outcomeThe reject set remains available after the import resolves, until the user leaves or starts another. It is the only artifact from which the next attempt can be built.
Do
500 rows read · 412 to create · 88 rejected
Create 412 parts
88 rows will not be created. Download them, correct them, and import again.

The consequence is stated as a number before the press, so the planner commits to something specific.

Don't
brk-catalogue-sep.csv uploaded
Import
 

Nothing has been judged. The planner presses Import and finds out what happened to 500 parts afterwards, which is the failure this pattern exists to prevent.

§05

Properties

PropertyOptionsWhat it decides
existingRecordsinsert-only · upsert · refuse-fileWhat a row naming a record that already exists means. insert-only: rejected with that reason, and the existing record is untouched — the safe default for a master-data load. upsert: an update, which must be shown as its own disposition and its own count, because "412 imported" hiding 60 overwrites of live item-master data is the most expensive ambiguity in this pattern. refuse-file: a collision means the file is wrong and the whole import stops — correct where the file is supposed to be new parts only.
commitScopeaccept-valid-rows · all-or-nothingWhether a file with rejects can be committed in part. accept-valid-rows: the normal choice for master data, where 412 parts are useful today. all-or-nothing: required where the rows are interdependent — a BOM whose components are meaningless without their parent — and then the commit is not merely disabled but absent, with the reason stated.
mappingSourceinferred-confirmable · explicitWhether the system proposes a mapping. inferred-confirmable proposes from header names and requires confirmation — never silently applied, because a wrong inference is invisible and writes the supplier's list price into the standard cost field. explicit asks for every field, correct where columns are unnamed or untrustworthy.
previewStalenessrefuse · re-runWhat happens when the mapping changes after a dry run. refuse discards the verdict and requires a new dry run, stating why. re-run re-judges automatically, acceptable only where the dry run is cheap. Committing a stale verdict is not an option, and no third value offers it.
rejectDeliverydownload-file · on-screen-listHow rejected rows reach the person who must fix them. download-file returns the original rows with a reason column added, so the correction happens where the data lives. on-screen-list suits small files. Above about twenty rejects, on-screen alone is a transcription exercise.

All five are reachable as tweaks in the reference implementation, every §08 state is reachable there, and so are the §18 boundaries — the unmapped required field, the collision, the stale verdict, the duplicate line within the file, and the file whose every row is rejected. That is what lets this spec claim zero open items.

Partial acceptance is a success with a remainder, not a partial failure. This is the distinction from bulk selection and action, where the user chose every target and anything unresolved is a broken promise. Here the file was never trusted: 412 of 500 is the expected shape of the answer, the 88 are data to correct rather than work to retry, and the outcome is worded accordingly — success with the remainder named, not danger.

The verdict holds the mapping it was computed under, not a flag saying it is fresh. Staleness is then an inequality the interface can assert on every render, and no handler has to remember to invalidate anything.

§09

Validation

Three levels, deliberately separate. Merging any two of them produces a message the user cannot act on.

LevelJudged whenReported where
File levelOn parse, before any mapping.One Alert about the file: not a delimited file at all, no header row, zero data rows, a required field with no possible column. The row table is absent, because there is nothing to judge.
Mapping levelAs the mapping is edited.Beside the mapping control it concerns: a required field unbound, one column bound to two fields, a column whose sampled values cannot be the field's type ("UOM contains Nos, NOS, PCS — 3 values not in the unit-of-measure master"). Reported before the dry run, because a dry run over a wrong mapping rejects 500 rows for the wrong reason.
Row levelIn the dry run, per row.On the row, with the rule that refused it and the value that broke it. Never aggregated into a file-level message, and never counted without being individually readable.
  • A row's reason names the rule, the value and the line. "Line 87 — cost centre CC-4412 is closed for period 2026-09" is correctable; "Invalid row" sends a planner to a 500-row spreadsheet with no idea what to look for.
  • Every row is judged, not the first failure. Stopping at the first bad row means eleven more attempts to discover eleven more problems. The whole file is judged in one pass and every reason returned.
  • A row with several problems reports all of them. One correction pass should fix the row completely.
  • Type coercion is declared, not silent. If 1,250.00 is read as a rupee amount and Nos is mapped to the unit NOS, the interface says so at mapping level; a coercion the user cannot see is a data-quality incident waiting for a month-end.
  • Sampled validation is labelled as sampled. Where the mapping check reads only the first N rows, it says so — the guarantee is about those rows, and the dry run is what covers the file.
Do
line 87cost centre CC-4412 closed for 2026-09
line 91part BRK-4820-A already in the item master
line 92unit “EA” not in the UOM master

Each row carries the rule and the value, so the correction is mechanical.

Don't
88 rows are invalid. Please check your file and try again.

Eighty-eight problems and no way to find one of them. The planner's only route is to guess, re-import, and guess again.

§10

Error handling

A rejected row is not in this section — it is §09. What belongs here is everything that goes wrong for reasons the file did not cause, and this pattern's own obligation is narrow: say what was written, because unlike every other pattern here a partial write leaves records in the system that the user never individually chose.

FailureWhat is guaranteed
The dry run failsNothing was going to be written anyway, so nothing is lost: the file, the mapping and the counts-so-far survive, and the dry run is offered again. It must never fall back to committing unjudged.
The commit fails whollyNothing was written. The verdict remains valid and the commit is offered again over the same verdict — not a fresh dry run, unless previewStaleness says the underlying data may have moved.
The commit fails part-wayThe interface states the line the write reached and which rows were created, and offers a resume over the remainder only. A blind retry over the whole verdict re-creates everything before that line. Where the service cannot say how far it got, this becomes an unknown outcome.
Rows refused at commit timeReported as their own set, distinct from the dry run's rejects, because their existence means the dry run's judgement was overtaken — a part created by someone else in the intervening minute. They join the reject delivery with that reason.
The outcome is unknownNeither success nor failure is claimed, no count is asserted, and no retry is offered. The interface names where the truth is — "check the item master for parts created after 14:20 (IST) before importing again" — because a retry on an unknown outcome is a coin flip between 412 parts and 824.
The user leaves mid-commitThe write is server-side and continues; the interface must have said so before the press. A dry run abandoned mid-flight costs nothing, and the difference between the two is worth stating.
Do
The write stopped after line 180. 167 parts were created; 245 rows were not attempted.
MES did not answer.
Resume from line 181

The remainder is named and the resume is scoped to it, so nothing is created twice.

Don't
Import failed.
Retry

167 parts exist. Retry creates them again, and the item master now has duplicate part numbers nobody ordered.

§12

Accessibility

  • The counts are text, not only a chart or a colour band. "412 to create, 88 rejected, of 500 rows" is the verdict; a green bar with a red segment is decoration over it.
  • Each phase transition is announced politely and names its result — "500 rows read, 12 columns found", "Check complete: 412 to create, 88 rejected" — because the visible change is a table appearing somewhere below the fold.
  • The blocked commit carries its reason in adjacent text, never a tooltip and never silence: "Run the check first", "88 rows must be corrected before this file can be imported".
  • Each mapping control is a labelled field naming its target, and a mapping problem is associated with that control rather than reported in a list elsewhere.
  • A rejected row's reason is in the row, readable in reading order with the line number, not conveyed by row colour alone.
  • Progress is announced in rows at intervals, not per row — a 500-row write announcing each one is a live region nobody can use.
  • Focus after the dry run goes to the verdict, and after the commit to the outcome. Both are new information the user must read before the next decision; focus left on the button that ran means a screen-reader user is told nothing happened.
  • The reject download is a labelled control naming what it delivers — "Download 88 rejected rows (CSV)" — since its consequence is a file, not a view change.
§14

Content

  • The commit names its number and its object. "Create 412 parts", not "Import" — the count is the commitment, and a label without it invites the press before the verdict is read.
  • Counts are always stated against the file's total. "412 of 500 rows" rather than "412 rows", so a partial verdict can never be mistaken for the whole file.
  • Dispositions are named in the system's verbs, not the file's: create, update, reject. "Processed" and "handled" hide the one distinction that matters under upsert.
  • An update is called an update, and counted separately. Under upsert, "60 existing parts will be updated" appears beside "352 will be created" — never merged into a single figure.
  • Rejection wording is about the data, not the person. "Unit 'EA' is not in the unit-of-measure master" states a fact about line 92; "you entered an invalid unit" accuses a planner of a supplier's spreadsheet.
  • The outcome states what was created, what was not, and where the rejects are — three facts, in that order, in one persistent message.
  • Nothing is called a success while rows are outstanding. "412 parts created · 88 rows returned for correction" is the honest form; "Import complete" is read as "the file is in".
  • The mapping proposal is labelled as a proposal. "Matched by column name — check before running" makes an inference visible; a pre-filled select with no such line is read as fact.
Do
412 parts created in the item master.
88 rows were returned for correction.
Download 88 rejected rows (CSV)

Both halves are stated with their counts, and the remainder has a route.

Don't
Import complete ✓
500 rows processed

"Processed" covers 412 creations and 88 refusals equally, and the planner leaves believing the catalogue is loaded.

§17

Performance

  • The verdict table is paginated or windowed; the counts are not. Counts are over every row, always. Rendering 500 rows to state a number is a page that stalls before it informs — and the counts are what the decision needs.
  • Rejects are the default view of the verdict. They are what the user must act on; the accepted rows are confirmation. A verdict that opens on 412 successes buries the 88.
  • The dry run reports progress in rows if it is not instant, and stays cancellable. Cancelling costs nothing, which is a property worth having on a 50,000-row file.
  • Row-level results are applied as they arrive where the response streams them, so a long dry run shows real progress; the verdict is still announced once, complete.
  • Above roughly 5,000 rows, the dry run belongs to the server and the file is not held in the browser. The contract is unchanged — a verdict before a write — but the verdict becomes a resource with an identity, and the commit references it rather than resending the rows.
  • The reject file is generated from the verdict, not by re-parsing the upload. It must carry the original row exactly as supplied plus a reason column, so a corrected re-import is the same file with cells changed.
§18

Edge cases

ConditionRequired behavior
A required field has no candidate columnFile-level, not mapping-level: the file cannot be imported as it stands. Name the field and what it needs, and do not offer a mapping the user cannot complete.
A source column maps to nothingStated explicitly as ignored, with its name. Silence here is how a supplier's minimum-order-quantity column is dropped for six months without anyone noticing.
Two rows collide with each otherWithin-file duplicates are rejected as such, naming both lines — "line 91 duplicates line 40 (BRK-4820-A)". Distinct from a collision with an existing record, which is existingRecords, and the two reasons are never merged.
A row collides with an existing recordResolved by existingRecords, and always visible as its own disposition and count. An update must never be reported inside a creation figure.
The mapping changes after the dry runpreviewStaleness: the verdict is discarded and re-run, or discarded and the commit blocked with the reason. Never committed as-is.
The underlying data changes after the dry runThe verdict is a judgement at a moment. Rows the service now refuses are commit-time rejects (§10), reported as such and joined to the reject delivery — not silently subtracted from the count.
Every row is rejectedOne file-level statement of the dominant cause, with the rows still individually readable. Four hundred instances of "cost centre closed for 2026-09" is one problem, and stating it once is the difference between a fix and a scroll.
The file is enormous or has thousands of columnsRefused at file level with the limit stated in the file's own units, before any parse. A limit discovered by a frozen tab is not a limit.
The same file imported twiceNot blocked — a re-import after correction is the normal recovery route. Protection comes from existingRecords: under insert-only the already-created rows reject as collisions, which is the correct and legible outcome.
A second file arrives mid-importOne import at a time. The new file either replaces the whole import — with the current verdict explicitly discarded — or is refused until this one resolves. It never merges into the set.
The user leaves with a verdict uncommittedNothing was written and nothing needs cleaning up; the pattern may say so on the way out. This is the cheapest exit in the system and users should be told it is safe.
§19

Anti-patterns

  • Importing on upload. The bytes arriving is not a decision. An import that starts writing when a file is dropped has removed the only step that made it safe.
  • A verdict that is only a count. "88 rows will be rejected" with no way to see which is a number the user must act on and cannot.
  • Silent inference. A pre-filled mapping presented as fact, where a wrong guess writes the supplier's list price into standard cost across 412 parts.
  • Rejects rendered on screen only, at volume. Above about twenty rows this is a transcription exercise, and the corrected file gets rebuilt by hand.
  • Committing a stale verdict. Arithmetic about a mapping the user has since changed, presented as a promise.
  • "Import complete" over a partial acceptance. The single most damaging sentence in this pattern: the planner stops, and 88 parts are missing from the master until someone notices at a goods receipt.
  • Rejection styled as failure. A red page over 88 rows of ordinary data problems trains planners to distrust a working import — and hides the real failures when they come.
  • Blind retry after a partial write. Covered in §10 because it is the most expensive mistake available here: duplicate master data, created deliberately by the interface.
  • One progress bar for parse, judge and write. Three phases with different consequences — one of which writes — shown as one indeterminate spinner the user cannot interpret or safely interrupt.
§20

Implementation notes

  • Hold the verdict as an object carrying the mapping it was computed under — { mappingHash, rows, counts, at }. Staleness is then an inequality the render can assert, not a flag someone must remember to clear. This one decision closes the whole stale-commit class.
  • Key rows by line number, and say so. This is the one pattern where positional identity is correct, because the row has no other identity until it is created. Every message states the line, and the reject file preserves the original ordering so the numbers still mean something in the user's spreadsheet.
  • The mapping is a map from target field to source column, never the reverse. The direction of the data structure is the direction of the UI, and it is what makes an unmapped required field representable at all.
  • Derive the counts from the rows; never maintain them alongside. A count that can disagree with the table under it is the defect users report as "the import lied".
  • Judge in one pass and return every reason per row, as an array. A single error string per row forces a second import to discover the second problem.
  • The commit sends the verdict's identity or its dispositions, not the file again. Re-uploading at commit invites a different parse — and a different answer — than the one the user approved.
  • Guard the commit with the state transition, a phase field that refuses a second entry, not with the button's disabled attribute. A double-press across a slow render is otherwise 824 parts.
  • Keep three phase results separate in state — parse, verdict, commit outcome. One status enum spanning them cannot express "committed 167, then failed", which §10 requires.
  • Build the reject file from the retained original rows plus a reason column, and generate it client-side from the verdict where the file is in the browser. Asking the server to reconstruct rejects it never stored is how the reason column becomes "see log".
  • Make the dry run cancellable and side-effect-free in fact, not by convention. If the endpoint that judges also reserves numbers, it is not a dry run, and the pattern's central guarantee is gone.
