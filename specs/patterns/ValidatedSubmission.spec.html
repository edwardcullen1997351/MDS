Interaction pattern

Validated submission

Collecting several related values, deciding whether the combined input is acceptable, and committing it through one explicit action — with the user's entries surviving anything that goes wrong along the way.

Written against: Interaction pattern spec standard §01–§21Required: Fieldset, Field, Input, ButtonReference implementation: card · standaloneReference domain: manufacturing ERP — releasing a work order to a production lineSections included: 12 of 21status: frozen 7 Sep 2026 · 0 open items
§01

Purpose

Required

Several values entered by a user form one logical submission. Individually each may be acceptable; together they may not be. The pattern owns the coordination between input, validation, submission, and submission outcome — the decision of when input is judged, what "acceptable" means across fields rather than within one, and what is guaranteed to the user when the commit does not complete.

Use it when the values are committed together, an acceptance decision applies to the set, and the commit is an explicit act the user takes.

Appropriate

  • A form whose values are accepted or rejected as one unit.
  • Input with a constraint spanning two or more values.
  • A commit that can fail for reasons other than bad input.
  • Settings or details edited together and saved once.

Not this pattern

  • A single field. One input and its own validation is Field's contract. This pattern is not a place to re-document it.
  • Values that commit as they change. Continuous or per-control commit has no acceptance decision and no submission state.
  • A search or filter query. Nothing is committed; there is no acceptance rule and no failure to recover from.
  • A sequence across several screens. A stepped flow may contain this pattern at each step, but the progression between steps is not owned here.

The relationship the pattern owns: one Fieldset boundary, one value set, one commit, one outcome. A second commit button in the same boundary means either two submissions or an ambiguous one — both are refused. Nothing outside the boundary participates in its validation.

§03

Flow

  1. Entry. The user enters or modifies values. Nothing is committed and nothing is judged that the user has not yet reached.
  2. Validation. Rules are evaluated according to the timing defined in §09 — some per value as it settles, some only against the whole set.
  3. Commit. The user activates the commit action. All applicable rules are evaluated against one snapshot of the current values.
  4. Branch — unacceptable. Nothing is sent. Every value remains editable and every unresolved problem is exposed at its field, plus a submission-level statement that the commit did not proceed. The user is directed to the first actionable problem (§12).
  5. Branch — acceptable. The snapshot proceeds to commitment and the pattern enters submitting.
  6. Success. The operation completes the submission. What happens to the values — retained, cleared, or replaced by a resulting state — is declared, not incidental (§04).
  7. Failure. Recoverable values are preserved, the failure is reported as an operational failure and not as invalid input, and the user may correct or retry.
  8. Interruption. Before commit, abandonment loses nothing the pattern promised to keep. After commit, the outcome belongs to the operation; the interface must not claim a result it does not have.
§04

Behavior

  • Submission operates on one coherent snapshot. All rules and the commit itself see the same value set, captured at activation — never fields read independently as the operation proceeds.
  • Submission never silently discards a value. Anything the pattern will drop — an unused field, a value invalidated by another choice, a trimmed entry — is either visible to the user before commit or reported at it.
  • The commit is single-shot while pending. Repeated activation during submitting must not create a second operation. Enforced by the pattern's own state, not by the button's appearance.
  • Implicit submission is the commit action. Enter pressed in a single-line control within the boundary activates the one commit action and nothing else — same snapshot, same evaluation, same single-shot guard. It is never a second commit path with its own behavior, and it is never suppressed: removing it strands keyboard users. Controls that consume Enter for their own purpose — a multi-line Textarea, an open Combobox list — keep it, and the pattern makes no claim on those keypresses.
  • Field-level and submission-level failures stay distinguishable at every point: in placement, in wording, and in what the user is asked to do about them. One says "this value is wrong"; the other says "your values were fine and the operation did not complete".
  • Success declares the fate of the values. The pattern must state whether they remain visible for further editing, reset for a subsequent entry, or transition to a resulting state. An undeclared outcome produces the two worst readings: a form that looks unsaved, and a cleared form that looks lost.
  • Validation state is the pattern's, not the controls'. Individual controls report their own validity; whether the submission is acceptable is a conclusion the pattern draws over all of them.
  • Correcting a value clears its own problem, not others'. Resolving one error must never suppress the remaining errors or the submission-level report while problems remain.

§09

Validation

  • Every rule declares its scope. Independent rules concern one value alone; dependent rules concern a value in relation to others. Which is which must be explicit, because it determines when the rule can be evaluated at all.
  • Cross-field constraints are evaluated against one logical value set — the same snapshot for every rule. Evaluating a dependency against a value read at a different moment produces conclusions that were never simultaneously true.
  • Timing. Independent rules may report once the user has finished with the value and never while they are still producing it. Dependent rules report when both participating values exist. All applicable rules are evaluated at commit, without exception — commit-time evaluation is the authority.
  • A blocking condition prevents the commit. If a rule is not blocking, it is advisory and must not be presented as an error; a warning that stops nothing but looks like a failure teaches users to ignore real ones.
  • Correction re-evaluates. Changing a value must allow its condition — and every dependent condition it participates in — to be judged again and cleared. A condition that cannot be cleared by correcting the value it names is a defect.
  • Dependent failure names the relationship. When two values conflict, the message must identify which value the user is expected to change, and attach to that value's field. A constraint reported on neither participant is unactionable.
  • Nothing is judged before the user reaches it. Untouched values are not errors on arrival; they become problems at commit, where the user asked for a verdict.

§10

Error handling

  • Operational failure is not invalid input. A timeout, an unavailable service, or a conflict elsewhere must not mark fields invalid or borrow validation's wording and styling. The exception is narrow and explicit: where the operation reports that a specific value caused the rejection, that becomes a field-level problem on that value, and only that value.
  • Recoverable input remains available. After failure every value the user provided is still there and still editable. Values a system cannot retain — a one-time credential, a secret it must not hold — are the only permitted exception, and the failure message must say what has to be re-entered.
  • Retry uses the current intended values. Retry re-snapshots at the moment of retry, including corrections made since the failure. Silently replaying an obsolete snapshot commits something the user no longer intends.
  • Report in place. Failure keeps the user with their input, using Alert within the submission's boundary. A failure reported only in a transient surface can be missed, leaving a form that appears to have succeeded.
  • Partial commitment is reported as partial. Where the operation can commit some of the set, the user must be told what was committed and what remains, and retry must be scoped to the remainder.
  • An unresolved operation is not a failure. When the outcome is genuinely unknown, say so and say where the truth can be found. Never guess in either direction; a false failure invites a duplicate commit.

§12

Accessibility

  • Validation feedback is programmatically associated with its input through the owning Field, wherever the problem belongs to a value. A dependent problem attaches to the field the user must change.
  • Submission-level status is conveyed independently of visual styling — a role and a text statement, not colour, position, or an icon alone.
  • After a failed submission, focus goes to the first actionable problem in reading order, and every remaining problem stays reachable and announced in its field. Moving focus must never be the only way the problems are conveyed, and it must not make the others harder to find.
  • The submission-level statement carries the count and nature of the problems so that a user who does not tab through the whole group learns the scale of what needs fixing.
  • Asynchronous completion and failure are announced. Entering submitting is announced politely and once; failure assertively; success by the outcome report. Silence during an asynchronous commit is indistinguishable from a dead interface.
  • Suspension of the commit is perceivable as a state and not only as a visual change — a user who cannot see the spinner must still be able to tell the operation is in flight.
  • No time limit. Values are never discarded and the commit never becomes unavailable through inaction.
§14

Content rules

  • The commit label names the commitment — Release work order, Post disposition, Save changes. Never Submit, OK, or Continue: a user reading only the button must know what they are agreeing to.
  • Validation messages state the problem and, where possible, the correction. "Enter a date after the start date", not "Invalid date". A message that only reports rejection leaves the user guessing at the rule.
  • Operational errors are not worded as validation failures. No "invalid", no "please check your entries" for something the entries did not cause. Say what did not happen, and whether trying again is expected to help.
  • Dependent messages name both values and the direction of the fix, so the user is not left choosing which of two fields to change.
  • Terminology is stable across label, validation message, and outcome report: a value called “Order quantity” in the label is not “volume” in its error.
  • Requirements are stated before commit, not only after. A constraint a user could not have known — a format, a minimum, a dependency — belongs in the field's description; discovering it only through an error is the pattern failing at its purpose.
  • Success is stated in terms of what now exists, not "success".

§17

Performance

  • A commit that is not immediate must be perceivable as in flight. Feedback begins at activation, without a delay threshold — the gap between clicking and any acknowledgement is where duplicate submissions are created.
  • Suspension takes effect at activation. The window in which the commit still looks available after being pressed must not exist.
  • Repeated activation during a pending operation never produces a second commitment, whatever the input path — pointer, keyboard repeat, or assistive activation.
  • Validation must not block input. Evaluation that depends on a remote check runs without preventing the user from continuing, and must not leave the commit indefinitely unavailable while it settles.
  • An unresolved remote check at commit is resolved before the verdict, not ignored and not treated as a pass.
  • Determinate progress only when the progress is known. Otherwise indicate activity, not completion.

Edge cases

ConditionRequired behavior
Value changes at commitA change that lands between activation and snapshot is either in the snapshot or not committed. Never partially applied. Where a control commits its value on blur, activating the commit must settle that value first.
Repeated activationAdditional activations while submitting are discarded. One activation yields at most one operation.

Value invalidated by another valueThe dependent condition is re-evaluated and exposed on the field the user must change — including when the newly conflicting value was entered long before and is scrolled out of view.

Rule set changes mid-entryWhen a choice adds or removes fields, values already entered into now-inapplicable fields are excluded from the snapshot and their conditions cease to block. Nothing is silently discarded (§04).

§20

Implementation notes

  • Three separate stores: input state, validation state, operation state. Derive the pattern states of §08 from them; never store a conflated "error" that both a rule and a request can write. Almost every defect in this pattern traces to one of the three standing in for another.
  • Snapshot at activation and evaluate every rule and the request itself against that one object. Rules that read live field state cannot be reasoned about and cannot be tested.
  • Guard the transition, not the control. Single-shot commitment is a refused transition out of submitting — relying on a disabled button leaves a race the width of one render.
  • Keep the snapshot until the operation resolves, so that retry, partial failure, and the reporting of what was attempted all have something to refer to.
  • Retry re-snapshots. Never resend the stored snapshot; take a new one from current input so corrections are included.
  • Preserve enough to retry without re-entry, including values held in controls whose own state resets on remount. If the surface can unmount, the values do not live in the controls.
  • Validation is a pure function of the value set, returning problems keyed to the fields that own them. Evaluated identically on change and at commit; two code paths become two definitions of acceptable.
  • Sequence on failure: resolve → write operation state → announce → move focus. Moving focus before the problems exist in the accessibility tree drops the announcement.
