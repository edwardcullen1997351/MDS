Interaction pattern

Selection-driven detail

Choosing one item from a collection to inspect it — with selection held as an interaction state rather than a navigation, a detail region that always describes the item currently selected, and a documented rule for what the selection becomes when that item is no longer there.

§01

Purpose

Required

A tool-room clerk is looking for a die to hand to press PR-03. The crib list gives ten dies by number; the stroke count, the last inspection and the refurbishment spend that decide the choice live in MES. The clerk picks a die, reads it, picks another, compares, then issues one. Nothing has been navigated to: the crib is still there, the choice is still reversible, and the panel beside it is only ever a view of whichever die is current.

Use it when selection in one collection determines what a coordinated detail region shows, and the user's task is comparison or inspection rather than moving into a record.

Appropriate

  • Inspecting records in turn without leaving the collection — a crib, a queue, an alarm list.
  • A detail region whose content is retrieved separately from the collection's own rows.
  • Actions that belong to whichever item is current and are read in the context of the collection.

Not this pattern

  • Opening a record. If the user's intent is to go to the die's own page — deep-linkable, shareable, with its own history entry — that is navigation. Selection state is not a substitute for a route, and a route is not a substitute for this pattern.
  • Choosing several to act on. A checkbox column feeding one operation is bulk selection and action. This pattern has exactly one current selection and no aggregate.
  • Choosing a value. Picking one option to fill a field is a Select, Radio group or Combobox — the selection is the answer, not a lens on a record.
  • Narrowing the collection. Ticking to change what is listed is collection refinement; refinement changes membership, selection changes what is being read.
  • One record only. With nothing to choose between, there is no selection: render the record.
§02

Anatomy

RoleComponentRequirement
CollectionList or TableRequired. Supplies the items and their stable identities. It does not own the selection (§20).
Item selectionRadio group, one per item, sharing a nameRequired. One-of-N is what the platform already models; the radio carries the current selection into the accessibility tree, is named after the record, and gives arrow-key movement for free. Table onRowClick may make the whole row a pointer target beside it — never instead of it.
Detail regionCard, or a surfaceRequired. Names the selected item in its own heading, so the panel is legible without reference to which row is highlighted.
Detail contentDescriptionList · Heading, Text, Badge, Tag, Image, AvatarOptional. A record's fields belong in a DescriptionList; a table for one record is a definition list wearing a table.
Detail actionsButton, ButtonGroupOptional. Operate on the current selected identity and name it (§14).
LoadingSkeletonRequired where retrieval is asynchronous. Occupies the detail region, never the collection.
No selectionEmptyState variant="first-run"Required where no selection is a reachable state. It says what selecting will do, not that something is missing.
Failure and unavailabilityAlertRequired. Two distinct conditions with two distinct tones: the read failed (danger, retryable), or the selected item is gone (info, not the user's fault and not retryable).

The relationship the composition creates is one-directional: the collection writes the selection, the selection determines the detail. The detail region never writes the selection back — except through an action that removes the item, which is a membership change (§08).

§03

Flow

  1. Entry. Under the declared initialSelection policy (§05) the pattern opens with nothing selected, or with the first item selected and its detail retrieved.
  2. Selection. The user chooses an item. The identity is stored, retrieval starts, and — this is the whole point — the collection stays where it is.
  3. Retrieval. The detail region reports that it is loading, tagged with the selection that asked for it.
  4. Detail. The response for the current selection populates the region and is announced politely. Focus has not moved.
  5. Change. A new selection supersedes the old one: any read still in flight is abandoned, and its response, if it arrives, is discarded (§17).
  6. Action. An action in the detail region operates on the current identity. Where it removes the item from the collection, step 6 applies.
  7. Unavailability. The selected item leaves the collection. The removalPolicy either clears the selection and says which item left and why, or selects a documented replacement and retrieves it.
  8. Exit. Clearing the selection returns to step 1's no-selection state exactly. Under serialized presentation, returning from the detail view preserves the selection (§15).

There is no completion in this flow and no commit. That is what distinguishes it: the user may sit in step 4 indefinitely, move between items freely, and leave without having done anything.

§04

Behavior

  • At most one item is the current selection. One identity, or none. There is no multiple-selection state and no notion of a secondary or previous selection that anything else reads.
  • Selection is a stable identity, not a position. The die number, not the row index — sorting the crib by stroke count re-assigns every position, and an index-based selection then points at whatever moved into that slot.
  • Selection is interaction state, not navigation. No history entry, no route change, no scroll to the top; the collection remains visible, operable and in the same place. Where the selection is worth restoring across a reload, it is persisted as state — a URL parameter is legitimate for that, but the pattern still owes the user a collection they never left.
  • The detail region always corresponds to the current selection. Content shown for one item may never be presented as another's. This is the pattern's single load-bearing rule, and every rule in §17 exists to keep it true under latency.
  • Changing the selection supersedes the previous detail state. The previous item's content is either replaced or explicitly labelled as the previous item's under loadingTreatment (§05) — never left standing under a new selection with no label.
  • An unavailable selection resolves by a documented rule, not by accident. Either the selection is cleared and the disappearance stated, or a defined replacement is selected and retrieved. Silently emptying the panel, or leaving the last-read detail on screen, are both failures.
  • Detail actions operate on the current selected identity, read at activation and named in the label. An action must never send the identity the panel happened to load first.
  • Selection survives changes to the collection's order and shape. Sorting, refinement and paging move rows; as long as the identity is still a member, it is still selected. If it moves out of view, the selection stands and the detail region still describes it.

§05

Properties

Four choices belong to the application of the pattern. Each has two defensible answers, which is exactly why leaving them implicit produces two products that behave differently for no stated reason.

PropertyOptionsWhat it decides
initialSelectionnone · first-itemWhat is selected on arrival. none is the safe default: it costs an extra click and it never asserts that a record the user did not choose is the one they wanted, which matters when the detail region carries actions. first-item suits a monitoring view where an empty panel is dead space and no action is destructive. Never a remembered selection from another session unless the collection is guaranteed to still contain it — a restored selection is subject to §08's unavailable rule like any other.
removalPolicyclear · select-nearestWhat the selection becomes when the selected item leaves the collection. clear says what left and why and asks the user to choose again — correct wherever the detail region carries actions, because an automatically selected replacement puts a different record under a button the user was already reaching for. select-nearest keeps a monitoring view populated. Whichever is chosen, the rule is documented and the change is announced (§12).
loadingTreatmentskeleton · retain-previousWhat the detail region shows while a new selection's content is being retrieved. skeleton is honest and cheap. retain-previous reduces flicker when the user is moving quickly through items, and is only permissible with the retained content labelled as the previous item's — unlabelled retention is the §04 violation this property most often causes.
presentationsplit · serializedWhether the collection and detail are shown together or one at a time (§15). Declared rather than derived so that a product can serialize deliberately — a hand terminal on the shop floor — and not only when a breakpoint fires.
§08

States

StateWhat is trueWhat is displayed
no selectionNo identity is current. The baseline, and the state clear returns to.The collection with nothing marked, and a detail region that says what selecting will show. Not a blank panel.
selection activeAn identity is current; its content has not arrived.The item marked in the collection, the detail region naming it and reporting the read.
detail loadingA retrieval is in flight, tagged with the selection that started it.Skeleton at the shape of the content, or the previous item's content labelled as such. The collection stays fully operable.
detail availableContent for the current selection is present.The fields, the item's status, and any actions — all named after the current identity.
selection unavailableThe selected identity has left the collection.Under clear: which item left, why, and that nothing is selected. Under select-nearest: the replacement, selected and announced.
detail failureThe retrieval failed. The selection is intact and still valid.The cause, a retry for that identity, and an explicit statement that the item is still selected.

Unavailable and failed are not the same state and never share a message. "Could not load DIE-2230" for a die that was issued twenty seconds ago sends the clerk to retry a read that will never succeed; "DIE-2230 was issued to PR-08" for an MES timeout sends them looking for a die that is still sitting in bay C-09. One is a membership change with no retry; the other is a retrieval failure with nothing else wrong.

§10

Error handling

  • A failed retrieval leaves the selection intact. The item is still selected, still marked in the collection, and the failure says so — a failed read is not a reason to un-choose what the user chose.
  • The failure names the item and the cause. "MES did not answer the tool-life read for DIE-2230" tells the clerk it is the interface, not the die.
  • Retry is scoped to the current selection at the moment it is pressed, not to the selection that failed. If the user has moved on, there is nothing to retry there — the failure went with the selection that owned it.
  • A failure for a superseded selection is discarded, not displayed. An error belonging to an abandoned read is as stale as a success belonging to one (§17).
  • Partial content is labelled by field, not by panel. Where some of a record's fields are unavailable, the fields that arrived are shown and the missing ones say they are unavailable. Failing the whole panel because the refurbishment figure did not resolve withholds eight facts to report one.
  • Actions are unavailable while the detail is failed or unknown. An action derived from content that did not arrive is an action taken on an assumption; the detail region says which is missing.
  • The collection never fails with the detail. The collection and the detail are separate retrievals; a detail failure leaves the crib list readable and selectable, which is the only way the user can move off the failure.
§12

Accessibility

  • Selection is programmatically perceivable through a real control. A radio group named after the records — aria-checked on the item the user chose — not a background colour and not a class. A highlighted row is not a selection state to anyone who cannot see the highlight.
  • Each item's control is named after its record. "DIE-2223", not "select" — a column of ten identical names is unusable, and the rest of the row is not read on arrival at the control.
  • The relationship between collection and detail is stated. The collection is a named group ("Dies in the crib — choose the die to inspect"), and the detail region's heading names the selected item. Two named regions whose names refer to each other are what makes the coordination discoverable; proximity is not a relationship.
  • Selecting does not move focus. Focus stays on the control the user operated, so arrow keys continue through the collection and each item's detail is readable as it is reached. Moving focus into the panel on every selection makes comparing three dies a sequence of escapes.
  • Detail arrival is announced politely, once, naming the item. The detail region is a polite live region; the announcement is the fact the user asked for, not "loaded". Rapid selection changes must not queue an announcement per abandoned read.
  • Failure and unavailability are announced by their severity — an Alert that appears, because the user's model of what is on screen is now wrong.
  • Serialized presentation restores focus on return. Coming back from the detail view lands focus on the control for the item that was selected, not at the top of the collection (§15).

§14

Content rules

  • The detail region names its subject in its own heading. "DIE-2223 · tool life", never "Details" — the panel must be legible on its own, because a screenshot, a narrow layout or a screen reader all separate it from the marked row.
  • Actions name the identity they will act on. "Issue DIE-2223 to PR-03", not "Issue" — the label is the last thing read before a die leaves the crib.
  • The no-selection state says what selecting does, in the collection's own nouns: "Choose a die in the crib to read its stroke count, inspection history and refurbishment spend." Not "no data" and not "nothing selected" alone.
  • Unavailability states which item left and why. "DIE-2230 was issued to PR-08 from the tool-room terminal" — a bare "not found" leaves the clerk searching the crib for a die that is on a press.
  • Retained content says whose it is. "Still showing DIE-2223 — tool life for DIE-2230 is being read." Without the sentence, retention is a lie of omission.
  • Failure copy separates the read from the record. The die is fine; the interface did not answer. Wording that blames the record sends the user to fix the wrong thing.

§15

Responsive

  • Where the space cannot hold both, the presentation serializes. The collection and the detail become two views of one interaction, not two screens: what changes is how many are visible, never what selection means.
  • Return is guaranteed and preserves the selection. A back affordance returns to the collection with the selected item still current and still marked. A serialization that loses the selection on return has converted the pattern into navigation, which is the one thing §01 rules out.
  • Serialized detail is still not a route. Whether the platform's own back gesture also returns is a product decision; if it is wired, it must return to the collection with the selection intact, and never to whatever preceded the screen.
  • The rest of the contract is unchanged. One current selection, detail corresponding to it, the same loading, unavailable and failure states, the same announcements. Only simultaneity is lost.
  • Serialization is declared, not only derived. The presentation property (§05) lets a product serialize on a hand terminal at any width; a breakpoint is one input to that choice, not the whole of it.
§17

Performance

  • Every retrieval is associated with the selection that initiated it, and only the response belonging to the current selection may write detail state. This is the mechanism behind §04's correspondence rule; there is no other.
  • A response for a superseded selection is rejected outright — not rendered for a frame, not merged, not queued. The clerk who clicks through four dies while MES is slow must never end on the second die's figures.
  • Rapid selection changes cost the reads, not the correctness. Abandoning an in-flight read is normal; where the collection is large or the backend expensive, a short debounce on retrieval is legitimate, but the marked selection must change immediately regardless.
  • Selection feedback is never gated on retrieval. The item is marked as current the moment it is chosen; only the panel waits.
  • The collection stays operable during a read. Nothing in the collection is disabled while the detail loads — that is what lets a user escape a slow read by choosing something else.
  • Loading treatment is a policy, not a timing accident. A skeleton delayed by ~200 ms avoids a flash on a fast read; what is never acceptable is unlabelled previous content standing in the interval.
§18

Edge cases

ConditionRequired behavior
Selected item removedResolved by the declared removalPolicy and announced. Never a panel left showing a record that is no longer in the collection.
Collection reorderedThe selection holds on its identity and moves with it. Reordering never changes what is being read. Where the user is the one doing the reordering, that move is direct manipulation of order, and the selection is not part of it.
Selected item scrolls or pages out of viewStill selected, and the detail region still describes it. The count or heading may say the selected item is not currently visible; it is not deselected for being off screen.
Rapid selection changesThe last selection wins; all earlier reads are abandoned and their responses discarded (§17).
Detail response arrives after a newer selectionDiscarded. The state it would have written belongs to a selection that no longer exists.
Response arrives for an item that has since left the collectionDiscarded, and the unavailable state stands. A read that resolves after its subject was issued has nothing to describe.
Re-selecting the current itemNo-op. Not a second retrieval, not a cleared panel; under serialized presentation it re-opens the detail view.
Collection becomes emptyThe selection is cleared under the unavailable rule and the collection says why it is empty in its own terms — "every die has been issued or sent for grinding".
Selected item's own data changesThe detail region updates in place, still corresponding to the same identity. A change to the record is not a change of selection.
Restored selection no longer existsTreated as unavailable on arrival: the collection loads, nothing is selected, and the pattern says the remembered item is not in the collection.
§20

Implementation notes

  • Hold the selected identity above both regions — one field, one identity, nullable. The collection renders whether each item matches it; the collection does not own it, and the detail region does not copy it.
  • Store the identity, never the object or the index. A stored row object goes stale the moment the collection refreshes; a stored index goes stale the moment it re-sorts.
  • Tag each retrieval with a monotonic request number and its identity, and discard any response whose number is not current. Checking the identity alone is not enough — two reads of the same item can overlap — and checking the number alone loses the ability to reject a response whose subject has left the collection.
  • Keep the detail's subject in the detail state, not implied by the selection variable: { for: 'DIE-2223', data }. Correspondence then becomes an assertion the UI can make — and the reason the reference implementation can show selection and detailFor side by side.
  • Reconcile the selection against membership on read, deriving the effective selection as "the stored identity, if it is still a member". No event handler then has to remember to prune it after a refresh.
  • Resolve the replacement identity before removing the item, from the current order — select-nearest means the item that will occupy the neighbouring position, which cannot be computed after the array has changed.
  • Read the identity at activation inside the action, from the selection state, not from a value captured when the panel first rendered.
  • Do not put the selection in the browser's history. Selection state may be reflected in the URL for restoration, but pushing a history entry per selection turns a comparison into a stack of ten back presses.
