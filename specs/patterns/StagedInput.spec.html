Interaction pattern

Staged input

Breaking one larger input task into ordered stages — with a gate that judges only the stage being left, backward movement that commits nothing, one value model that survives every transition, and a single explicit completion at the end.

§01

Purpose

Required

Some input tasks are too large to answer in one pass, and their parts are not independent: a purchase requisition needs a charge and a date before a line item means anything, and needs the line value before it knows whether it needs an approver. The pattern owns the ordering itself — which stage is current, what it takes to leave it, what movement backwards means, what happens to values as the user passes through, and the one act at the end that commits the whole set.

Use it when stage boundaries change validation, progression, or the preservation of state — not when they merely group fields on screen.

Appropriate

  • A task whose later questions depend on earlier answers.
  • A task long enough that a single failed submission would waste real work.
  • Deliberate progression where the user should confirm one part before being asked the next.
  • A task where whether a whole group of questions applies is itself decided by an earlier answer.

Not this pattern

  • Sections for tidiness. Fields grouped under headings on one page, all validated together at one submit, is validated submission with layout.
  • One value governing another. A single dependent input inside a stage is conditional input; this pattern only owns dependencies that make a whole stage apply or not.
  • Navigation between independent screens. Tabs or routes over unrelated tasks have no gate, no shared value model, and no final commit.
  • A wizard over three fields. If the task fits on one screen, staging it adds ceremony and removes the user's overview.
§02

Anatomy

RoleComponentRequirement

The relationship the pattern owns: an ordered list of stages, exactly one of them current, a gate on each forward transition, and one value model that no transition may rebuild. Stages are presentation; the value model is the truth.

§03

Flow

  1. Entry. The user enters at the first applicable stage — or, where a draft is resumed, at the first stage that is not complete. Applicability of every stage is evaluated before the first render.
  2. Completion of the current stage. The user supplies whatever this stage asks. Nothing outside the current stage is judged.
  3. Forward attempt. The user asks to advance. The gate evaluates the current stage only.
  4. Gate. If the stage is blocking-invalid, movement is refused, the problems are shown against their fields, the stage says why it cannot be left, and focus moves to the first blocking value. The user stays where they are.
  5. Advance. Otherwise the next applicable stage becomes current — recomputed from current values, since a value just entered may have changed which stages apply.
  6. Backward movement. Where permitted, the user returns to an earlier stage without validation and without commitment. Values are unchanged by the movement itself.
  7. Final stage. Cross-stage rules — the ones no single stage could evaluate — are reported here, each attributed to the stage that can fix it.
  8. Completion. One explicit final action commits the whole staged set. It is single-shot: while it is in flight, a second activation does nothing.
  9. Failure. Completion may fail without any stage being wrong. Every stage survives; where the failure is attributable to input, the user is offered the stage that owns it.
  10. Cancellation. Exit obeys the declared preservation policy (§05), and the user is told which policy applied before it applies.

The order matters in one place: re-evaluate stage applicability, then choose the next stage. Advancing by index into a stale stage list is how users land on a stage that no longer applies.

§04

Behavior

  • Exactly one stage is current. Not zero — there is no between-stages state the user can be parked in — and not two, which is a page with headings pretending to be a flow.
  • Forward movement is gated by the current stage alone. A later stage's emptiness is not a reason to refuse the transition out of this one; the user has not been asked yet.
  • Backward movement implies no commitment and performs no validation. Going back is not an assertion that the stage being left is finished, so it must never be blocked by that stage's errors — the user may go back because the current stage cannot be completed as it stands.
  • Entered values survive every transition. Leaving a stage, returning to it, and passing over it again all leave its values exactly as the user typed them, including values a stage's own controls have unmounted.
  • Only an actual dependency invalidates a later value. Changing an earlier answer invalidates a later one when the later one was derived from or constrained by it — and nothing else. Wholesale clearing of everything downstream of an edit teaches users not to correct their mistakes.
  • Stage applicability is a rule over values. A stage that applies only above a threshold stops being a stage below it: it leaves the progression, its values leave the payload, and neither is discarded. Applicability is never derived from what has been rendered or from how far the user got.
  • Nothing commits before the final action. No stage transition writes to a system of record, and no stage transition is irreversible on the user's behalf. If a stage genuinely must commit as it is left, that is a sequence of separate submissions, not one staged input.
  • Completion is single-shot, guarded at the state transition rather than by a disabled button, and operates on the whole coherent value set as it stands at activation.

§05

Properties

Four choices belong to the application of the pattern rather than to any component. Each is declared once for the whole task and changes the behavioral contract, so none may be left implicit.

PropertyOptionsWhat it decides
backtrackingfree · one-stepWhether the user may jump directly to any earlier stage or only step back one at a time. free unless an earlier stage's values are genuinely expensive to re-derive. Neither option ever validates on the way back.
gatingblocking · advisoryWhether stage-local problems refuse forward movement or merely mark the stage and let the user proceed. advisory is legitimate only when the final stage reports every outstanding problem and routes back to it; without that, advisory gating is a flow with no gate at all.
preservationdraft · session · noneHow long entered values outlive the interaction — persisted for return, held for the session, or discarded on exit. This is what "come back to it later" means, and the user is told which applies (§14).
cancelPolicykeep-draft · discardWhat cancellation does to the value set. discard requires the label to say so before it happens; an unlabelled discard is data loss the user authorised without knowing.
§08

States

Two state models, kept separate: one per stage, and one for the task as a whole. A stage's state is not the aggregate of its fields' states, and the task's state is not the aggregate of its stages'.

not startedEntered nothing. Distinct from "on the first stage with values" — it is what a cancel policy of discard returns to.

completion pendingThe final action is in flight. No stage is editable, movement is suspended, and a second activation is refused.

Stage state and field state are separate stores. A stage is not "done" because its inputs were mounted, and a field does not become empty because its stage is not on screen. Collapsing the two produces the classic staged-input failure: a stage that reports complete while holding the values of a stage the user never reached.

§09

Validation

  • Every rule is classified before it is written: stage-local — decidable from the values of one stage — or cross-stage, needing values from two. The classification decides where the rule runs, when it may fire, and which stage it is reported on.
  • Stage-local rules gate that stage's forward transition. They fire on the attempt to leave, and on the field once the user has touched it; never on a field the user has not reached.
  • Cross-stage rules may not gate a stage that cannot see them. A lead-time rule needing the supplier cannot block the stage that holds the date, because at that point the supplier is unknown. They are evaluated at the final stage and reported there.
  • A cross-stage problem names the stage that can fix it and offers movement to it. A problem the user cannot navigate to is a dead end with a message attached.
  • Changing an earlier answer re-evaluates every rule that reads it — including rules on stages already marked complete. A stage's completeness is a conclusion, not a receipt; it is re-derived, never remembered.
  • Invalidation is surgical. When an earlier change makes a later value wrong, that value is marked and the user told what to check. Values with no dependency on the change are untouched, and a marked value is never silently cleared.
  • Leaving a stage validates nothing else. The final action revalidates the whole set — nothing is trusted because it passed a gate earlier.

§10

Error handling

  • Failure of the final operation destroys nothing. Every stage keeps every value, the stage the user was on stays current, and no stage reverts to not-started. The work of a long task must never be the price of one timeout.
  • Failure is attributed or it is not. Where the operation names input as the cause, the pattern resolves that to a stage and a field, marks it, and offers movement to that stage. Where it does not, the failure is reported at the final stage and no stage is marked — inventing a culprit sends the user to edit a value that was never wrong.
  • Operational failure is never worded as invalid input (§09 versus §10). "Purchasing did not answer" and "that part is not in the item master" are different events with different remedies, and the second is the only one that returns the user to a stage.
  • Retry re-reads the current value set, including anything corrected since the failure. A retry that replays the snapshot captured at the first attempt silently discards the fix the user just made.
  • An unknown outcome is stated as unknown. Where the operation may or may not have completed, the pattern says so, says how to check, and warns that a blind retry may duplicate — it never presents an unconfirmed outcome as either success or failure.
  • Interruption is not failure. Navigating away, a reload, or a dropped session is governed by the preservation policy (§05); a resumed task re-evaluates applicability and re-derives every stage's state rather than restoring stale stage flags.

§12

Accessibility

  • The current stage is programmatically identifiable, not merely styled. Position in the applicable sequence, the stage's name, and its state are available to assistive technology — a rail that carries movement marks its current item as such.
  • Focus moves once per stage change, predictably, to the new stage's heading or its first control. Never left on the button that was pressed — which is now labelled for a different transition — and never dropped to the document.
  • A refused forward movement moves focus to the first blocking value, because the refusal is the answer to the user's action and the field is where the answer must be acted on. The other problems stay reported; only focus is prioritised.
  • The change of stage is announced, once, politely, naming the stage and the position. The announcement says what is now being asked, not what the interface did.
  • Validation is associated with the stage and the fields needing attention — the gate message on the stage group, each problem on its own field. A stage-level message that lists field names instead of pointing at the fields leaves a screen-reader user counting.
  • Progress is meaningful or absent. A determinate indicator reports position in the applicable stage set; it may not animate as reassurance, may not report 100% before completion succeeds, and may never be the only statement of where the user is.
  • Completion pending is announced and bounded. The wait is stated, movement is visibly suspended, and the announcement does not claim the task is done.
§14

Content rules

  • Every stage heading names the task of that stage in the domain's words — "Sourcing & delivery", not "Step 3". The number is position; the heading is what the user is being asked.
  • Forward, backward, cancel and final actions are lexically distinct. "Continue to Sourcing" and "Release requisition" cannot be the same word: the user must be able to tell the transition that costs nothing from the one that commits.
  • The final action names the commitment, and says on the final stage that nothing has been sent yet. A "Submit" whose consequence is unstated is activated by users who thought they were still drafting.
  • Progress wording never implies completion before commitment succeeds. "Reviewing stage 4 of 4 — not yet released", not "Complete". A bar at 100% beside an uncommitted task is a false receipt.
  • Cancellation states its policy in its label — "Save draft and leave" or "Cancel and discard" — because the two are the same gesture with opposite outcomes.
  • A gate message says what to do, not that a rule exists. "This stage cannot be left yet. 2 values below need attention" beats "Invalid stage".
  • Where a stage applies conditionally, the condition is stated in the stage itself — "applies because the line comes to ₹2,50,000, at or over the ₹2,00,000 threshold" — so a user who sees a stage appear, or who never sees it, can account for it either way.

§18

Edge cases

ConditionRequired behavior
Earlier change invalidates a later valueOnly the dependent value is marked, with a statement of what to check. Independent later values are untouched, and nothing already entered is cleared to force a re-answer.
Earlier change makes a later stage inapplicableThe stage leaves the sequence and its values leave the payload without being discarded. If it was the current stage, the next applicable stage becomes current and the reason is announced.
Earlier change makes a new stage applicableThe stage enters the sequence at its defined position, the progression re-reports its length, and the user is told a stage now applies rather than discovering it at the end.
Jump to a completed stage, then forward againStage states are re-derived from current values on arrival. A stage passed earlier may now be invalid, and must present as invalid rather than as previously approved.
Final stage valid, operation failsTask state is completion failed, every stage keeps its values, and the user stays on the final stage unless the failure is attributed to an earlier one.
Double activation of the final actionThe second activation is refused at the state transition. One operation, one attempt in flight, regardless of how the control was activated.
Interruption and returnUnder draft or session preservation the value model is restored, applicability re-evaluated, stage states re-derived, and the user placed on the first incomplete stage. Restored stage flags are never trusted.
Deep link into a later stagePermitted only if every stage before it is complete under current values; otherwise the user lands on the first incomplete stage and is told why.
All applicable stages already complete on entryEntry is at the final stage. The task is still not complete: it has been reviewed, not committed.
Cross-stage rule broken by a backward editReported when the user next reaches the final stage, on the stage that can fix it — not raised as an error on the stage they are currently editing.
§20

Implementation notes

  • One value model for the whole task, held above every stage. Values keyed by field, never nested per stage and never held inside the stage's components — a value that lives where the inputs live is a value the next transition deletes.
  • Stage state is derived, not stored. Keep the current stage id, which stages have been gated, and which fields have been touched; derive applicability, validity and completeness from values on every render. Stored "stepComplete" flags are the source of stages that report complete after their values were edited away.
  • Applicability is one pure function of the value model, returning the applicable stage list in order. Movement resolves against that list — never against a fixed index into the full list, which is how a user lands on a stage that no longer applies.
  • Rules carry their classification and their owning stage as data: stage-local rules keyed by field, cross-stage rules each naming the stage that can fix them. Then the gate, the final-stage report and the failure attribution all read one table.
  • Transitions render, they do not reconstruct. If a stage's fields are unmounted between visits, they must remount from the value model; nothing may re-initialise from defaults on mount.
  • Guard completion at the state transition, not on the button. Enter pending or return; disabling the control is presentation and loses to a keyboard repeat or a double tap.
  • Sequence on a forward attempt: evaluate the current stage → refuse and focus the first problem, or re-evaluate applicability → choose the next applicable stage → render → announce → move focus. Announcing before applicability settles names a stage the user is not going to.
  • Keep the failure's field mark separate from validation state. An attributed operational failure marks a field that passed every rule; storing it as a validation error means the mark disappears the moment the field is re-derived as valid.
