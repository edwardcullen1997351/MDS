Interaction pattern

Conditional input

Asking for additional or alternative input only when another user-controlled value makes that input relevant — with the dependency stated as a rule, and the value, its applicability and its validity kept as three separate facts.

Written against: Interaction pattern spec standard §01–§21Required: Field, one controlling control, one dependent controlReference implementation: card · standaloneReference domain: manufacturing ERP — dispositioning a nonconforming lotSections included: 11 of 21status: frozen 7 Sep 2026 · 0 open items
§01

Purpose

Required

Some input only makes sense in light of another answer. A written justification is needed only when a lot is scrapped; a mobile number only if the supervisor is told by SMS; a hold window only once the lot is held at all. The pattern owns the dependency itself — when a dependent input applies, whether it is required, what happens to a value once it stops applying, and what the user is told and where their focus goes when the set of questions changes underneath them.

Use it when a value the user controls changes the relevance, availability, or acceptance rules of another input.

Appropriate

  • A disposition that requires supporting detail only when chosen.
  • A choice that swaps one input for a different one.
  • A limit or format on one value determined by another.
  • Several inputs governed together by one control.

Not this pattern

  • Disclosure for tidiness. Collapsing a section that always applies is progressive disclosure — no dependency exists, so nothing here is needed.
  • Availability the user does not control. A field disabled by role, plant, or licence state is not conditional input; the controlling value must be one the user can change.
  • Whether the set as a whole is acceptable. One acceptance decision over many values, and its commit, belong to validated submission; this pattern sits inside it.
  • A branch that changes the destination. An answer that routes the user to a different step is a stepped flow.
§02

Anatomy

RoleComponentRequirement
ControllerRadioGroup, Select, Switch, Checkbox, CheckboxGroup, SegmentedControl, Combobox, or any value-bearing controlRequired, at least one. Holds the value the dependency reads. A controller whose options carry a description states the consequence of choosing each one there (§14).
Input relationshipFieldRequired per dependent value. Carries the label, the condition in its hint, the requiredness mark, and the error association. Requiredness on a dependent Field is set by the rule, not fixed in the markup.
Dependent captureInput, Textarea, Select, Checkbox, CheckboxGroup, Radio, RadioGroup, Switch, Combobox, Autocomplete, MultiCombobox, DatePicker, TimeFieldRequired, at least one. A dependent may itself be a controller for a further dependency — that is a chain, not a new pattern.
Dependent groupFieldsetOptional. Where one controlling value governs several dependents, a named group makes the set one thing rather than several coincidences, and gives the condition one place to be stated.
Change statementLive region, or AlertRequired whenever the change is more than one field appearing next to the control that caused it. Says what now applies, what no longer does, and what happened to anything entered.

The relationship the pattern owns: a named condition over controlling values, a set of dependents that condition governs, and a declared policy for each dependent's value when the condition is false. A dependent with no stated condition, or a condition with no stated policy, is an incomplete application of the pattern.

§03

Flow

  1. Entry. Every dependency is evaluated against the current values before the user touches anything — including values restored from a draft, a URL, or a previous session. Conditional input has no privileged first render.
  2. Change. The user changes a controlling value.
  3. Re-evaluation. Every rule reading that value is re-evaluated, and every rule chained behind those, in dependency order and in one pass.
  4. Transition. Dependents that became applicable are presented; dependents that became inapplicable are withdrawn under the declared unavailability policy, their values handled under the declared retention policy, and their conditions cease to block.
  5. Statement. What changed is stated (§12) and focus is placed (§12) before the user's next action.
  6. Completion. The user completes whatever now applies. Applicable dependents participate in validation and in the submission exactly as unconditional fields do.
  7. Return. Restoring a previous controlling value re-evaluates the same rules against the current value set — never against the set as it stood when the condition last held.

The order matters in one place: re-evaluate the whole graph, then present, then announce, then move focus. Presenting before the graph settles produces a frame in which a chained dependent is applicable while its parent is not.

§04

Behavior

  • The dependency is a rule over values, not over what is on screen. Applicability is a function of the value set. Deriving it from visibility — asking whether a node is in the DOM to decide whether a value counts — makes presentation the source of truth and guarantees the two will disagree.
  • Rules are deterministic and acyclic. The same value set always yields the same applicability. A rule may not read a value its own dependent controls; a circular dependency has no correct resolution and is refused rather than resolved by evaluation order.
  • Every dependent declares a retention policy — preserve or clear — and it holds for the life of the interaction rather than being decided per event. Preserve keeps the value out of the submission while inapplicable; clear discards it as the condition ends. Undeclared is the failure case: the user cannot tell whether their typing still exists.
  • Nothing is discarded silently. Under a clear policy the user is told what was cleared, in the same statement that says what no longer applies.
  • Restoration is a re-evaluation, not a rewind. A preserved value returns only if it is still valid to return it; otherwise the field returns empty or returns marked, and never returns quietly wrong.
  • An inapplicable value never participates. It is excluded from the submission, cannot block completion, and cannot be the reason something else fails.
  • Unavailability has a declared form — removed from the flow, or present and disabled with the condition stated. Disabled is for a dependent whose existence the user should know about before it applies; removal is for one that would be noise. Either way, the condition is readable without operating the control.
  • The controller is never disabled by its own dependent. Whatever state a dependent is in — incomplete, invalid, mid-edit — the user can always change the value that governs it. Trapping the user inside a branch they can no longer leave is the pattern's worst failure.

§05

Properties

Three choices belong to the application of the pattern rather than to any component. Each is declared per dependent — or per group of dependents governed together — and each changes the behavioral contract, so none of them may be left implicit.

PropertyOptionsWhat it decides
unavailabilityhidden · disabledHow an inapplicable dependent presents. hidden removes it from the flow; disabled keeps it visible, not focusable, with its condition stated outside the control. Choose disabled where knowing the field exists changes the user's choice of controlling value.
retentionpreserve · clearWhat happens to an entered value when its condition ends. preserve for anything the user authored or would resent re-entering; clear where carrying the value back would be misleading or unsafe. Both are announced (§04).
requirednessrequired-when-applicable · optionalWhether becoming applicable also makes the dependent blocking. Requiredness is a property of the applicable state; it is never a static attribute on a field that comes and goes.
§08

States

Per dependent — not per form. Several dependents governed by one controller each hold their own state, and the group's state is nothing more than the set of them.

StateWhat is trueBlocks completion
inactiveThe condition is false. The dependent is unavailable under the declared policy, its value held or cleared under the declared policy, out of the submission.Never
active · incompleteThe condition is true and no value has been supplied yet.Only if required-when-applicable
active · invalidThe condition is true and the value fails a rule — including a rule the current controlling value introduced.Yes
active · completeThe condition is true and the value satisfies every applicable rule.No

Applicability, value, and validity are three states, not one. A dependent can hold a value while inactive, and can be active with a value that was valid under the previous condition. Collapsing them into a single "shown and required" flag is what produces forms that cannot be submitted because of a field nobody can see.

§09

Validation

  • Only applicable values are judged. A dependent whose condition is false is not incomplete, not invalid, and not a reason the submission cannot proceed — whatever it contains.
  • Requiredness follows applicability in both directions. Becoming applicable can make a field blocking; becoming inapplicable must release it in the same pass. A field left blocking-required behind a false condition is unresolvable by any action the user can take.
  • Changing a controlling value re-evaluates every rule it participates in — the dependents' own rules and any rule whose limits it sets. A value that was acceptable under the previous condition is re-judged, not grandfathered.
  • A newly-invalid preserved value is reported at once, not held until commit: the user changed something and the consequence is theirs to see. A value the user has never touched is still not judged before they reach it.
  • The message names the condition, not just the rule. “Scrap must clear the hold within 14 days. Shorten the hold, or change the disposition” tells the user both fixes; “Maximum 14” tells them a number they cannot account for.
  • The problem attaches to the field the user is expected to change, which is usually the dependent and not the controller. Marking both leaves the user to guess which one is wrong.

§12

Accessibility

  • A change in what is being asked is announced, not merely rendered. Visual proximity is not perception: a user reading through a virtual cursor, or magnified onto one field, sees nothing at all when two fields appear elsewhere. The statement names what now applies, what no longer does, and what became of anything entered.
  • One statement per change, politely. A live region assertive enough to interrupt every keystroke-driven re-evaluation is worse than none; announce on the settled result of a controlling change, once.
  • Focus is never left inside content that becomes unavailable. When a controlling change strands the focused element, focus moves to the control that caused the change — a place the user can account for. Focus must not be dropped to the document, and must not be moved when nothing was stranded.
  • Requiredness changes are carried in the accessible name and state, not by an asterisk alone: the field's required state follows the rule, and the condition is in its description so it is read on arrival.
  • Newly available dependents are reachable in the reading order that matches their visual placement — immediately after their controller, not appended at the end of the group.
  • A disabled dependent explains itself outside the control. A disabled control is not focusable and its own text may never be read; the condition belongs in the surrounding Field or Fieldset.

§14

Content rules

  • The controlling choice states its consequence where the choice is made — “Scrap: write the lot off at standard cost — asks for a justification and a quality manager”. A user choosing blind cannot weigh the cost of the branch they are entering.
  • Every dependent states its condition in its own description, in words, and permanently. “Required for Scrap”, not “Required”. A label that only makes sense to someone who watched it appear fails everyone who did not.
  • Never refer to the disclosure event. No "the field below", no "now that you have chosen this" — position and history are not available to every reader, and neither survives the value being restored from a draft.
  • The change statement is written in terms of applicability, not visibility: "no longer applies", not "hidden". What the user needs to know is whether they are still being asked, not what the interface did.
  • Dependent errors name both values and the direction of the fix, since two values produced the conflict and either may be the one the user wants to change.
  • Terminology is stable between the controlling option, the dependent's condition line, and any error that cites it: a disposition called “Scrap” in the radio is “Scrap” in the hint and “Scrap” in the message.

§18

Edge cases

ConditionRequired behavior
Controller changes while focus is inside a dependentThe in-progress value is handled by the retention policy, the change is announced, and focus moves to the controller. The keystroke in flight is never committed to a field that no longer applies.
Previously valid value becomes invalidRe-evaluated against the new condition and reported immediately on the dependent, with the controlling value named. Never silently corrected, clamped, or left as an accepted value that the rules now reject.
One controller, several dependentsAll governed dependents transition in one pass and are announced as one statement. Not one announcement per field, and never a partially applied group.
Chained dependencyA dependent behind an inapplicable parent is inapplicable, whatever its own condition says. Evaluate parents first; a child may never be active under an inactive parent.
Rapid controller changesEach evaluation is complete and independent; the final value set decides. Announce the settled result, not every intermediate one.
Restored draft or deep linkRules are evaluated on arrival. A stored value whose condition is false is inactive and out of the submission — even though nothing was disclosed in this session.
Controlling value cleared to noneAn empty controller is a value like any other: its dependents are inactive, not indeterminate. There is no third state between applicable and not.
Dependent options depend on the controllerA dependent whose choices narrow keeps its value only if the value survives in the new set; otherwise the value is cleared and the user told, never mapped onto a neighbouring option.
Condition restored after clearThe dependent returns empty and incomplete. It must not appear complete, and must not be treated as untouched-and-therefore-fine at commit.
§20

Implementation notes

  • Three separable stores: values, applicability, validity. Applicability is derived from values; validity is derived from both. Storing "visible" or "required" as writable state is what allows the three to drift apart.
  • Applicability is one pure function of the whole value set, returning a map keyed by dependent. Not a condition scattered across each field's own render, which cannot be read as a whole, tested as a whole, or checked for cycles.
  • Chained rules restate their parent's condition in the same function, so an inactive parent cannot leave an active child even for a frame.
  • The submission is built from the applicability map, not from what rendered. Same map, same source of truth, for the fields, the requiredness, the validation and the payload.
  • Preserved values live above the controls. A value held in a field that unmounts is a value lost; retention must be state the mount cycle cannot touch.
  • Sequence on a controlling change: re-evaluate the graph → apply retention → render → announce → move focus if the active element was stranded. Moving focus before the new content exists lands it nowhere.
  • Confirm the focus move landed. The withdrawal that stranded focus is a re-render, and a re-render can replace the node focus was just placed on — leaving the document focused a frame after the move looked successful. Place focus, then verify it holds, and place it again if it fell back to the document.
  • Check for cycles where rules are defined, not where they run. A dependency graph that can be traversed can be validated; a cycle discovered at runtime shows up as a render loop, not as a message.

Omitted sections and why. §06 Variants — hidden versus disabled, and preserve versus clear, are declared policies within one contract (§05), not different forms of the pattern; a dependency that changes the destination is a stepped flow. §07 Sizes — no coordinated sizing exists at the pattern level. §10 Error handling — the pattern commits nothing and calls nothing; operational failure belongs to whatever pattern owns the commit, normally validated submission. A dependent whose options load remotely inherits that component's loading contract. §11 Input & interaction modalities — every affordance is an ordinary control; the one cross-component responsibility the pattern adds, moving focus out of withdrawn content, is stated in §12 because it is a focus contract rather than a modality one. §13 Motion — disclosure may be animated for continuity, but no motion carries pattern-owned meaning, and a transition must never delay the announcement or the focus move of §12. §15 Responsive — the questions asked do not change with available space; only their layout does. §16 Internationalization — locale-sensitive parsing and formatting of individual values are owned by the capturing controls, and the pattern is direction-agnostic. Its one cross-cutting requirement, that a dependent never refers to the position of anything, is stated in §14. §17 Performance — evaluation is local and synchronous, and must be immediate; nothing here waits, and a rule that does is a remote validation governed by §17 of validated submission. §19 Anti-patterns — the refusals in §01, the trapping and silent-discard rules in §04, and the blocking rule in §09 cover the recurring misuses. §21 Developer notes — the contract in §04, §05, §08 and §20 is the whole contract; there is no separate API surface.
