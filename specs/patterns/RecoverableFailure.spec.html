Interaction pattern

Recoverable failure

An operation failed, the user's work is still good, and there is a way forward — so the pattern's job is to say what did not happen, keep everything that remains valid, and offer a recovery that targets the failure rather than repeating work that already succeeded. Failure, validation and emptiness are three different things, and this is the specification that keeps them apart.

§01

Purpose

Required

At 22:10 IST the line supervisor on PR-05 posts six production confirmations and a downtime note he has just typed. MES does not answer. Nothing about the shift is wrong: the figures are right, the note is right, and in thirty seconds the gateway will be back. What decides whether he loses ten minutes of work is entirely in the interface — whether the note survives, whether the retry sends the four confirmations that already posted a second time, and whether the message tells him the shift is unposted or merely that "something went wrong".

Use it when an operation or retrieval has failed and the user can meaningfully retry or correct the situation while keeping useful context.

Appropriate

  • An operation that failed for reasons outside the user's control — an outage, a lock, a refusal by another system.
  • A retrieval that failed while the screen still holds the user's own work.
  • A failure where part of the work succeeded and the rest must be recovered without repeating it.

Not this pattern

  • Field validation. A rule about the user's input is decided locally, shown on the control, and is not a failure — it belongs to validated submission and the components' own contracts. Presenting it as an operational error blames the user for a rule the screen could have stated.
  • A successful operation that returned nothing. Zero confirmations, zero results, an empty queue: the system answered, and the answer was none. That is EmptyState, with no cause and no retry.
  • Pending. Work in flight is asynchronous action; this pattern begins at the moment that operation resolves badly, and inherits its identity, guard and pending rules.
  • A failure with no recovery of any kind. If nothing the user can do changes anything, the honest interface states the condition and who to contact — and does not draw a retry button (§10).
§02

Anatomy

§03

Flow

  1. An operation fails. The failure is captured with the context needed to retry it: what was attempted, on which subjects, with which of them succeeded, and which attempt this was.
  2. The failure is communicated where the affected state is, saying first what did not happen and then why.
  3. Recoverable state remains. Input, selection, scroll position and already-succeeded work are untouched.
  4. The user recovers — retrying, or correcting the relevant input, or taking the alternative route the failure named.
  5. The attempt runs again, scoped by retryScope and guarded by retryBackoff, with pending feedback.
  6. It resolves. Success clears the failure. Another failure replaces it — with the attempt count, and under repeatedFailure an escalated message — rather than accumulating beside it.

The failure is a state of the operation, not a message that was shown once: it is created at step 1, replaced at step 6, and cleared the moment its condition stops being current — including when a fresh retrieval or a different route has made it obsolete.

§04

Behavior

  • Failure destroys nothing that is still valid. Typed input, chosen values, selection and the results of the parts that succeeded all survive. This is the pattern's first obligation and the one most often broken by unmounting the region that failed.
  • Recovery targets the failed operation, or its current valid replacement. If the user changed the input after the failure, the retry sends what is on screen now — never a replay of the attempt that failed.
  • Work that succeeded is not repeated. Where the composition can tell which parts went through, the retry covers only the rest, and says so in its label.
  • One failure state, replaced not stacked. A second failure supersedes the first and carries the attempt count; three alerts for three attempts is a screen that cannot be read and a state model that cannot be trusted.
  • Success clears obsolete failure state, at the same moment it reports success. So does any other event that makes the failure untrue — a fresh retrieval, a recovery by another route, a change that removes the condition.
  • Failure is a category of its own. Validation, emptiness, pending and operational failure are four separate states, each with its own component and its own copy, and none is rendered in another's clothing.
  • Stale content is labelled, not disguised. Content kept through a failed refresh says when it was read and that it may no longer be current.
  • A non-recoverable failure offers no retry. It states the condition and the route that does exist — a different document, a different terminal, a person.

§05

Properties

PropertyOptionsWhat it decides
retryScopefailed-only · whole-operationWhat a retry sends after a partial failure. failed-only is the default and the correct one wherever repeating succeeded work has an effect — a duplicate confirmation is a duplicate booking. whole-operation is defensible only where the operation is idempotent as a whole, and the label must then say how many it is sending.
repeatedFailureescalate · sameWhat the second consecutive failure says. escalate adds the attempt count and the route that exists when retrying is evidently not working — another terminal, another person, a deadline. same is for a failure with no alternative, where an escalating message would only add noise.

retrievalPreservationkeep · clearWhat happens to already-retrieved content when a refresh fails. keep — labelled with its age — is right wherever stale data is better than no data, which on a shop floor it usually is. clear is for content whose staleness is dangerous, and it then has to say that it cleared and why.

§08

States

StateWhat is trueWhat is displayed

Each category says who has to act: the user, nobody, or the system. That distinction is the whole content of the difference.

Don't

shown when MES timed out, when the shift was empty, and when the note was too short

One message for three situations: it blames the supervisor for an outage, invites a retry against an empty shift, and hides the one rule he could actually satisfy.

§10

Error handling

  • Recoverable and non-recoverable failures are distinguished before anything is rendered. The distinction decides whether a retry control exists at all.
  • No retry where repeating the operation cannot change the outcome. A closed period, a revoked permission, a rejected reference: retrying produces the same refusal and teaches the user that the button is decorative.
  • A non-recoverable failure names the route that exists — the correction document, the other terminal, the person who can reopen the period — and carries the user's work into it rather than making them retype it.
  • Partial failure reports both halves. What went through, what did not, and per item why; the recovery covers only the remainder under retryScope.
  • Retrieval failure and operation failure are different failures with different recoveries: read again, or post again. They are never merged into one "something went wrong".
  • The cause is stated at the level that supports recovery. "The cost centre is blocked for period 2026-09" is actionable; a stack trace and "Error 500" are not, and neither is "unexpected error".
  • Sequential failures replace each other and keep a count. Two consecutive failures of the same operation are one state with attempt 2, not two states.
  • Obsolete failures are cleared, not left to be contradicted by the screen around them.
Do
Period 2026-09 is closed — this shift cannot be posted

A retry that cannot succeed, offered against a closed period: the supervisor presses it until the shift is late, and nothing on screen mentions the correction document that would have worked.

§12

Accessibility

  • The failure is communicated in text, not by colour or an icon alone. The Alert's title names the failure; tone is reinforcement, never the message.
  • A failure that appears announces itself as an alert, because the user's belief about what happened is now wrong. One announcement per failure, not one per attempt artefact.
  • The recovery action is in logical focus order, immediately after the text that explains it — not before it, and not in a toolbar elsewhere on the page.
  • Repeated failure is announced with its count, so a screen-reader user can tell attempt 2 from attempt 1; an identical announcement twice is indistinguishable from nothing having happened.
  • Successful recovery is announced, and says that the earlier failure no longer applies. Silently removing an alert leaves the user believing the failure stands.
  • Preserved state is stated, not merely still rendered: "your note and the downtime reason are unchanged" is the only way a non-sighted user knows nothing was lost.
  • Focus stays where the user was. Failure does not steal focus; a validation refusal moves focus to the field that must change, because that is where the user must act.
§14

Content rules

  • Lead with what did not happen, in the domain's own terms. "Nothing was posted" before "gateway timeout".
  • Explain at the level recovery requires, and no deeper. The supervisor needs to know whether to retry, wait, or raise a correction — not which service returned which code.
  • Never blame the user for an operational failure. "Check your entries and try again" against an outage is a false accusation, and it sends the user hunting for a mistake that does not exist.
  • Say what is preserved. Naming the note, the reason and the four confirmations that posted is what makes the guarantee visible.
  • Recovery labels describe the next action and its scope. "Retry the 2 refused confirmations", "Repost all 6", "Raise a correction document (4C)" — never a bare "Retry" where the scope is ambiguous.
  • Empty is not phrased as failure, and failure is not phrased as empty. "No confirmations recorded this shift" against "The shift could not be read" — one is an answer, the other is the absence of one.
  • An escalated message adds a route, not adjectives. "MES has refused twice; post from the plant office terminal or hand it to Anjali Deshmukh" beats "Still failing. Please try again later."

Both halves reported, the refusal explained per operation, and a label whose scope cannot be misread.

§17

Performance

  • A retry shows pending feedback under perceptible latency, in the region that failed, under asynchronous action's appearance threshold. A retry that looks like nothing happened gets pressed again.
  • Repeated retries never run concurrently. One attempt at a time, guarded at the state transition; retryBackoff additionally rate-limits the control, and the press that lands inside the guard is answered in words rather than ignored.
  • Automatic retry, where a product chooses it, is bounded, visible and interruptible — a stated attempt count and a way to stop. Silent background retries make the state model unreadable to the user and to whoever debugs it later.
  • The failure state does not depend on a timer. Nothing about it expires; only the user's recovery or a change in the underlying condition removes it.
  • Only the current attempt may write. A response from a superseded attempt is discarded, exactly as in asynchronous action §20.
§18

Edge cases

ConditionRequired behavior
Dependency remains unavailableEach attempt replaces the failure and increments the count; under escalate the message adds the alternative route. Never an unbounded loop of identical alerts.
User changes relevant state before retryingThe retry sends the current valid state, not the attempt that failed. Where the change resolves the failure's cause, the failure is cleared rather than retried.
Retry succeeds after the original context changedSuccess is reported against what was actually sent, and the failure is cleared. A result that no longer has a subject is reported, not written blind (asynchronous action §05).
Partial failureBoth halves reported; recovery scoped by retryScope; the succeeded part never sent again under failed-only.
Partial failure, then a full failure of the remainderOne failure state describing the remainder, with the earlier successes still recorded as posted.
Failure while validation is also outstandingBoth are shown in their own places — the rule on its field, the failure in its region — and the recovery makes clear which must be resolved first.
Retrieval fails while the user has unsaved inputInput untouched; retrieved content kept or cleared per retrievalPreservation, labelled either way.
Retrieval succeeds after an operation failedThe operation's failure is obsolete once the state has been re-read; it is cleared, and the user is told it was.
Non-recoverable failure resolved by another routeThe failure is replaced by what the route produced — a document number, an owner, a next step — not left on screen beside its own resolution.
§20

Implementation notes

  • Hold the failure as state with its retry context: { kind, recoverable, why, subjects, failedSubjects, attempt }. A message string is not a failure state, and everything in this specification needs the context that a string throws away.
  • Never rebuild the region that failed. Preservation is achieved by not unmounting and not resetting — every scheme that restores values after the fact loses something.
  • Keep four state categories separate in code, not just in copy: validation problems, emptiness, pending, and operational failure. One error field used for all four is how an outage ends up telling a supervisor to check his entries.
  • Record which subjects succeeded as they succeed, so the remainder is derivable and failed-only retry is a consequence of the data rather than a special case.
  • Derive the retry payload at press time from current state, not from the failed attempt's payload.
  • Clear the failure wherever its condition stops being current — success, a fresh retrieval, a resolving edit, recovery by another route. Put those clears next to the events that cause them, or stale errors will outlive their cause.
  • Model non-recoverability explicitly as a flag on the failure, set from what the service said. Deciding it in the view means the retry button appears wherever someone forgot.
  • Guard the retry at the transition and rate-limit the control, answering a press inside the guard rather than disabling it (§05, §17).
  • Keep an attempt log, including refusals and discarded responses. A failure that is retried five times and then resolves by another route is a story someone will have to reconstruct.
