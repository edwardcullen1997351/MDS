Interaction pattern

Explicit save

Editing that stays provisional until the user says otherwise — a draft the pattern opens from committed state, a commit that promotes it in one piece, a cancel that restores by discarding it, and a dismissal whose meaning is declared in advance rather than decided by which control the user happened to reach.

Written against: Interaction pattern spec standard §01–§21Required: at least one editable control, ButtonGroup or several ButtonsReference implementation: card · standaloneReference domain: manufacturing ERP — parameters of a routing operationSections included: 13 of 21status: frozen 7 Sep 2026 · 0 open items
§01

Purpose

Required

A manufacturing engineer opens operation OP-40 of routing RTG-7310-B to re-time it: setup up from 60 to 75 minutes, the check frequency tightened, a note saying the coolant nozzle changed. Every figure she types would, if it took effect on the keystroke, be a live instruction to the shop floor — so none of them may, until she says so. The pattern owns the boundary around that work: what the routing reads while the form is open, what the commit promotes, what the cancel restores, and what Escape means at the moment there are unsaved changes.

Use it when a set of changes should be provisional until accepted or discarded, and the acceptance is a decision the user makes deliberately.

Appropriate

  • Settings, parameters and configuration that take effect together and are worth reviewing before they do.
  • An editing context — a drawer, a dialog, a panel — over a record whose live value other people are reading.
  • Any edit where abandoning the work must be as available, and as unambiguous, as accepting it.

Not this pattern

  • Immediate-effect controls. A switch that applies on toggle has no draft and no cancel; it needs an optimistic update and its own failure handling.
  • Creating or completing a record. A form whose whole purpose is one submission is validated submission — its defining feature is the validated commit, not a draft boundary. Across ordered steps it is staged input.
  • Editing inside a collection, row by row. A draft per item in the list's own context is collection editing; this pattern is one draft over one subject in an editing context of its own.
  • A decision with no editing. "Cancel this work order?" holds no draft — that is confirmed action. A confirmation dialog appearing inside this pattern, to resolve a dirty dismissal, is a use of that pattern, not a merger of the two.
  • Autosave with undo. If changes commit continuously and the safety net is a reversal, the contract is undo, not a draft; do not name a Save button that does nothing.

§03

Flow

  1. Enter editing. A draft is created from the committed state and stamped with the revision it was opened against. Nothing else happens: opening the editor is not a write.
  2. Modify the draft. Committed state is untouched, and anything reading it — the table behind, another user's screen, the MES — still reads the old values.
  3. Decide. Commit, cancel, or attempt dismissal.
  4. Commit validates the draft first (§09) and refuses without closing or clearing anything. A valid draft is promoted in one piece; the disposition afterwards follows postCommitDisposition.
  5. Cancel discards the draft, which restores committed state because committed state was never written to. Under cancelWhenDirty: confirm it asks first; a clean draft never asks.
  6. Attempted dismissal — Escape, the scrim, the close control — resolves through the single rule dismissalPolicy declares. A clean draft closes silently under every policy.
  7. Resolution. On success committed state is replaced and the change is announced. On failure the draft stands exactly as typed, committed state does not move, and the message says both things.

Steps 3 to 6 are one decision with three doors, and the pattern exists because two of those doors are easy to get wrong: cancel must be reachable while the draft is invalid, and dismissal must not silently pick one of the other two.

§04

Behavior

  • Committed state and draft state are separate. The draft is a copy; editing writes only to the copy. No component, and nothing downstream, reads the draft as though it were committed.
  • Entering editing initialises the draft from committed state, every time — never from a previous draft, never from whatever the controls last held.
  • The commit promotes one coherent draft. All of it, at one moment, or none of it. A commit that lands field by field is not this pattern and cannot be cancelled.
  • Cancel restores committed state by discarding the draft, and is available in every state the draft can be in, including invalid and failed. There is no undo to compute.
  • Dismissal has one declared meaning. Escape, the scrim and the close control all route to the same rule, and that rule is the same every time: guard, discard, or refuse. Dismissal must never alternate between committing and discarding.
  • Dismissal never commits. Under no policy does closing the editing context save. A user who wanted to save can always find the button that says so.
  • A clean draft is not guarded. Asking "discard your changes?" of a user who made none teaches them to click through the question they will later need to read.
  • Dirty is derived, not remembered. It is the comparison of committed values with draft values, so returning a field to its committed value makes the draft clean again and dismissal stops asking (§20).
  • A commit is single-shot until it resolves, guarded at the state transition rather than by the button's disabled attribute, and a superseded or orphaned response writes nothing.

§05

Properties

PropertyOptionsWhat it decides
surfacedrawer · dialog · inlineWhere the draft is edited. drawer keeps the subject's context readable beside the work and suits several parameters; dialog is right where the edit is short and must be finished before anything else; inline has no dismissal affordance at all, so dismissalPolicy becomes inapplicable and commit and cancel are the only exits. The choice changes what has to be declared, which is why it is a pattern property and not styling. It also decides modality, and with it which rules can be exercised: a modal surface makes a second entry unreachable and hides the subject's committed values behind a scrim, while a non-modal drawer or an inline panel keeps them readable beside the draft — which is the point of editing beside a collection at all. Prefer a non-modal drawer where the committed state is worth seeing; keep the dialog modal, because a dialog is a decision.

No option commits.

§08

States

StateWhat is trueWhat is displayed
cleanA draft exists and equals committed state.Editors seeded from committed values, cancel available, and a commit that has nothing to do — inert, with a sentence saying why. Dismissal does not ask.
dirtyAt least one draft value differs from committed state, or a commit-only field such as a change note has content.What differs and what committed state still holds, an active commit, and a cancel named as a discard. Dismissal follows dismissalPolicy.
invalid draftThe draft is dirty and breaks a rule. Fully editable.The problem on the offending control, the rule beside it, a commit that refuses without discarding, and a cancel that is not blocked by the errors.
commit pendingA valid draft is being committed.Progress naming the subject, editors inert with the draft still visible, and no claim that anything has been saved.
commit failedThe commit failed. The draft is intact; committed state is unchanged.The cause, an explicit statement that nothing was committed, and a retry. The draft is still dirty and still the user's.
committedCommitted state has been replaced by the draft.The new values wherever they are read, one announcement, and the disposition postCommitDisposition declares.
cancelledThe draft is gone; committed state was never written.The committed values, and a statement of what was discarded — never a claim that anything was restored, because nothing changed.

"Dirty" is a comparison, not a memory of activity. A form that goes dirty on the first keypress and stays there will guard a dismissal after the engineer types 75, thinks again, and types 60 back — asking her to discard changes she has already undone by hand, and training her to answer the guard without reading it.

§09

Validation

  • Validation gates the commit, not the typing. Errors may appear as the user works, but no keystroke is rejected, no control is locked, and the draft is never coerced.
  • The whole draft is validated in one pass, against one snapshot, so cross-field rules read consistent values: the check frequency rule depends on the scrap allowance in the same draft, and the work centre's capability depends on whether first-piece approval is on.
  • Cancellation does not require validity. The way out of an invalid draft is never "fix it first". This is the rule most often broken by disabling every control but the commit.
  • An invalid draft stays whole and stays editable. A refused commit clears nothing, closes nothing, and moves nothing but focus, which goes to the first offending control.
  • Each problem is attached to the control it belongs to through Field's error, and a cross-field rule is reported on the control the user can change to satisfy it, stating the values it used.
  • Fields that exist only for the commit are required only when there is something to commit. A mandatory change note is demanded of a dirty draft, not of a form the user merely opened.

§10

Error handling

  • A failed commit preserves the draft, exactly as typed. Every field, including the long ones. The work is the user's and the failure was not theirs.
  • A failed commit states that nothing was committed, in the subject's own terms — "routing RTG-7310-B still reads revision 6" — before it explains the cause.
  • The editing context stays open on failure. Closing it to show the error puts the message and the draft in different places, and the user cannot act on either.
  • Retry sends the draft as it is at the moment of retry, never the values that failed; the user may have corrected them in between.
  • A stale draft is reported, not overwritten. If committed state moved after the draft was opened, the commit says so, names the revision, keeps the draft, and offers the choice between committing over it and reloading from it. Silent last-write-wins destroys someone else's change.
  • A subject withdrawn mid-edit ends the edit and keeps the explanation, including what the uncommitted values were. The draft cannot be committed because its subject is gone.
  • Failure never leaves the draft looking committed. Anything outside the editing context that shows the subject keeps showing committed values.

§12

Accessibility

  • Commit and cancel have distinct accessible names that carry the subject — "Save the changes to OP-40 as routing revision 7", "Discard the changes to OP-40 and keep revision 6". Two buttons called "OK" and "Cancel" in a routing editor are two unlabelled risks.
  • Entering editing moves focus into the first editor, not onto the container, so the keyboard is where the work is.
  • Focus lands predictably when the editing context closes: on the control that opened it, after a commit under close, after a cancel, and after a dismissal. Never on the document body, and never lost inside a removed subtree.
  • The dirty-dismissal decision opens with focus on the non-destructive choice and returns focus to the editor the user was in when they choose to keep editing.
  • Errors that prevent the commit are communicated before the user is asked to retry — announced on refusal, with focus moved to the first problem, so the second press is informed.
  • Draft state is stated in text, not only in appearance. That there are unsaved changes, how many fields differ, and that the subject is unchanged, are all readable — a screen-reader user cannot see that a field looks modified.
  • Under block, the close control is removed rather than disabled, so nothing announces as an available exit that is not one.
§14

Content rules

  • The two actions name their outcomes, not their mechanics. "Save changes" and "Discard changes" — never "OK", "Done" and "Close", where nothing on screen says which one keeps the work.
  • Where the consequence is countable, count it. "Discard 4 changes" beats "Discard"; "Save writes revision 7" beats "Save".
  • While the draft is dirty, say what the subject still holds. "The routing still holds revision 6 until you save" is the sentence that makes the draft boundary visible.
  • If dismissal discards, the context says so before it happens — in the editing surface, not only in the guard dialog. Under discard there is no dialog to carry the warning.
  • A clean draft's inert commit explains itself. "Nothing to save yet — change a parameter first", never a dead button with no reason.
  • Cancel copy names what is kept, not only what is lost. The committed state is the thing the user is returning to.
  • Never label a discard as a cancellation of the operation itself. "Cancel" beside a work-order form reads as cancelling the work order; name the object of the verb.

§17

Performance

  • Typing is never gated on validation or on the network. Draft edits are local and immediate; validation is cheap and runs on the draft in memory.
  • The commit is guarded at the state transition, not by disabling the button — a second press arrives before the disabled attribute lands, and two commits mean two revisions of the same change.
  • Each commit carries a request identity, and only the current one may promote a draft or clear it. A response that arrives after a cancel, a newer commit, or the subject's withdrawal writes nothing.
  • A commit slow enough to notice is reported where the draft is, with progress naming the subject, and with the draft still legible — not behind a page-level overlay.
  • Nothing about the draft is persisted on a timer unless the product says it is. A background autosave silently converts this pattern into autosave-with-undo and voids the cancel guarantee.
§18

Edge cases

ConditionRequired behavior
No changes were madeThe commit is inert and says why; dismissal and cancel close without asking. Committing nothing must not write a revision or announce a change.
Draft returned by hand to committed valuesThe draft is clean again — derived, not remembered — so the guard stops asking and the commit goes inert.
Dismissal while dirtyResolved by dismissalPolicy, identically for Escape, the scrim and the close control. Never a commit.
Commit fails after valid inputDraft preserved as typed, committed state unchanged and said to be unchanged, context open, retry available against the current draft.
Committed state moved while the draft was openReported at commit against the revision the draft was opened on; the draft is kept and the user chooses. Never patched into the draft as the user types.
Subject withdrawn while editingEditing ends, the draft cannot be committed, and the pattern states which subject left, why, and what the uncommitted values were.
Repeated commit activationThe second activation is refused while the first is in flight. No queue, no second revision.
Invalid draft plus an attempted dismissalDismissal is resolved on dirtiness alone; validity is irrelevant to leaving.
Navigating or closing the window with a dirty draftOut of the pattern's power to prevent, in its obligation to warn: the unsaved draft is announced as unsaved, and the product decides whether to guard the exit as well.
Opening a second editing context while one is dirtyRefused, with the open subject named and focus returned to it — one draft boundary at a time, or two commits race the same screen. Under a modal surface the case cannot arise, because the scrim already prevents it; the rule is still required, because the same screen may be given a non-modal or inline surface (§05) and because programmatic entry points do not meet the scrim.
§20

Implementation notes

  • Hold committed state and draft state as two values, and let the editors write only the second. Every guarantee in this specification follows from that one arrangement; each alternative reconstructs them badly.
  • Derive dirty by comparing the two, field by field. Never a touched flag, never a change-event counter, never the controls' own visual state — those all report activity, and activity is not difference. Count commit-only fields (a change note) as dirty when they have content, and say so in the spec of the screen.
  • Normalise before comparing. Draft values arriving from text controls are strings; comparing "60" with 60 makes every draft dirty forever, which is the usual cause of a guard nobody can escape.
  • Route Escape, the scrim and the close control through one handler, and put the policy in that handler. Three call sites are three chances for the three exits to diverge.
  • Stamp the draft with the revision it was opened against, and compare at commit. Without it a stale draft is undetectable and the §10 rule is unimplementable.
  • Derive the draft's state, do not store it. Clean, dirty, invalid, pending, failed and committed are all computable from the two values, the validation result and the in-flight request. A stored isDirty is what survives the change that cleared it.
  • Validate a copy of the whole draft in one function returning problems per field; per-control validators closing over stale siblings produce cross-field errors that contradict the screen.
  • Copy values out of the committed object when seeding the draft. A draft holding a reference into committed state is a mutation waiting for a re-render — and it silently deletes the cancel guarantee.
  • Keep focus management with the transitions — entry to the first editor, refusal to the first problem, exit to the control that opened the context — rather than inside the editors, which then fight each other on mount.
