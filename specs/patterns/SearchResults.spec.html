Interaction pattern

Search results

Submitting or changing a query and keeping the retrieved result set coordinated with it — including what the previous results mean while new ones are on their way, and the permanent difference between a search that found nothing and a search that did not happen.

§01

Purpose

Required

A planner types part of a part number and reads back a set of items. Two things are on screen — a query and a collection — and the whole difficulty is that they are retrieved at different moments. The pattern owns the correspondence between them: which query the displayed rows belong to, what happens to those rows while a newer query is being retrieved, what an empty collection means, and how a service that did not answer is told apart from an item master that answered and holds nothing.

Use it when query entry and a retrieved collection form one coordinated interaction whose result state has a lifecycle — loading, results, none, failed.

Appropriate

  • A lookup against a record set too large to present whole.
  • Search whose results are retrieved, paginated, or sorted by the service rather than in the page.
  • Any search that can fail, wait, or return nothing.

Not this pattern

  • Renaming SearchField. The component owns the query value, clearing, and the submit split. The pattern begins where the query governs a result collection and its states.
  • Choosing one value from suggestions. A listbox with a cursor and a selection contract is Autocomplete; nothing is retrieved into the page and there is no result set to keep coherent.
  • Narrowing a set already in the page. Filtering a loaded collection with no request, no wait and no failure mode is a filter, not this.
  • Starting a long job. A report the user waits minutes for, and returns to, is an asynchronous operation with its own progress and completion contract.
§02

Anatomy

RoleComponentRequirement
Query entrySearchFieldRequired. One query value. Whether onSubmit is present is the pattern's trigger decision (§05), not a styling choice.
Result collectionTable or List (with ListItem, or Card per result)Required. Presents the result set that belongs to one query state. Its sort and selection are result-dependent state the pattern coordinates (§04).
Retrieval indicationSkeleton or Table loading · ProgressRequired whenever retrieval is perceptible. Skeleton where the result shape is known and nothing is being replaced; Progress where existing results stay on screen and the wait needs a signal that is not a false row.
Zero matchesEmptyState variant="no-results"Required wherever zero matches is reachable. The variant exists to keep this case apart from first-run: the collection is not empty, this query's slice of it is.
Retrieval failureAlert tone="danger"Required wherever retrieval can fail. Carries the cause, the preserved query, and the retry. Never an EmptyState.

StatusLive region (role="status")Required. One polite statement per resolved retrieval — the count, the range shown, and any reset that was applied (§12).

What the pattern owns is not this list but the pairing: one query state, one result set, one status statement, and the rule that the three never describe different queries at the same time.

§03

Flow

  1. Entry. The pattern opens in a declared state: an initial prompt with no result set, or the full set under an all-results empty query (§05). A query restored from a URL or a draft is retrieved on arrival like any other.
  2. Query change. The user provides or edits the query. Under as-you-type this schedules a retrieval; under on-submit it changes nothing but the query state, which is then visibly ahead of the results.
  3. Initiation. A retrieval is issued for the current query, page 1, and the current sort. Page position from the previous query does not travel with it.
  4. Retrieval. The pair enters retrieving. Under retain the previous set stays, labelled as the previous query's; under replace it is withdrawn in favour of skeleton rows.
  5. Resolution. The retrieval resolves to results, zero matches, or failure. Only a response from the current request may write result state.
  6. Statement. The resolved outcome is announced politely, once, with the count and the range. Focus does not move.
  7. Within a result set. Paging and sorting are retrievals against the same query and re-enter step 4. They never rearrange one page and call it the set.
  8. Revision. The user edits the query and the sequence repeats; or clears it and returns to the state declared in step 1.

Sequence matters in one place: the status statement is made from the resolved response, never from the request. Announcing at initiation states a count that is not yet known and, when the response is discarded as obsolete, a count that never becomes true.

§04

Behavior

  • Every displayed result set corresponds to a defined query state, and says which one. The set carries the query it was retrieved for; the count and the range are stated in terms of that query, not of what is currently in the field.
  • Retrieval is a state of the pair, not a third screen. A search that is retrieving still has a query and — under retain — still has the previous results. Blanking the region on every keystroke destroys the reference the user was reading.
  • Retained results are labelled, never re-captioned. While a newer query is in flight, the visible rows are the previous query's and are described as such. Leaving them under a count or a heading that names the new query is a false statement the user has no way to detect.
  • Zero matches means the retrieval completed. The service answered and holds nothing for this query. Nothing else may produce this state.
  • Failure is never zero matches. A retrieval that did not resolve says so, keeps the query, and offers retry (§10). The two states are permanently distinct because the user's next action differs: revise the query, or try again.
  • Changing the query resets result-dependent state, and says that it did. Page position resets to the first page; a selection of rows that are not in the new set is dropped; a sort the user chose is a property of the query, not of the set, and survives.
  • Paging and sorting are retrievals against the current query. Sorting the rows of one page of many tells the user they have ordered the result set when they have ordered a fragment of it.
  • Only the current request may write result state. A response from a superseded query is discarded — not merged, not appended, not rendered for a frame.
Do

Retrieving items for “brake caliper”.6 items · showing 1–4 for “brake”
BRK-4820-ABrake caliper bracket, LH

The rows on screen still belong to “brake”, and the count says so. The planner can keep reading them and knows they are about to change.

Don't

The count has moved to the new query while the rows are still the old query's. A brake pedal bracket now appears to be a caliper match, and the planner has no way to know it is not.

§05

Properties

Four choices belong to the application of the pattern. Each changes the behavioral contract, so each is declared rather than inherited from whatever the first implementation happened to do.

PropertyOptionsWhat it decides
triggeron-submit · as-you-typeWhen a retrieval is issued. on-submit where retrieval is expensive, the query is long, or a wrong intermediate query is costly to read; as-you-type where the set is cheap and the user is narrowing by feel. on-submit creates the query-entered state (§08) and requires the pending statement that goes with it.
debounceA stated interval, in ms — as-you-type onlyHow long input must settle before a retrieval is issued. A value must be named: retrieving on every keystroke is not an option this pattern offers (§17). Zero is legitimate only where retrieval is local and synchronous, which is a filter, not this pattern.
staleResultsretain · replaceWhat the previous result set does while a newer retrieval runs. retain keeps it, labelled, and is right when the user is comparing successive queries; replace withdraws it for skeletons, and is right when a stale set would be acted on by mistake.
emptyQueryprompt · all-resultsWhat no query means. prompt retrieves nothing and states what is searchable; all-results treats it as a query for everything. Either is defensible; leaving it undeclared produces a clear control that sometimes empties the page and sometimes fills it.
§08

States

Pattern states are states of the query-and-results pair. Retrieval is orthogonal to the outcome currently on screen, which is why it is a column here rather than a row.

StateWhat is trueWhat is displayed
initialNo query has been retrieved. Under all-results this state does not exist.The prompt: what is searched and how. No result region, no zero-match copy.
query enteredon-submit only: the query state is ahead of the result set.The previous set, its own count, and one line saying the results are for the earlier query and how to retrieve this one.
retrievingA request is in flight for a known query. Held with whichever outcome is on screen — including none.retain: the previous set, labelled, plus an indication. replace, or nothing to retain: skeleton rows at result geometry.
resultsResolved, one or more matches, page position valid.The collection, the count and range for its query, and pagination if partitioned.
no resultsResolved successfully, zero matches for this query.no-results empty state naming the query, with a way back (§14). No pagination.
failedThe retrieval did not resolve. The query is intact; the last retrieved set, if any, is intact.The failure alert and retry, above whatever was last retrieved — still labelled with its own query.

Retrieving is not an outcome, and failed is not an outcome of the set. Modelling these six as one enum forces a choice between showing stale rows with no indication and blanking the region on every keystroke. Hold the outcome and the in-flight request as two facts; the six states above are their legal combinations.

§10

Error handling

  • Failure preserves the query — the characters, the caret, and the field's focus. A search that clears itself when the service is down makes the user type it again to find out the service is still down.
  • Failure is stated as failure, with what did not answer and what the user can do. It never borrows the words, the glyph, or the component of zero matches.
  • Retry operates on the query the user currently intends — the one in the field at the moment they retry, not the one that failed, if they have edited it since. A retry that replays a stale query answers a question the user has stopped asking.
  • What was last retrieved survives, labelled with the query it belongs to. Discarding good rows because a newer request failed loses ground the user already gained.
  • A failed page or sort retrieval keeps the result set and the position it had. The set does not silently become page 1, and the failure names the page that could not be retrieved.
  • Repeated failure escalates in words, not in noise. One alert, its cause updated; not one alert per attempt.
Do
BRK-4899
Item master (MES-IM) did not answer within 8 s. Your query is unchanged and nothing has been searched.
Retry “BRK-4899”

Failure named, cause given, query kept, retry pointed at what the planner still wants. Nothing claims the part does not exist.

Don't
BRK-4899
No items found.
Try a different search.

A service outage rendered as zero matches. The planner concludes the substitute is not in the item master and raises a part-creation request for an item that already exists.

§12

Accessibility

  • Result updates are announced without moving focus. The caret stays in the field through every update; a search that sends focus to the results steals the next keystroke and makes narrowing impossible for anyone typing.
  • One polite status per resolved retrieval, naming the query, the count, the range shown, and any reset applied. Announcing at initiation, or once per keystroke, is a live region no one can use.
  • The result region carries aria-busy while retrieving, and its skeletons stay aria-hidden. The region makes the one announcement; placeholders make none.
  • Zero matches announces politely; failure announces as an alert. The first is an outcome to read, the second interrupts because the user's model of what is on screen is now wrong.
  • Keyboard focus stays predictable as the set changes. Focus on a page control that survives the update stays there; focus on a row that no longer exists moves to the result region's container, never to the document.
  • The searchable scope is named where the query is entered, not only in the results heading — a user who arrives on the field alone must know what it searches.

The planner keeps typing while the count is read out behind them. Nothing they do is interrupted by the results arriving.

Focus jumps to the results, so the next characters go nowhere, and an assertive region interrupts itself faster than it can be read.

§14

Content rules

  • Zero-match copy names the query and supports revision. It says what was searched, that the search completed, and what a useful next query would be — a shorter prefix, a description word, a different scope.
  • Zero matches never invites creation as if nothing existed. “Add your first item” is the first-run case; here 1,412 items exist and this query matched none of them. Where creating the record genuinely is the answer, it is named as the consequence — who to raise it with, and that it must exist before anyone plans against it.
  • Failure copy describes failure. It names what did not answer, states that nothing was searched, and never asserts that no matching content exists.
  • Counts state their query. “6 items match “brake”” rather than “6 results”, so a count read out of context cannot be attached to the wrong query.
  • Status wording says what is happening to what. “Retrieving items for “brake caliper”” rather than “Loading”: the second is true of every wait in the product.
  • The initial prompt states what is searchable, including how — part numbers whole and by prefix, descriptions by word — because a query shaped wrongly returns zero matches that read as an absence.

§17

Performance

  • The trigger is declared, not emergent (§05). Whether a keystroke costs a request is a decision with a cost owner.
  • Under as-you-type, request frequency is controlled by a stated interval. Rapid editing must not produce a queue of retrievals whose responses interleave; the interval reduces them, and the request identity (§20) handles whatever still overlaps.
  • A response from an obsolete query never replaces newer result state, however late it arrives. Latency ordering is not response ordering.
  • Retrieval indication is delayed past the flicker threshold — roughly 300 ms. A skeleton that appears and vanishes in 120 ms reads as a fault in the page.
  • The field is never blocked while retrieving. The user must be able to keep narrowing; a disabled search field during retrieval converts every slow response into a lost keystroke.
  • Page and sort travel inside the request. A page retrieved with the wrong sort, or a sort applied to a page, is a coherence failure that presents as a data error.
§18

Edge cases

ConditionRequired behavior
Empty queryHandled by the declared emptyQuery policy, identically whether the field was cleared, emptied by backspace, or never filled. Anything in flight stops being current.
Whitespace-only queryTreated as empty. It is never sent as a query that matches everything by accident.
Rapid query changesThe final settled query decides the result set. Intermediate queries produce no statement and no rendered set.
Out-of-order responsesThe obsolete response is discarded on arrival. Nothing about it reaches the result set, the count, or the live region.
Query changed while a request is pendingThe pending request ceases to be current at the moment the new one is issued — not when its response arrives. Under retain the visible set remains the last resolved one.
Current page ceases to existReset to the first page and state the reset. This covers both a new query with fewer pages and a re-retrieval of the same query whose set shrank underneath the user.
Zero matches on a page beyond the firstTreated as a position failure, not as no results: the query has matches, this page does not. Reset, restate, and do not show zero-match copy.
Selected row absent from the new setDropped from the selection, and the drop is stated with the count. A selection that survives invisibly is acted on by the next bulk action.
Same query submitted againA legitimate refresh under on-submit — re-retrieved, position preserved where it still exists. It is not a no-op, because the set may have changed.
Very long or pasted querySent as entered, and the query in every statement is truncated for display only — never truncated before being sent.
§20

Implementation notes

  • Every request carries a monotonically increasing identity, and only a response whose identity is still current may write result state. This one rule closes the whole out-of-order class; nothing about latency, debouncing, or cancellation replaces it.
  • Cancelling a request is not the same as invalidating it. Aborting the network call is an optimisation; the guard on write is the correctness measure, because an already-delivered response cannot be aborted.
  • Keep the query the user is typing and the query the results belong to as two values. Their inequality is the query-entered and the retaining state; deriving either from a single string is what produces counts attached to the wrong rows.
  • Hold the outcome and the in-flight request separately, as §08 requires. A single status enum that includes loading cannot express “retrieving, over the previous results”.
  • The request key is query + page + sort, and the response is applied against that whole key. A page number stored beside a set retrieved under different terms is a stale coordinate.
  • Announce from the response. The live-region text is derived from the resolved result set, so a discarded response cannot announce a count that was never displayed.
  • Cancel the pending debounce on submit, on clear, and on unmount. A timer that fires after the user has left issues a retrieval whose response has nowhere to go.
  • Derive pagination from the resolved total, never from the requested page. Clamping at resolution is what makes “the page no longer exists” a stated outcome instead of an empty table.
