Interaction pattern

Confirmed action

Requiring an explicit second act before something consequential happens — with initiation that executes nothing, a consequence stated in the units the user will live with, a target captured when the question is asked and revalidated before it is answered, a cancellation with no side effects, and a failure that can never be mistaken for the thing having worked.

§01

Purpose

Required

WO-2026-4471 is running on PR-03 with 3,150 of 4,800 pieces made. Cancelling it strands ₹58,275 of work in progress, releases ₹90,000 of reserved material and leaves assembly line 2 short by 1,650 pieces. One misplaced click should not do that, and a planner who does mean it should be told, in those numbers, what they are about to do. The pattern owns the gap between pressing the button and the operation happening: what the question says, what it is asking about, what happens if the answer arrives late, and what the screen says when the operation fails after the user has already committed to it.

Use it when immediate execution carries a real risk of accidental, consequential and hard-to-reverse effect.

Appropriate

  • Irreversible operations with material consequence — cancelling released work, scrapping stock, deleting a record others depend on.
  • Operations whose consequence is larger than the control that triggers them suggests.
  • Operations whose scope the user cannot fully see from the trigger — a count, a value, a downstream commitment.

Not this pattern

  • Reversible actions. Holding the line is undoable: it acts at once and offers an undo. A confirmation on a reversible action buys nothing and teaches users to dismiss confirmations without reading them — which is how the one that mattered gets dismissed too.
  • Friction for its own sake. A confirmation is not a way to slow a user down, and it is not a substitute for permissions: if this user may not do it, do not offer it.
  • An operation over many chosen items. Whether a confirmation is required for a bulk operation, and what set it names, belongs to bulk selection and action; this pattern owns the confirmation itself.
  • Collecting input. A dialog that gathers values and submits them is validated submission in a modal. An acknowledgement gate is not input.
  • A warning the user cannot act on. If there is no decision — no way to proceed and no way to avoid it — it is an Alert, not a confirmation.
§02

§03

Flow

  1. Initiation. The user activates the action. The operation does not run. The target and the figures the user will be shown are captured (§20).
  2. Confirmation. The dialog states the action, the target and the consequence in the captured figures, and offers exactly two answers.
  3. Cancel or dismiss. Either exits with no effect whatsoever: no operation, no partial write, no change to the target. The capture is discarded and focus returns to the initiator.
  4. Confirm. The pattern revalidates the live target against the capture. If the target moved, the declared targetRevalidation policy decides: refuse and re-present the current figures, or proceed against the live target.
  5. Execution. The operation runs, once, on the confirmed target. Further activation does nothing until it resolves.
  6. Resolution. Success states what happened to the target in its own units. Failure states that the operation did not happen, why, and what the target still is.
  7. Retry. Retry re-enters the flow at step 1 for the same action and target, so the user re-reads a consequence computed from current figures — not a silent second attempt against a stale capture.

Two separations do the work: initiation is not commitment, and confirmation state is not operation state. Collapse the first and a click executes; collapse the second and a dialog that has closed still owns the fate of an operation in flight.

§04

Behavior

  • Opening the confirmation executes nothing. No optimistic write, no lock, no reservation, no analytics event claiming the deed. The order is still running while the question is on screen, and the dialog says so.
  • Cancellation is side-effect free. Cancel, Escape, the scrim and the close control all leave the target byte-for-byte as it was. There is no "cancelled" state to write anywhere.
  • The confirmation applies to the target and action it presented. The identity is captured at initiation; nothing between the question and the answer may redirect it to another record.
  • The live target is revalidated before execution. Where the world can move — a quantity reported, a status changed by MES — the pattern compares the live target with the capture and applies the declared policy rather than sending a stale intent.
  • If the target is no longer valid, no substitute is chosen. The operation is refused, and the pattern says what the target is now. An action whose target vanished has no fallback target.
  • Confirmation is single-shot. A second activation of the confirm control does nothing while the first is in flight — guarded at the state transition, not by disabling the button.
  • Confirmation state and operation state are separate. The dialog closes on confirm; the operation continues in the page's own state, with its own pending, failure and success. A pending operation is never held inside a dismissed dialog.
  • The consequence shown is the consequence computed for the captured target, and the pending and success messages describe the same figures. Three different numbers across question, progress and outcome is the same defect as three different targets.

§05

Properties

PropertyOptionsWhat it decides
acknowledgementnone · checkboxWhether the confirm control is gated on an explicit acknowledgement. none is right for nearly everything: a well-written consequence and a labelled confirm button already require reading. checkbox is for a consequence that lands on someone else — a line supervisor who must be told the press is stopping — where the affirmation is a fact, not a ritual. A typed-reference gate is a third option some products need; it belongs to the same property and is subject to the same rule: one gate, never two.

§08

States

StateWhat is trueWhat is displayed
idleNothing initiated. The action is available if it is permitted.The target and the initiating control, named.

Confirmed is not completed. Closing the dialog on confirm is correct; treating the close as the outcome is not. The moment a screen shows the post-operation state while the request is still in flight, a failure has to un-tell the user something they have already acted on — and on a shop floor they have already told the supervisor.

§10

Error handling

  • A failure after confirmation never implies success. The target keeps its pre-operation state on screen, and the message says the operation did not happen before it says why.
  • The cause is stated in operational terms. "MES refused the cancellation — the shift B production report for PR-03 is open and must be posted first" tells the planner what to do next; "Something went wrong" tells them to try again forever.
  • Retry preserves the action and the target, and re-asks: the consequence is recomputed from current figures and confirmed again. A silent retry against the original capture can send an intent the user formed several minutes and several hundred pieces ago.
  • If the target is no longer valid, retry refuses and says what the target is now — never substituting a similar record, and never disabling itself without explanation.
  • Failure is persistent and in place. Not a toast: the only record of a consequential operation not happening must not expire on a timer.
  • An unknown outcome is reported as unknown. Where the response is lost rather than refused, the pattern says the operation may have been sent and points at where the truth is — never a guess in either direction.

§12

Accessibility

  • The consequence is available before the commitment. The dialog is named by the question and described by the consequence, so both are read on open — not discovered by exploring the dialog after arriving on the confirm button.
  • Focus follows the dialog's contract. It enters the dialog on open and is trapped there; where the action is destructive, initial focus lands on the cancel control or the dialog body, never on the destructive confirm button, which can then be triggered by a keypress already in flight.
  • Focus returns to the initiating context on exit — cancel, dismiss or confirm — which the Dialog handles by restoring focus to the element that opened it. Where that element has since disappeared, focus goes to the region that replaced it, never to the document.
  • The acknowledgement gate is perceivable as a gate. The confirm control's unavailability is explained in text next to it, not signalled only by colour.
  • Asynchronous completion and failure are announced. The dialog is gone by then, so the announcement is the only way a non-sighted user learns the outcome: success politely, failure as an alert.
  • Drift discovered at confirm is announced where the user is, inside the still-open dialog, with the refreshed figures — not as a page-level message behind a modal.

§14

Content rules

  • The question names the action and the target. "Cancel work order WO-2026-4471?" — a title that could belong to any record on the screen is not a confirmation.
  • The consequence is stated in the plant's own units, not as a warning adjective: pieces stranded, rupees of material released, who goes short and by how much. "This action cannot be undone" is true of everything and informs nobody.
  • The confirm label restates the action and its scope. "Cancel 1,650 pieces and close WO-2026-4471" — because the label is the last thing read, and often the only thing read.
  • The decline label says what happens instead. "Keep running", not "No" — a pair of Yes/No buttons under a negatively phrased question is a coin toss.
  • Never a generic confirmation where the consequence is computable. If the system knows the numbers, the dialog states them; if it does not, it says which figures it could not read rather than rounding the risk down to a shrug.
  • The acknowledgement is a statement of fact the user can honestly affirm, naming the person or system affected: "I have told Sandeep Kulkarni that PR-03 is stopping." Not "I understand this is permanent."

§17

Performance

  • The single-shot guard sits at the state transition, not on the button's disabled attribute: a double press on a destructive confirm is faster than a frame, and two cancellations of one work order is a reconciliation job.
  • The dialog closes on confirm and the pending state appears where the user's attention lands. Leaving the dialog open with a spinner in it makes the pending state modal for no reason and traps the user in a decision they have already made.
  • The operation carries a request identity, and only the current one may write the outcome — a response arriving after the target changed or a newer attempt began writes nothing.
  • The page stays usable while the operation runs, except for the action itself: the user may read the record, the schedule and the WIP they are about to inherit.
  • A slow confirmation does not become an optimistic one. If the operation is slow enough that showing the result early is tempting, the answer is progress and a real outcome, not a guess — an optimistic destructive action has no honest failure story.
§18

Edge cases

ConditionRequired behavior
Target's figures change while the dialog is openUnder block: the confirm is refused, the change is stated from-and-to, and the refreshed figures are presented for a second answer. Under proceed: the live target is used, and the outcome states the figures actually acted on.
Target becomes invalid for the actionRefused under both policies, with the target's new state named. No substitute target, ever.
Target disappears entirelyThe confirmation closes with an explanation of what happened to it; nothing is sent, and the initiating control reflects that the action is no longer available.
Repeated activation of confirmThe second activation is refused while the first is in flight. No queue, no second operation.
Non-action dismissal (Escape, scrim, close)Identical to cancel: no side effects, capture discarded, focus restored. Under explicit these paths do not exist and the two buttons are the only answers.
Operation fails after confirmation§10. The target's pre-operation state stands and the retry re-asks.
Response never arrivesReported as unknown, with where to verify. Never resolved optimistically in either direction.
Permission lost between initiation and confirmationRefused with the reason. A confirmation is not an authorisation that outlives the check.
Acknowledgement given, then the target driftsThe acknowledgement is cleared with the refreshed figures: it was affirmed about the old numbers.
§20

Implementation notes

  • Capture the target when the confirmation opens — identity plus the figures shown — and hold it in the confirmation state: { action, snapshot }. The dialog then renders from the capture, so nothing it says can drift mid-sentence.
  • Keep confirmation state and operation state in separate fields. confirm is cleared when the dialog closes; operation lives until the response resolves. One field for both is how a dismissed dialog ends up owning an in-flight request.
  • Compare the live target with the capture inside the confirm handler, before dispatching, and branch on the declared policy. This is the only place the comparison can be correct.
  • Never write anything in the initiation handler. No lock, no soft-delete, no "pending cancellation" flag — the only legitimate side effect of opening a confirmation is the capture.
  • Guard with the operation object itself: a truthy in-flight operation refuses a second confirm synchronously, before any re-render.
  • Tag the request with a monotonic number and check it, plus the target's continued validity, before writing the outcome.
  • Send the identity and the state the user confirmed against, so the service can refuse a stale intent itself: the client-side revalidation is a courtesy, not a guarantee.
  • Route retry back through initiation, not into the executor. Retry is a new confirmation with a fresh capture, which keeps §10's promise that the user confirms current figures.
