Interaction pattern

Collection editing

Changing values on items of a collection in place — with the committed values and the draft held apart, validation run over the draft as a whole, a commit that is the only thing permitted to write the collection, and a failure that leaves the user's figures exactly where they typed them.

Written against: Interaction pattern spec standard §01–§21Required: Table or List, Field, an editable input, ButtonReference implementation: card · standaloneReference domain: manufacturing ERP — the press-shop weekly shift capacity planSections included: 13 of 21status: frozen 7 Sep 2026 · 0 open items
§01

Purpose

Required

A planner is looking at ten press slots for week 2026-W37 and needs to move Monday's PR-03 quantity from 4,800 to 4,400 and put Wednesday's PR-05 slot onto shift C. It is four keystrokes of work against data she can already see, and sending her into a form for each slot loses the comparison that made the change obvious. The pattern owns everything between the first keystroke and the plan actually changing: what the row shows while it is being edited, what happens to the figures if the commit fails, and what the collection says when someone else revised the slot underneath her.

Use it when users change values on items of a collection in the collection's own context, and the collection's other rows are part of how they decide.

Appropriate

  • Adjusting a few fields of a record where neighbouring records are the reference — plans, prices, quantities, assignments.
  • Corrections and small revisions that do not justify a separate screen.
  • Editing that the user expects to abandon freely, row by row.

Not this pattern

  • Creating or completing a record. A record with many fields, dependencies and a meaningful submit is validated submission, and across steps, staged input. In-place editing of eighteen fields is a form with a table drawn around it.
  • One operation over many chosen items. Setting one value on twenty rows at once is bulk selection and action — one snapshot, one operation, per-item outcomes.
  • Inspecting rather than changing. If the row only opens a panel to read, that is selection-driven detail; selection is not a draft.
  • Changing the order of the collection, or an item's membership of it. Moving a row to a new position is direct manipulation of order — order is committed state with its own commit and its own rollback, not a field with a draft. A typed sequence number is this pattern; the move itself is not.
  • Immediate-effect controls. A switch that takes effect on toggle has no draft, no cancel and no commit — it is a control with an optimistic update and its own failure handling, not this pattern.

§03

Flow

  1. Read. The collection shows committed values. Nothing is a draft.
  2. Entry. The user enters editing for one item, by its Edit control or by row activation under the declared entry policy. A draft is created for that identity, initialised from the committed values, and stamped with the revision it was opened against.
  3. Editing. The user changes values. The draft is the only thing that changes; the collection's canonical values are untouched, and other rows still show their own committed figures.
  4. Commit or cancel. Cancel discards the draft, which restores the committed values because they were never written to. Commit validates the draft first (§09) and refuses without leaving editing.
  5. Conflict check. If the item's committed revision has moved since the draft was opened, the declared staleDraftPolicy decides: refuse and show both sets, or overwrite.
  6. Saving. The operation runs on the validated draft. The row reports saving and refuses a second activation.
  7. Resolution. On success the canonical values are replaced, the draft is disposed of under postSaveDisposition, and the save is announced. On failure the draft stands, the canonical values do not move, and the message says so.

The order of steps 4 and 5 is load-bearing: validation is about the draft alone and belongs to the user, while the conflict check is about the world and belongs to the collection. Running them the other way round reports someone else's revision to a user whose own figures are not yet valid.

§04

Behavior

  • Committed values and draft values are separate state. The draft is keyed by the item's identity and holds its own copy; canonical data is not mutated as the user types, and no component reads the draft as though it were the plan.
  • Entering editing initialises the draft from the committed values, every time — never from a previous draft, and never from whatever the input last held.
  • Cancel restores the committed values by discarding the draft. There is no "undo" to compute: if canonical data was never written, restoration is deletion.
  • Editing one item cannot touch another. Drafts are per identity. A shared editor buffer, or a draft keyed by row position, is how a quantity typed for Monday lands on Tuesday.
  • Identity is stable through sorting, filtering and refresh. A draft belongs to the slot, not the row: re-sorting the collection moves the row and takes the draft with it, and a collection refresh that changes other rows leaves the draft alone.
  • Whether several items may be edited at once is declared, not accidental. Under single the pattern refuses a second entry and says which item is still open; under multi each draft validates, commits and fails independently.
  • The commit is the only writer. Canonical values change on a successful commit and at no other moment — not on blur, not on keystroke, not optimistically before the response.
  • A commit is single-shot until it resolves. A second activation on the same item does nothing; the guard is the state transition, not the button's disabled attribute.
  • A superseded commit response is discarded. A response that arrives after a newer commit for the same item, or after the item left the collection, writes nothing.
Do
PR-03 · Mondraft 4,400
PR-03 · Tue4,800
committed = {"PL-0301":{qty:4800}} · drafts = {"PL-0301":{qty:"4400"}}The plan still reads 4,800 until you save.

Two values, two places, one identity. Cancel is a deletion, a failed save costs nothing, and the row can honestly say what the plan currently holds.

Don't

row 24,800
plan[0].qty = 4400 (typed straight in)Saving…

Canonical data mutated by keystroke and keyed by position. Cancel has nothing to restore, a failed commit leaves the plan showing figures MES never accepted, and one re-sort moves the edit onto a different press.

§05

Properties

PropertyOptionsWhat it decides
concurrencysingle · multiHow many items may hold a draft at once. single keeps the state model small and the user's attention on one row, and is the safe default; multi suits a planner making a pass down a column, and requires per-row state, per-row validation and per-row failure — all three, or it is single with a bug.

staleDraftPolicyblock · overwriteWhat happens when the item's committed revision moved after the draft was opened. block refuses the commit, shows both sets of figures and asks — correct wherever the other party's change may be load-bearing, which in a shared plan it always is. overwrite is only defensible where the edited fields cannot conflict in practice, and must still be a decision, not a silent last-write-wins.
postSaveDispositionexit · stayWhat the row does after a successful commit. exit returns to read and moves focus back to the row's own control; stay keeps the editors open with the draft re-based on the new committed values, for a user working down a column. Either way the save is announced and the row stops claiming to be a draft.
§08

States

StateWhat is trueWhat is displayed
readNo draft for this item.Committed values, an Edit control, no editors.
editingA draft exists and matches the committed values.Editors seeded from committed values, commit and cancel, and a statement that the collection is unchanged.
invalid draftThe draft breaks a rule. Still fully editable.The problem on the offending field, the rule that field must satisfy, and a commit that refuses without discarding anything.

stale draftThe item's committed revision moved under an open draft.Both sets of figures with their revisions, and the choice the staleDraftPolicy defines.

"Saving" and "saved" are not the same claim, and a row must never make the second while doing the first. An in-place editor that drops back to read state the moment the button is pressed has told the planner the plan says 4,400 when MES has not yet been asked — and if the commit then fails, the correction arrives against a row that already looks committed.

§09

Validation

  • Validation runs over the draft, before the commit. Not over the committed values, and not over a merge of the two.
  • Cross-value rules inside the item are evaluated coherently, against one snapshot of the draft: the quantity rule depends on the shift and the manning chosen in the same draft, so all three are read together. Evaluating each field against the committed values of its siblings produces errors that contradict what the user can see.
  • An invalid draft stays editable and stays whole. A refused commit clears nothing, closes nothing and moves nothing but focus, which goes to the first offending field.
  • The problem is attached to the field it belongs to — through Field's error, so the editor is aria-invalid and points at the message — and the rule stays visible beside it as a hint.
  • Where a rule spans fields, it is reported on the field the user can change to satisfy it, and states the other values it depends on: "Shift C with 1 operator makes 3,000. Over by 1,800." A rule reported on nothing in particular is a rule nobody can act on.
  • Validation is not a gate on typing. Errors may appear as the user works, but no keystroke is rejected and no editor is locked; the commit is the gate.

The message names no field, no rule and no numbers, and the refusal has reverted the row — so the planner's four keystrokes are gone and she cannot see what was wrong with them.

§10

Error handling

  • A failed commit preserves the draft, exactly as typed. This is the pattern's first obligation on failure: the work is the user's, and the failure was not theirs.
  • A failed commit leaves the collection unchanged, and says so in the collection's own numbers. "Nothing was committed: the plan still reads 4,800 pieces." A message that only says "save failed" leaves the planner unsure which figure MES now holds.
  • The unsaved draft is never presented as committed data. The row keeps a state that distinguishes them — and anything that reads the collection downstream keeps reading the committed values.
  • Retry operates on the draft as it is at the moment of retry, not on the values that failed. The user may have corrected them in between; retrying the old attempt discards a correction silently.
  • A conflict is not a failure. A stale draft has not been refused by the service — it has been overtaken. It reports both revisions and offers a choice, and it never overwrites without one under block.
  • An item withdrawn mid-edit ends the edit and keeps the explanation. The draft cannot be committed because its subject is gone; the pattern says which item left, why, and what the uncommitted figures were, rather than dropping the editor and the work in silence.
  • The collection never fails with the editor. A failed commit on one row leaves every other row readable and editable.
Do
PR-03 · Mon 08 Sep was not saved
The MES day plan refused the commit — the week lock is held by Anjali Deshmukh. Nothing was committed: the plan still reads 4,800 pieces, and your 4,400 is still in the row.
Retry saving PR-03 · Mon 08 Sep

Cause, consequence and the two figures kept apart — so the planner knows what the plan holds, what she typed, and that retry will send what she can see.

Don't
Couldn't save. Try again later.
PR-03 · Mon4,400

The row now shows 4,400 as though it were the plan, the draft is indistinguishable from committed data, and the next person to open the screen releases a quantity MES never accepted.

§12

Accessibility

  • Entering and leaving editing are perceivable. The row's state is stated in text, not only by the appearance of a box: a screen-reader user who cannot see the editors must be told the row is now editable and, later, that it is committed.
  • Focus moves into the first editor on entry, so the keyboard is where the work is; it never lands on the row's container.
  • Focus returns predictably on exit. After a commit under exit, or after a cancel, focus goes back to that row's Edit control — not to the top of the table and not to the document.
  • Every editor is named by its value and its row. "Planned quantity for PR-03 · Mon 08 Sep", visually hidden in the cell — a column of editors all called "Quantity" is unnavigable.
  • Validation messages are associated with their editor, through the Field that owns it, so the error is read on arrival at the control rather than announced into the void.
  • Refusals and failures are announced where the user is. A refused commit announces the problems and moves focus to the first one; a failed save announces as an alert, because the user's belief about what was saved is now wrong.
  • Row activation is never the only way in. Under the row entry policy the Edit control remains, because a click target on a table row is not operable by keyboard and not announced as anything.
§14

Content rules

  • Edit, save and cancel are three distinguishable actions, named as such and never abbreviated into one ambiguous control. Their accessible names carry the item: "Save the PR-03 · Mon 08 Sep slot".
  • While a draft is open, the row says what the collection still holds. "The plan still reads 4,800 pieces until you save" is the sentence that makes the draft model visible.
  • Failure copy states that nothing was committed, in the collection's units, before it explains the cause. "Not saved" first, mechanism second.
  • Cancel copy says what will be restored, not what will be lost — the committed figures are the thing the user is returning to.
  • A conflict names both parties' figures and their revisions, and labels the choices by what they do: "Save my figures over revision 5", "Discard mine and take the revision". Never "Overwrite?" alone.
  • Rules are stated as hints before they are stated as errors. "Multiples of 200" beside the field costs nothing and prevents the error it describes.

§17

Performance

  • The commit is guarded at the state transition, not by disabling the button: a second press arrives before the disabled attribute lands, and a double commit on a plan slot is a double release.
  • Each commit carries a request identity, and only the current one for that item may write canonical values or clear the draft — a response that arrives after a newer commit, a cancel, or the item's withdrawal writes nothing.
  • Typing is never gated on validation or on the network. Editors respond to keystrokes at once; validation is cheap and local, and anything expensive happens at commit.
  • The collection stays usable while a row saves. Only the saving row's controls are inert; sorting, filtering and — under multi — other drafts continue.
  • A slow commit is reported in the row it belongs to, with progress naming the item. A page-level spinner over a per-row commit hides which row is waiting.
§18

Edge cases

ConditionRequired behavior
Item removed during editingEditing ends, the draft cannot be committed, and the pattern states which item left, why, and what the uncommitted figures were. Never a silent disappearance of the editor.
External update to the item being editedThe draft is untouched; the conflict surfaces at commit under staleDraftPolicy. Live-patching a draft from a refresh destroys the user's work without asking.
External update to other itemsApplied normally. Other rows refreshing is not a reason to disturb an open draft.
Filter or sort hides the item being editedThe draft is kept and reported — "1 edit in progress on a slot this filter hides" — never discarded because its row went off screen.
Repeated save activationThe second activation is refused while the first is in flight. No queue, no second commit.
Save resolves after the editing context changedDiscarded if it belongs to a superseded commit, a cancelled draft or a withdrawn item; canonical values are written only for the commit that is still current.
Entering edit on a second item under singleRefused, with the open item named and focus returned to it. Not a silent discard of the first draft.
Draft identical to committed valuesCommitting is permitted and harmless; cancelling is equivalent. The pattern does not claim a change it cannot see.
Navigating away with an open draftOut of the pattern's control to prevent, in its obligation to warn: an unsaved draft is announced as unsaved, and the product decides whether to guard the exit.
§20

Implementation notes

  • Hold three things separately: the item's identity, the committed values, and the draft. The draft map is keyed by identity — { 'PL-0301': { qty, shift, manning, baseRev } } — never by index, and never a single "editing buffer" shared between rows.
  • Never write canonical data before the commit succeeds. This one rule delivers cancel, failure recovery and the honest row state for free; every alternative reconstructs them badly.
  • Stamp the draft with the revision it was opened against and compare at commit. Without a revision (or an ETag, or a timestamp the service honours) there is no way to detect a stale draft, and staleDraftPolicy is unimplementable.
  • Derive the row's state, do not store it. Read, editing, invalid, saving, failed and stale are all computable from the draft, the validation result and the in-flight commit; a stored isEditing flag is what leaves a row editable after its item disappears.
  • Validate a copy of the whole draft in one function, returning problems per field. Per-input validators that close over stale siblings are the usual source of contradictory cross-value errors.
  • Tag each commit with a monotonic request number and check it — plus current membership — before writing anything.
  • Keep focus management with the transitions, not in the editors: entry focuses the first editor, refusal focuses the first problem, exit focuses the row's own control. Editors that grab focus on mount fight the pattern.
  • Do not reuse the collection's row objects as drafts. Copy the values out; a draft holding a reference into the collection is a mutation waiting for a re-render.
