Interaction pattern

Evidence attachment

Some records are only as good as the files behind them. A calibration without its certificate, a nonconformance without its photographs, a receipt without its test report — the record can be saved, and it should not be, because downstream the reading will be trusted as if the evidence were there. This pattern specifies the relationship between an attachment set and the commit it gates: when the files go up, what the commit is allowed to do while they are moving, what survives a failure, and who may take evidence away once the record is closed.

§01

Purpose

Required

Bore gauge GG-2214 comes back from Pune Metrology Services on 2026-09-07 (IST) with a certificate. Meera Nair opens CAL-2026-0912, types the certificate number, drops the PDF and the readings CSV, and presses Return GG-2214 to service — and at that instant the certificate is at 64%. If the record posts anyway, the gauge is back on final inspection with a certificate number that points at nothing, and the next forty lots are measured on the strength of a file that never arrived. The gate is the pattern.

Use it when a record's validity depends on files the user supplies, and committing without them would be believed.

Appropriate

  • Evidence that substantiates a claim on the record — a calibration certificate, an inspection photograph, a material test report, a signed deviation.
  • A commit that must wait for, or account for, files still in flight.
  • Records that are later read by someone who was not there, and who will treat the record as complete.

Not this pattern

  • A file that IS the transaction. A supplier catalogue whose rows become item-master records is bulk data import: the file is consumed rather than kept, and the contract is a column mapping and a dry-run verdict rather than a gate on a set’s status.
  • Optional decoration. A profile photo, a nice-to-have diagram. If the record means the same thing without the file, there is no gate and no pattern — just a FileUpload in a form.
  • Importing a file to be processed. A BOM CSV that becomes rows is asynchronous action with a result: the file is an input, not evidence, and nobody keeps it.
  • The set's own mechanics. Which files are allowed, how one row shows progress, what "finished" means for the set — all owned by FileUpload and its parts. This pattern starts where that contract ends: at the commit.
  • A document library. Browsing, versioning and retention of files that outlive any one record is a different problem with a different shape.
§02

Anatomy

RoleComponentRequirement
The evidence setFileUploadRequired, exactly one per record. It owns selection, validation, per-file state and the set's aggregate status; this pattern consumes that status and never reimplements it. Two sets on one record are two records' worth of evidence, or a table.
The commitButtonRequired. Its label names the consequence on the record ("Return GG-2214 to service"), never the file operation ("Upload"). It is gated by §04 and states its blocking reason in text beside itself.
The record's own fieldsField + controlsRequired where the evidence substantiates a value — a certificate number, a disposition, a measured result. The gate is the conjunction of these and the set: either alone is not a complete record.
Failure of the commitAlertRequired when the post can fail. Persistent, placed with the record, and distinct from any per-file error — see §10.
Retention noticeField hint, or textRequired once the record is committed and removal is closed: the interface must say why the evidence can no longer be taken away.

Nothing else is part of the pattern. In particular there is no count badge, no total-size readout and no separate "evidence complete" indicator: the set's rows are the count, and the commit button's state is the indicator.

§03

Flow

  1. Enter. The record opens in draft. If evidence is required, the commit is blocked from this moment — but the interface does not yet complain, because nobody has done anything (§09).
  2. Attach. Files are picked or dropped. Refusals are reported by the set, naming the file; accepted files enter the set as queued.
  3. Upload. Either immediately (onArrival) or deferred to the commit (onSave) — the choice is §05, and it changes what the operator is waiting for and what they may close the tab on.
  4. Fill the record. Runs concurrently with uploading; the two never block each other. Typing a certificate number while a PDF uploads is the normal case, not an edge one.
  5. Commit. Permitted only when the set is settled and the record's own fields are valid. Under onSave the first press starts the uploads and does not post; the post follows when the set settles, and the button says so.
  6. Resolve. Committed, failed, or unknown (§10). A committed record moves removal into whatever §05 allows, and the evidence stops being editable by default.
  7. Leave early. Navigating away mid-upload abandons the set, and the pattern must have said so before it happened — see §18.

Branch that matters: a failed file. The set reports failed, the commit stays blocked, and the operator has two ways out — retry the file, or remove it and commit without it, which is only a route if evidence is optional. A pattern that offers neither has stranded the record.

§04

Behavior

ContractRule
Commit gateThe commit is enabled only when the set's status is idle and the record's own validation passes. busy and failed both block; invalid blocks when evidence is required. This conjunction is the pattern's central guarantee.
Blocked, with a reasonA disabled commit always carries its reason in adjacent text — "Waiting for the evidence to finish uploading", "One file did not upload" — never a tooltip, never silence.
One commit at a timeThe commit guards against a second activation while in flight. Two posts of one calibration double-book the gauge.
Evidence and fields are independentUploading never disables the record's fields, and editing a field never interrupts an upload.
Commit does not re-uploadFiles already complete are referenced by id at commit. A retry of a failed commit re-posts the record, not the evidence.
Removal after commitClosed by default. Where a role may still remove, the removal is itself a recorded event on the record — evidence that vanishes without a trace is worse than evidence that was never attached.

Do

  • Block the commit while the set is busy, and say what is being waited for.

The operator can see the bar; what they cannot see is whether the button will wait for it.

Don't

  • Let the commit fire at 64% and let the server sort it out.

The record posts, the reference dangles, and the gauge is trusted. This is the failure the pattern exists to prevent.

§05

Properties

PropertyOptionsWhat it changes
uploadTimingonArrival · onSaveonArrival: bytes move as files are picked, so the commit is usually instant and an abandoned draft leaves orphaned files to reap. onSave: nothing leaves the browser until the operator commits, so the record and its evidence succeed or fail together — at the cost of a commit that is now slow, and a first press that starts uploads instead of posting. Choose by whether an orphan or a slow commit is the worse problem on that surface.
removalAfterCommitnever · roleGatednever: once posted, the evidence is part of the record. roleGated: a named role may remove, and the removal is recorded. Nothing else is offered — an unrecorded post-commit removal is not a supported option.
evidenceRequiredrequired · optionalrequired: an empty set blocks the commit, with the message deferred until the set is touched or a submit is attempted. optional: an empty set commits, but a failed or in-flight file still blocks — a file the operator tried to attach is never silently dropped just because evidence was optional.

All three are reachable as tweaks in the reference implementation, every §08 state is reachable there, and so are the two §18 boundaries — leaving with an uncommitted set, and a record closed elsewhere. That is what lets this spec claim zero open items: the standard's rule is that a declared policy with no way to see it behave is an open item, not a footnote, and every policy declared here has a button or a tweak behind it.

The set's status and the record's state are two different things, and conflating them is the most common implementation error here: a set that is idle says the files are settled, not that the record is posted. The commit reads both.

§09

Validation

  • Required-evidence status is immediate; its message is not. An empty required set makes the commit invalid from the moment the record opens — the button must never look pressable when it is not — but the sentence "A calibration certificate is required" waits until the operator has touched the set or attempted a submit. A record that reddens on arrival teaches people that red means nothing.
  • Set-level and file-level messages never duplicate. Why that file failed belongs on its row; that the set as a whole is unsatisfied belongs in the field error.
  • Refusals are always named. Three dropped, one refused, and the message says which one and which rule.
  • The record's own validation is independent. A missing certificate number and a missing certificate are two failures with two messages, in two places, and fixing one must not clear the other.

Do

  • Defer the required message until the set is touched, or a submit is attempted.

The gate is honest from the first render; the accusation waits until there is something to accuse.

Don't

  • Render "A certificate is required" on an untouched record.

This was a real defect: the composite shipped doing exactly this, and its first consumer found it (FileUpload §06).

§10

Error handling

Three failures, deliberately separated. Merging any two of them is how an operator ends up re-posting a record that already exists.

FailureWhere it showsWhat is guaranteed
A file did not uploadThe row, with the reasonThe rest of the set is untouched; the row offers Retry; the commit stays blocked. Removing the file is a legitimate resolution only where evidence is optional.
The commit failedAlert with the recordNothing is lost: field values, the set, and every uploaded file's state all remain. The commit is offered again, and it does not re-upload what already arrived.
The outcome is unknownAlert, warningThe post left and nothing came back. The interface must claim neither success nor failure, must not offer a blind retry, and must tell the operator where to check — a second post of one calibration double-books the gauge.

Do

  • Say "Outcome unknown — check CAL-2026-0912 before posting again."

It names the record and the next action, which is the only useful thing an interface can do when it does not know.

Don't

  • Show "Something went wrong" with a Retry button.

A retry on an unknown outcome is a coin flip between a duplicate record and nothing.

§12

Accessibility

  • Blocked commits announce their reason. The reason sits in text next to the button, in the DOM next to the button — not in a title and not in a tooltip, both of which are unreachable to a keyboard user and inconsistent on touch.
  • Arrivals and refusals are announced once. The set owns a polite live region ("2 files added, 1 refused"); the pattern must not add a second one for the same event.
  • The outcome is announced where it happened. A commit failure is an Alert adjacent to the record, and focus moves to it — the operator pressed a button and something must answer at the button, not at the top of a scrolled page.
  • Removal does not strand focus. Owned by FileUpload; the pattern's duty is not to remount the set around it, which would throw focus to the body anyway.
  • The retention notice is text, not a disabled control's implication. "The record is posted; its evidence cannot be removed" is a sentence. A greyed-out remove button is a guess.

The commit names its effect on the record, never on the files. "Upload" promises the wrong thing twice: it suggests the files are the point, and it suggests pressing it is what moves them.

§18

Edge cases

  • Leaving mid-upload. Under onArrival the bytes are already gone but the record is not saved, so the files are orphans; under onSave nothing has left. Either way the surface warns before unload while the set is non-empty and uncommitted, and the copy says which of the two is true — the wording changes with the policy, because “you will lose your files” and “you will leave files nobody owns” are different warnings. Reachable in the reference implementation: a beforeunload guard while the set is dirty, plus a harness button that shows the same decision inline, since an iframe cannot raise the browser's own dialog.
  • Double commit. Guarded in the pattern, not on the server alone. A double-posted calibration is visible to the operator as one press.
  • The same file twice. Not refused — a two-page certificate legitimately arrives as two identically named scans from some devices. The set shows both; deduplication is a product decision, not an interface reflex.
  • Evidence for a record someone else has closed. The gauge came back to service while the tab was open. On commit the record is refused as stale — not merged, not silently overwritten — and the refusal says who closed it and when, keeps the operator's evidence and certificate number, and sends them to reload and check what is already attached before posting again. A blind second post here is the double-booking of §04 by another route. Reachable in the reference implementation via the harness.
  • Every file failed. A set of four failures is not four problems: the field error says one thing ("No evidence uploaded. Retry, or attach it after the network is back") and each row keeps its own reason.
  • More than about eight files. The set stops being a stack and becomes a table; the gate in §04 is unchanged, and that is the point — the contract is not a property of the layout.
§19

Anti-patterns

  • Committing on the strength of a filename. A row that exists is not a file that arrived. Read the set's status, never its length.
  • Uploading on select and calling it saved. The evidence being in the store does not make the record true; only the commit does, and until it happens the files are orphans waiting to be reaped.
  • A set-level spinner in place of per-file bars. One spinner over four files hides which one is stuck.
  • Silently dropping a failed file when evidence is optional. Optional means the operator may choose not to attach — not that the system may discard what they tried to attach.
  • Removing evidence after commit with no record of it. Worse than never attaching it: the record now claims a certificate that someone quietly deleted.
  • Using this for file imports. An import's file is consumed and forgotten; evidence is kept and re-read. Different lifetimes, different pattern.
§20

Implementation notes

  • The queue lives in the surface, at record level. Not inside the set, and not inside a row: the commit needs to read every entry's state, and a queue held lower cannot be read by the button that depends on it.
  • Entry ids must survive re-render and be the thing the commit posts. The record references uploaded files by id; an id regenerated on every render turns a retry into a new file.
  • One AbortController per entry. Cancel must stop the bytes, not just the row — see FileItem §14.
  • Derive the gate; never mirror it. Keep the set's status as a derived value (deriveStatus), not a second copy in state that can disagree with the rows the operator is looking at.
  • Under onSave, the first press is not the post. It starts the uploads and returns; the post fires when the set settles. Say so on the button, or the operator presses it twice.
  • Progress comes from bytes. XMLHttpRequest.upload.onprogress or a progress-reporting stream. A timer-driven bar reports 100% for an upload that died, which defeats the gate this whole pattern is built on.
