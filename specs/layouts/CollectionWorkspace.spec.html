Layout template

Collection workspace

Nikhil Bhagat opens the instrument register once a week and does five different things to it: finds the gauges due, narrows to the machine shop, sorts by days overdue, ticks eleven of them, books the lab for all eleven. Not one of those is about a single gauge. This frame is the reusable surface for exactly that — finding, refining, selecting, manipulating and acting on a collection — and its whole discipline is keeping the controls that act on the collection structurally separate from the items in it, so that at any moment a user can tell what a control will touch.

§01

Purpose

Unconditional

Provide a reusable work surface for finding, refining, selecting, manipulating and acting on a collection, while keeping collection-level controls structurally distinct from the items themselves. The frame is right when one collection is the screen: the user arrives to do something to that set, the work is done through the controls around it, and an individual member — when it is opened at all — is opened somewhere else.

The distinctness is the point. Three scopes coexist on this screen: actions on the collection (add, import), actions on the current refinement (search, filter, sort), and actions on a selected subset (schedule, recall, withdraw). A user must be able to tell which is which from where the control sits, before reading its label. Every failure of this frame is a scope the user guessed wrong.

Appropriate

  • A register maintained over time: instruments, items, suppliers, customers, work centres.
  • A queue worked in bulk: goods receipts to post, requisitions to approve, certificates to import.
  • Any screen where the answer to "what am I looking at?" is one collection, and members open as their own pages.

Not this layout

  • Selection structurally controls a simultaneously visible detail region. Use master-detail — that frame owns selection identity, the detail's four states and the position-preserving return, and none of it is specified here.
  • Several independent modules, not one collection, are the composition. Use dashboard.
  • Sequential reading content. Use single column.
  • Two substantial surfaces compared. Use split view.

Applicable interaction patterns. Primary: none — the frame hosts collection work rather than implying one contract. Supported: search results, collection refinement, bulk selection and action, collection editing, direct manipulation of order, bulk data import. Most real workspaces host three or four of these at once; the frame's contribution is that each one's controls have a place to live where their scope is legible.

§02

Anatomy

Unconditional
#RegionRequirementWhat it owns
1Collection headerRequiredThe heading and the context that says what this collection is and as of when, plus the actions whose scope is the whole collection — add a member, import members. Owns the h1. A selection-scoped action never appears here, because position is how scope is read.
2Collection controlsRequiredSearch, refinement, and scope or sort controls where the collection component does not carry them. Structurally above and outside the collection surface, and never interleaved with items. Each control names the collection it affects (§08).
3Selection and action regionConditionalActions on the selected subset, where selection is supported. It sits between the controls and the collection so that appearing does not move what the user is reading, and its label states how many members it will act on. Present-on-selection or present-and-disabled is a declared property (§03) — never both behaviours on one product.
4Collection surfaceRequiredThe collection itself — Table, List, Tree, a card or grid composition, or SortableCollection. The dominant region at every width. Which component it is does not change the frame (§12).
5Collection footerConditionalPagination, or the supplementary status that makes the collection legible — how many of how many, as at when. Bound to the collection surface, not to the page, and reachable without scrolling the collection body past it.
6State regionsConditionalLoading, empty, no-matches and failure presentations, which occupy the collection surface and its footer in place of them (§06). They are regions, not overlays: the controls above stay present and usable, because a user whose refinement returned nothing needs the refinement controls most.

What the frame does not own: anything inside the collection surface. Row structure, columns, sorting mechanics, inline editing, drag handles, per-item actions and the collection's own keyboard model all belong to the collection component and to the patterns in play.

§06

States

Conditional — included: five states change which structural region occupies the workspace

These qualify as layout states because each one decides which major region is present. They are not the collection component's states aggregated: the frame decides whether region 4 exists at all right now, and what stands in its place.

StateWhat occupies the workspaceContract
loading collectionA placeholder in place of regions 4 and 5The header and controls stay present. Reserve the collection's height so the workspace does not jump when rows arrive, and never blank the controls the user is about to use.
empty collectionAn empty state in place of region 4Nothing exists yet. It offers the collection-scoped way out — add the first member, import a set — and it is a different screen from no-matches. Conflating the two tells a user with a stray filter that their register is empty.
no refinement matchesAn empty state in place of region 4, controls untouchedMembers exist; this refinement excludes them. It says what was searched and refined, how many the collection holds, and offers to clear the refinement. The controls must remain exactly as the user left them.
selection activeRegion 3 in addition to everything elseThe only additive state: nothing is replaced, and the collection stays fully visible. Selection is held by identity, so it survives refinement and paging; where a selected member is no longer visible, the frame says so rather than silently dropping it.
collection-level failureA failure presentation in place of regions 4 and 5The collection could not be read. Nothing is shown, because nothing is known — never a stale collection presented as current. The refinement is preserved and the retry is offered where the collection was. Recovery is recoverable failure's contract; the frame's part is that the failure occupies the collection's region and no other.
§07

Keyboard

Conditional — included: regions appear and disappear, and focus order is the frame's
  • The frame invents no collection-navigation semantics. Arrowing rows, expanding tree nodes, moving items, entering and leaving a cell editor, typeahead — all belong to Table, List, Tree, SortableCollection and the patterns. This section exists only because regions come and go.
  • A region appearing does not move focus. Ticking a row raises region 3; focus stays on the control the user just used. The new region is reachable by ordinary forward movement from there, which is why it sits above the collection and not at the foot of the page.
  • Focus order follows the regions' order at every width — header, controls, selection region, collection, footer — including when the refinement moves into a panel: the trigger keeps the controls' place in the order and the panel's contents follow it.
  • A region disappearing hands focus back deliberately. When the last selection is cleared and region 3 leaves, focus goes to the control that cleared it or to the collection — never nowhere, which is what happens by default and drops the user at the top of the document.
  • State regions are focusable destinations, not traps. When a state region replaces the collection, its own action (clear the refinement, retry, add the first member) is in the focus order where the collection was.
§08

Accessibility

Unconditional
  • Every control identifies the collection it affects. "Search the instrument register", not "Search"; "Actions on the selected instruments", not "Actions". The frame is the only thing that knows there is one collection here and what it is called, and a control named for its mechanism is unusable to anyone who cannot see what it sits above.
  • Regions are labelled and heading levels run down the document. The header owns the h1; a titled region starts at h2. The primary search may publish a search landmark named for the collection; a second unnamed one on the same page is worse than none.
  • The selection region does not relocate focus disruptively (§07), and it reports its scope in words — the count and the noun — not by a highlight the user must infer.
  • Loading, empty and failure states communicate through their components — Skeleton, EmptyState, Alert — with the politeness their own specs define. The frame adds only that the replacement is announced as a change to the collection region, and that the surrounding controls' names still describe the same collection.
  • Selection state is exposed on the members themselves, not carried by row shading, and a select-all control states its own scope: this page, or the whole refined collection. The two are different promises and only one of them is usually true.
  • Sort and refinement changes are perceivable without sight of the collection. Where the frame owns the sort or scope control, its current state is legible from the control, and the resulting count is stated in text.
§11

Responsive

Unconditional
  • Expanded. Controls may occupy one coordinated horizontal row, and the collection may use its richer multi-column presentation.
  • Constrained. Controls wrap or stack ahead of the collection — never below it, never interleaved — and non-essential simultaneous controls may move into a Popover or Drawer. Search stays directly visible: it is the control most likely to be the reason the user opened the screen.
  • The collection remains the dominant region at every width. A workspace whose controls take more vertical space than its collection has inverted itself.
  • Changing Table to a list or card presentation is a component-level responsive decision, not a new layout. The frame is unchanged by it, and no product may fork this template because its collection renders differently on a phone (§12).
  • Region order is preserved in every form, in the DOM and on screen: header, controls, selection region, collection, footer.
  • The selection region stays reachable when the collection scrolls. Pinning it is permitted; covering the last row is not, and neither is a floating bar that hides the footer's own controls.

Controls after the collection can only be found by scrolling past what they are meant to narrow. And a card presentation is not a new frame: forking "table page" and "card grid" doubles the specifications and halves the consistency.
§12

Anti-patterns

Unconditional
  • Separate "table page", "list page", "card grid" or "gallery" templates derived from the collection component chosen. One frame, many collection surfaces. This is the misuse the frame exists to prevent, and it is the most common one.
  • Using it where selection structurally controls a simultaneously visible detail region. That is master-detail; adopting this frame instead leaves you without a detail state model.
  • Using it where several independent modules are the composition. That is dashboard — and summary tiles above a collection do not make a dashboard either.
  • Mixing the three scopes in one action strip, or putting a selection-scoped action in the header (§02).
  • A bulk region that displaces the collection, covers the last row, or appears and takes focus with it.
  • One empty state for both "nothing exists" and "nothing matches". Two different screens, two different ways out (§06).
  • Blanking the controls while the collection loads, or showing a stale collection during a failed read.
  • Refinement that clears the selection silently, or a select-all whose scope — this page or the whole refined set — is not stated.
  • Controls interleaved with items — a filter row inside the collection, a sort control in a column header that also acts on other collections — dissolving the distinctness in §01.
  • Growing a detail pane into the workspace because one member needed more room. At that point the screen is master-detail and should be specified as such, not improvised here.
§13

Implementation notes

Unconditional
  • One vertical order, built with Stack inside Container; regions 4 and 5 sit on one Surface so the collection and its pagination read as a single object. Use Toolbar for each action group so that each set of controls carries its own accessible name and one tab stop, and Grid only inside a region.
  • Selection lives in the frame, keyed by member identity — never by row index or page position. That is what lets selection survive sorting, refinement and paging (§06), and it is what makes a bulk action's count trustworthy.
  • Keep three action scopes in three places in the DOM. Resist the convenience of one action array rendered in one strip: the scope distinction in §01 is carried by position, and it disappears the moment the strips are merged.
  • Refinement state and page belong together and belong in the URL where the workspace is shared, bookmarked or returned to from a member's page. Restoring a workspace means restoring query, refinement, sort, page and scroll — a member's page returning to page 1 unfiltered is the same defect master-detail names in its §12.
  • Give the collection surface a bounded height only if you need it to scroll independently, and then keep the footer outside the scrolled area. Never nest a scrolling collection inside a scrolling page: two scrollbars on one collection is unnavigable with a trackpad and impossible with a keyboard.
  • Reserve the collection's height across state changes. Loading, empty, no-matches and failure all occupy the same box; if they do not, every read reflows the screen and the controls move under the pointer.
  • The state regions are mutually exclusive and evaluated in one place. Failure, then loading, then empty, then no-matches, then the collection — decided once, so two states can never render together.
  • Every region needs min-width: 0, and a wide collection scrolls horizontally inside its own surface rather than widening the workspace.
