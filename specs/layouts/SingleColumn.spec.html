Layout template

Single column

Most screens in a plant system are one thing after another: read the request, fill the request, submit the request. A single column is the frame for exactly that — content whose hierarchy is a vertical reading or task sequence, with no lateral region because none is needed. It is the system's default frame, and the discipline in it is negative: what it refuses to add when the viewport gets wide, and the moment at which persistent side content means a different layout has been adopted rather than this one stretched.

§01

Purpose

Unconditional

Provide the default structure for content whose hierarchy can be expressed as a single vertical reading or task sequence. Sandeep Kulkarni raises MWR-2026-0488 against press line P-2: he identifies the asset, describes the fault, states the impact on this shift, routes it, submits it. There is nothing he must hold in view while doing it, and no second body of content he moves between — so a lateral region would assert a hierarchy the work does not have. The layout is appropriate precisely when that is true.

Appropriate

  • A task completed in order: raise, edit, review, submit.
  • Reading-oriented content — a specification, a procedure, a shift report.
  • A record whose fields are read top to bottom, with reference material that may sit subordinate in the same flow.
  • Any screen where a second region would be filled only because the space exists.

Not this layout

  • Continuous lateral reference. If the inspector must keep the drawing tolerances in view while typing measurements, that is a sidebar frame, not a taller column.
  • Two bodies of content moved between. A queue and the record it selects is list–detail.
  • Parallel figures compared at a glance. Shift output across four lines is a dashboard grid.

Applicable interaction patterns. Primary: none — this frame hosts patterns, it does not imply one. Supported: validated submission, explicit save, recoverable failure, evidence attachment. Each brings its own contract; the layout adds only a place to put the commit (§02, region 4) and one for the failure to be stated where the user is looking.

§02

Anatomy

Unconditional
#RegionRequirementWhat it owns
1Page regionRequiredThe outer Container or Surface. Owns content width, alignment and the page gutter — see §03. Exactly one; never nested inside another page region.
2Header regionOptionalWhat the page is and where it sits: Heading level 1, supporting Text, record metadata, Breadcrumb, and header-level actions that act on the page rather than complete the task. Absent on a screen reached with its subject already stated.
3Primary content regionRequiredA vertical Stack of sections. Owns section order, the vertical rhythm between sections, and the heading level each section takes. The frame does not care what a section contains.
4Action regionOptionalTerminal actions that complete or abandon the sequence, or the same actions contextually anchored to the viewport foot. Owns their position and grouping only — availability, commit and failure belong to the pattern in play.
5Supplementary regionOptionalContent that stays subordinate in the same vertical flow: related records, reference notes, history. Its subordination is the contract — the moment it must be seen at the same time as region 3, it is not this region.

Regions appear in this order and nothing sits between them. Name them by role, not position: on the reference implementation the action region moves to the viewport foot under one property and it is still region 4.

Open requests already on P-2 are reference: useful before submitting, never needed at the same instant as the field being typed. Below the flow, they stay reference.
Don't — lateral, so no longer subordinate
3 · primary

Put it beside the form and it is co-equal, permanently in view, and competing for the reading order. That is a sidebar frame — adopt one, do not widen this.

§08

Accessibility

Unconditional
  • DOM order is the reading order, and matches the visual order. This frame makes that cheap — there is one axis and no lateral region to reorder. Nothing in it may use visual order to reposition a region against its place in the document.
  • Heading levels express the section hierarchy, independent of spacing. Region 2 carries the single h1; each section in region 3 takes h2; nesting continues from there without skipping. A section given more air is not thereby more important, and a visually small heading keeps its level — Heading separates level from size for exactly this.
  • Landmarks only where they are semantically warranted. One main around regions 3 and 4. Region 2 is a header only if it is the page header rather than the first block of content; region 5 takes aside only when it is genuinely tangential, and then it carries an accessible name. Landmarks on every region make the landmark list useless.
  • The anchored action region must not obscure content. When region 4 is anchored to the viewport foot, the page reserves its height at the end of the flow, so the last section and the focus ring of the last control are reachable and visible.
  • Focus order crosses no region boundary the frame invented. Focus proceeds through regions in document order; the layout moves focus nowhere and traps it nowhere. Anything that does — a dialog, a failure summary taking focus — is the pattern's contract, not this frame's.
§11

Responsive

Unconditional

The fundamental relationship does not change at constrained widths, because the template already follows one axis. There is no stacking transition to specify: the frame is already stacked. What changes is measure and gutter.

  • Narrow. The gutter reduces to the smallest step and the bounded width becomes the available width. Sections keep their order and their rhythm. Nothing collapses, nothing becomes an overlay.
  • Expanded. Increase the margins, or increase the bounded content width by one step where the content earns it. Do not introduce columns at a breakpoint: a second column that exists only above 1200px is content the product does not have a hierarchy for.
  • Adoption boundary. A transition to persistent lateral content is the adoption of a sidebar layout, not a single-column breakpoint. If wide viewports get a side region and narrow ones do not, two layouts are in play and the responsive rules belong to the one that has the side region.
  • The anchored action region (§03 has it as a composition choice) is the one behavior that may legitimately differ by space: anchored where the sequence is long enough that the actions leave the viewport, terminal where it is not. Whichever is chosen, it is the same region with the same contents.
Do — margins absorb the width
At 1600px the measure stays readable and the space becomes margin. The frame is unchanged, so nothing has to be re-learned between a desk and a tablet on the shop floor.
Don't — stretch because the space is there
A 150-character line of fault description is a scan, not a read. Width is not a resource that must be spent; contentWidth: full is for a wide table, not for prose.
§12

Anti-patterns

Unconditional
  • Using it where reference material must stay in view. If the user is expected to consult supporting content continuously while working in the primary region, use a sidebar frame. Pushing that content to the foot of a single column means it is read once, or never.
  • Stretching reading-oriented content across an arbitrarily wide viewport merely because the space is available.
  • A second column introduced at a breakpoint. Content that appears beside the primary region above some width, and below it otherwise, has two hierarchies and belongs to a layout that owns one.
  • Spacing used as hierarchy. A section separated by more air but sitting at the same heading level reads as more important to sighted users and identical to everyone else.
  • More than one page region. A Container inside a Container gutters twice and quietly narrows the measure by two steps.
  • The supplementary region carrying required content. Anything the user must act on is a section of region 3. Subordinate placement is a claim that it can be skipped.
  • An anchored action region that overlaps the last section instead of reserving its height — the commit covers the field the user is trying to fix.
§13

Implementation notes

Unconditional
  • Build it from Container, Stack, Box, Surface, Spacer, Divider, Heading and Text. Any core or composite component may occupy a section without changing the template — the frame has no knowledge of what is inside a section, and adding one must never require touching it.
  • Space comes from the parent gap, never from margins on children. One Stack owns region 3's rhythm; a section that sets its own top margin breaks the single rhythm §03 promises and cannot be reordered safely.
  • One page region, gutter applied once. Container owns the gutter and the cap; sections inside it use padding, not their own container.
  • No scroll container of its own. The page scrolls; the frame introduces no nested scroll region. A section whose content overflows either paginates internally (its component's contract) or the section grows.
  • Sections must survive min-width: 0. Any grid or flex track inside a section needs minmax(0, 1fr), or a wide table inside it will push the column past the bounded measure and defeat contentWidth.
  • The anchored action region is position: sticky at the foot of the page flow, inside the page region so it inherits the same width and alignment, with its height reserved at the end of region 3. It is not fixed positioning, and it does not leave the document order.
  • The frame holds no state. Nothing in this layout persists, collapses or remembers. If a screen needs a region to collapse and stay collapsed, it has outgrown this template.

Omitted, with reasons — §04 Variants: the frame has one structural form; the bounded/fluid and terminal/anchored choices are properties and composition, not variants. · §05 Sizes: there are no frame-level size classes; measure is contentWidth in §03 and everything else comes from the spacing and density tokens. · §06 States: the frame holds no state — no region collapses, nothing is remembered, and a section's own loading or empty state belongs to the component in it. · §07 Keyboard: the layout creates no keyboard relationship between regions and moves focus nowhere; every control in it is operated under its own component's contract. · §09 Motion: no structural change occurs, so there is nothing to make legible. · §10 Content rules: the frame constrains no content beyond each region's stated purpose in §02; measure is a property, not an editorial rule. · §14 Developer notes: nothing technical remains once §13 is written — no slot API, no routing or persistence responsibility, no per-region data boundary.
