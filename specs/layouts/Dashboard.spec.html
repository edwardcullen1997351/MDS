Layout template

Dashboard

At 07:15 five people stand at one screen for eleven minutes: the press-shop head, the quality manager, the maintenance head, the planner and the shift supervisors. None of them reads it top to bottom. Each scans for the module that is theirs, then for whatever is red, then leaves. This frame exists for that eleven minutes — several independently meaningful modules held simultaneously so that status can be scanned, compared and left behind, with a route into the depth when a number turns out to matter. It is a multi-module structure, not a two-column page that happens to contain cards, and the difference is that the frame owns how prominence is distributed.

§01

Purpose

Unconditional

Provide a simultaneous overview of several independently meaningful information modules, prioritising rapid scanning, comparison, status awareness, and access to deeper information. The frame is right when a reader arrives without a task, leaves with an assessment, and the modules they scan are answerable in their own right — each one a fact about the plant that stands up alone.

Two tests, both required. Multiplicity: there are several modules and no single one is the task surface — remove any one and the screen is still worth opening. Independence: each module means what it means without its neighbours; nothing is understood only because of what sits beside it. A screen that fails multiplicity is a single-purpose page with decoration; a screen that fails independence is one document broken into boxes.

Appropriate

  • A shift-handover or morning-meeting screen: output against plan, OEE, open nonconformances, overnight breakdowns, material shortages, despatch adherence.
  • A role's standing overview — the maintenance head's assets, backlog, spares and MTTR — where each module belongs to a different system.
  • Any screen whose job is to tell several different readers, quickly, whether their area needs them today.

Not this layout

  • Sequential content that happens to be in cards. Use single column: an ordered read is not a scan.
  • One collection is plainly the task surface. Then the screen is a collection workspace, or master-detail if a member is worked beside it — the summary tiles above a queue do not make the queue a dashboard.
  • A stepwise task with a prescribed sequence. A grid asserts that order does not matter; a staged task asserts the opposite.
  • Two substantial surfaces compared. That is split view.

Applicable interaction patterns. Primary: none — the frame implies no sequencing or commit contract of its own; it hosts whatever its modules do. Supported: search results and collection refinement where a module or the shared controls narrow what is shown, asynchronous action where a module starts work that outlives the glance, and recoverable failure because on a screen of eight independent reads, one of them failing is a normal Tuesday and must be survivable in place.

§02

Anatomy

Unconditional
#RegionRequirementWhat it owns
1Dashboard headerRequiredThe heading and the context that makes every figure below readable — which plant, which period, as of when. Optionally the shared controls (scope, period, area) whose reach is the whole grid. Owns the h1. Nothing that is really one module's business belongs here: a control in the header is read as governing everything, and that reading must be true (§03).
2Module gridRequiredThe column structure, each module's span, and the order the modules are authored in. It distributes prominence: which modules are in the first viewport, which are full-span, which sit three to a row. This is the frame's whole substance — a dashboard's design problem is composition, not decoration.
3Module contentRequiredPer module: a heading that names what the module is about, the information itself, and local actions where the module needs them. Each module is independently comprehensible — its own heading, its own scope stated when it differs from the header's, and no meaning borrowed from whatever happens to sit next to it. Its own loading, empty and failure treatments are the module's business, not the frame's.

Three regions, and no fourth. A dashboard has no place for a persistent lateral region, a detail pane or a footer band of actions: a lateral region beside a grid is sidebar plus a grid inside it, and a detail pane fed by clicking a module is master-detail. Both are legitimate screens; neither is this frame, and conflating them produces a grid whose modules are secretly a collection.

What a module contains — table, list, figures, meters — is composition, not a property of this frame. Nor is refresh: how often a module's data is re-read belongs to the module and its source system.

§08

Accessibility

Unconditional
  • Every module carries a real heading, and the levels form one outline. The header owns the h1; each module's title is an h2, and anything inside a module starts at h3. A module titled only by a graphic, a figure or a colour is unreachable by heading navigation — which is how most people who cannot scan visually use a screen of eight modules.
  • Modules are named regions. A titled module is a labelled section; an untitled box is not a region and must not pretend to be one.
  • DOM order stays logical when the grid changes visual placement. Spans may change with available space; document order may not. Never use order, grid-area or auto-placement tricks to move a module visually without moving it in the document — a reading order that disagrees with the visual order is the defect this frame is most prone to, because grids make it so easy.
  • Shared controls state their scope. A control in the header is labelled with what it governs ("Scope every module to an area"), and its current value is legible from the modules it has scoped — each module repeating the scope it is showing, so no figure is orphaned from the filter that produced it.
  • Status is never colour alone. A module signalling a breach carries the figure and a word; the colour is reinforcement. This is the frame's business because scanning for "whatever is red" is exactly the behaviour it invites.
  • A module updating in place does not steal focus or move the grid. Where a module re-reads, its region keeps its height and its position; an arrival worth announcing is announced politely, by a module that names itself.
§10

Content rules

Conditional — included: the frame only pays off if the first viewport earns its place
  • The first viewport carries the most consequential information. Prominence is assigned deliberately, not mechanically or alphabetically or by build order. If everything is equally prominent, nothing is — and the reader with eleven minutes does the prioritising the frame refused to do.
  • Each module is independently comprehensible. Its heading says what it is about; its figures carry their units, their period and their scope. A module that means something only because of the module beside it has borrowed meaning from spatial proximity, and proximity does not survive §11.
  • No label depends on adjacency. A figure whose unit sits in a neighbouring module, a legend shared across two modules, a heading that reads as a continuation of the one above it: all break the moment the grid reflows to one column.
  • Say when the figures are from. Every module states its period or its as-of time, either its own or the header's. A dashboard whose numbers have no stated age gets trusted at 07:15 and blamed at 15:00.
  • A module shows one thing well. If a module needs three headings and two tables, it is two modules — or a screen of its own, reached from here.
  • Give depth a route, not a summary. Where a figure raises a question, the module links to the screen that answers it rather than growing until it becomes that screen.

Do

  • "Nonconformances open — PL-04, shift C, internal PPM against a target of 1,500." Read alone, in one column, on a phone at the gate, it still says exactly what it is.

Don't

  • "Open: 14 · 6 · 3" with the meaning of the three numbers in the module to its left. At desk width it looks efficient; in the single-column form it is unreadable, and it was always unreadable to anyone using headings to navigate.
§11

Responsive

Unconditional
  • Expanded. Multiple simultaneous columns with differentiated module spans, as declared in §03.
  • Intermediate. Modules reduce their span while priority and logical sequence are preserved: a third becomes a half, a half becomes full. Which modules share a row changes; which module comes first does not.
  • Constrained. The grid normally becomes a single ordered stream — one module per row, in the authored order. This is the form in which module ordering (§03) and the first-viewport rule (§10) do all the work, because nothing is beside anything.
  • Visual reflow must never produce a reading order inconsistent with DOM order (§08). Reflow is span arithmetic on one document order; a module that appears to move because of order or an explicit grid area is a defect, not a responsive form.
  • Modules keep their identity across the forms. Same heading, same scope statement, same content — a module does not shed its title or its units to fit a narrower column; if it cannot fit, it shows less data, not less label.
  • A module may cap its own height and scroll internally, but the grid does not. Competing scroll containers across a grid of eight modules make the whole screen unnavigable.

§12

Anti-patterns

Unconditional
  • Calling any page that contains cards a dashboard. Cards are a grouping device; a dashboard is a claim about multiplicity and independence (§01). Most "dashboards" that fail review are one task surface with tiles above it.
  • Using it for sequential content. A report meant to be read in order belongs in single column; a grid tells the reader order does not matter.
  • Using it where one collection is the primary task surface. The queue is the screen; give it a collection workspace, or master-detail if members are worked beside it.
  • Using a grid for a stepwise task. A prescribed sequence in a layout that denies sequence — the user finds step 3 before step 1 and the frame is why.
  • Equal prominence for everything, whether by uniform tiles or by an alphabetical order nobody chose (§02, §10).
  • Modules that only make sense together — a legend in one, its units in another, a heading continued from its neighbour. The first reflow destroys them.
  • A whole-dashboard loading or error state because one module's source did not answer. Eight independent reads means eight independent failures; the failing module says so where it sits.
  • Shared controls that do not govern everything below them, or a module control mounted in the header — the reader cannot tell which figures a filter touched.
  • Modules that grow into screens. A module with tabs, its own toolbar and a paginated table is a page being smuggled into a grid; link to it instead.
  • A module count that keeps rising. Every added module dilutes the first viewport; a dashboard nobody can scan in a minute is a report with worse typography.
§13

Implementation notes

Unconditional
  • One grid, spans as data. Build region 2 with Grid and one GridItem per module, and derive each span from the declared column count so a change of count does not require re-authoring every module. Compose modules from Card or Surface with Stack, and place Table, List, DescriptionList, Badge, Skeleton, Alert and EmptyState inside them as the module needs.
  • Author the modules once, in the reading order, and never re-place them. Responsive behaviour is span arithmetic; if a product needs a different order at a different width, that is a different order and it changes the document, not just the CSS (§08).
  • Every module track needs min-width: 0. A wide table or a long unbroken part number will otherwise push its module past its span and silently take a neighbour's width.
  • Modules stretch to their row, and their content does not have to. Align items to stretch so a row of modules reads as one band, and let each module's content sit at the top rather than distributing to fill — vertically centred figures in unequal modules look like a fault.
  • One request boundary per module. Each module owns its own read, its own loading treatment and its own failure; nothing coordinates them, and no module may block another's render. A shared control changing scope re-reads every module independently.
  • Reserve module height where the data arrives late. A grid that re-lays itself out three times as eight reads land is unusable in the first ten seconds, which is most of the eleven minutes.
  • Levels report levels. An OEE bar, a utilisation figure or a capacity meter is something that is simply true — role="meter" or a chart, never Progress, which is for work in flight.
  • Frame state is limited to the shared controls. The scope and period in the header live in the frame (and belong in the URL where the screen is shared or bookmarked); everything else lives in the module that owns it.

Omitted, with reasons — §04 Variants: one structural form; column count, spans and order are properties (§03) and the reduced-span and single-stream arrangements are §11 consequences rather than standing choices. · §05 Sizes: the frame names no size or density classes — the column count in §03 and the spacing and density tokens carry it, and each module's contents keep their own size scales. · §06 States: the frame holds no state of its own beyond the shared controls' current values; module loading, empty and failure states are owned entirely by the modules (§13), and aggregating them here would be exactly the child-state list the standard forbids. · §07 Keyboard: the frame creates no keyboard relationship between modules — tab order follows document order, there is no region collapse or focus transfer to own, and heading-level navigation is stated in §08 where it belongs. · §09 Motion: no region collapses, expands or is revealed; a module refreshing in place is a module concern and must not move the grid (§13). · §14 Developer notes: nothing technical remains once §13 is written — the per-module request boundary, the span derivation and the one piece of frame state are all stated there.
